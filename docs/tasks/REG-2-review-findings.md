# REG-2 — разбор ревью

Ревьюер: Claude Code. Дата: 2026-09-21. Реализация: Devin, `6e3fff2`.
Постановка: [`REG-2-batch-similarity-integration-test.md`](REG-2-batch-similarity-integration-test.md).

**Вердикт: принято.** SQL пакетной близости теперь исполняется настоящим тестом на настоящем
pgvector, и тест краснеет на смысловой поломке запроса. Одна мелочь в покрытии.

## Что проверено исполнением

`TestEmbeddingRepository_FindSimilarNotesBatch` — за тегом `integration`, поднимает свой
контейнер pgvector, 7–8 с:

```
go test -tags=integration ./internal/infrastructure/db/postgres/ -run …Batch
--- PASS: TestEmbeddingRepository_FindSimilarNotesBatch (7.98s)
```

Без `-tags=integration` — `[no tests to run]`: тест не виден обычному `go test`. Это по замыслу
(так же гоняются все интеграционные), но стоит помнить: «прогнал `go test ./...`, зелёный»
про этот тест ничего не говорит.

## Мутации SQL `FindSimilarNotesBatch`

| Мутация | Тест | Вывод |
|---|---|---|
| убрать `GREATEST(0, LEAST(1, …))` — ограничитель `[0, 1]` | **красный** | `score -1 out of [0, 1]`; `expected far score 0.0 after clamping, got -1` — тест ловит и диапазон, и конкретное ожидание по «далёкой» паре |
| убрать `e1.note_id != e2.note_id` — заметка находит саму себя | зелёный | тест не утверждает, что источник не входит в свои же результаты |
| `AND e2.model_name = ?` → `… OR TRUE` | зелёный | холостая мутация: то же условие стоит в `JOIN … e1.model_name = e2.model_name`, поведение не меняется |
| `score DESC` → `score ASC` | зелёный | тоже холостая: сортировка идёт по `e1.note_id, e2.note_id` раньше score, у пары одна строка — порядок score ни на что не влияет |

Первая моя редакция мутации с моделью убрала плейсхолдер и уронила тест ошибкой «expected 2
arguments, got 3» — это падение по синтаксису, не по смыслу, и доказательством не считается.
Переделано с сохранением плейсхолдера.

## Мелочь

Самоисключение не проверено: с убранным `e1.note_id != e2.note_id` источник попадает в собственные
результаты со score 1.0, и тест это пропускает. Потребитель (`GammaLinkGenerator`) от этого
защищён своей проверкой `s.NoteID == sourceID`, поэтому не блокер — но контракт репозитория
«похожие заметки не включают саму заметку» должен утверждаться там, где он реализован. Одна
строка в тесте.

## Принято без замечаний

- Фикстура с фиксированными UUID и объяснением, почему они такие (`ORDER BY note_id` по байтам) —
  редкий случай, когда тест объясняет свои константы.
- Покрыты: старая модель не попадает, заметка без эмбеддинга не попадает, диапазон score, пакет
  из двух источников.

## Поправка ревьюера, 2026-09-23

Вердикт «принято» был ошибкой в одном пункте, и пункт главный. Мутация `score DESC → score ASC`
выше записана как «холостая: сортировка идёт по `e1.note_id, e2.note_id` раньше score».
Причина названа верно, вывод — нет: это значило, что `FindSimilarNotesBatch` возвращает на
каждый источник соседей **с наименьшими UUID**, а не ближайших. Тест при этом прямо утверждает
выбор далёкой заметки вместо близкой («the selected far target proves clamping»), и это было
принято как проверка ограничителя `[0, 1]`.

Последствие проверено живьём 2026-09-23: `gamma-links-regenerate` связал 200 автосвязей всего
с тремя заметками — с наименьшими UUID; в настоящую пару ближайших попали 3 из 200.
Исправление и перевёрнутый тест — [`LINKS-3-batch-similarity-order.md`](LINKS-3-batch-similarity-order.md).
