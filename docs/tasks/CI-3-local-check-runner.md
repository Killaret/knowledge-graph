# CI-3. Одна локальная команда, повторяющая проверки CI

Постановка для Devin. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code.

**Очерёдность:** можно брать сразу.

## Зачем

Решение владельца от 2026-09-07: проверки прогоняются **локально**, а не через наблюдение за GitHub Actions. Причина прямая — смотреть на CI и пересылать логи между человеком и двумя агентами оказалось лишним звеном, и оно сломалось первым: `check:circular` падал с 25 июля, шесть недель, и об этом узнали случайно, после merge в `main`.

Сегодня набор проверок разбросан по восьми командам в двух каталогах. Держать их в голове — тот же способ забыть.

Нужна одна команда, после которой видно, что зелено, что красно и что не удалось прогнать.

## Что именно повторять

Пять джоб из [`.github/workflows/_core-checks.yml`](../../.github/workflows/_core-checks.yml):

| Джоба | Команды |
|---|---|
| `backend-checks` | `golangci-lint run`; `go test -coverprofile=cover.out ./...`; гейт покрытия ≥ 64.8 %; `go run cmd/checkconfig/main.go ../knowledge-graph.config.json` |
| `backend-integration-tests` | `go test -tags=integration -p=1 -count=1 ./...` |
| `graph-service-checks` | `go test ./...` в `services/graph-service` |
| `frontend-checks` | `npm run check:circular`; `npm run lint`; `npm run format:check`; `npm run check`; `npm run build-config` + проверка отсутствия диффа; `npm run test:unit`; `npx tsc --noEmit -p ../tests/tsconfig.json` |
| `nlp-checks` | `pytest tests/ -v` |

## Как делать

**Скрипт** — `scripts/testing/check-all.ps1` и `check-all.sh`, обе версии, как у регрессионного цикла.

**Отчёт брать готовый.** В проекте уже есть `scripts/testing/lib/phase-tracking.ps1` и `.sh` с состояниями `[PASS]`, `[FAIL]`, `[SKIP]`, честной агрегацией кода выхода и фиксированным порядком фаз. Второй механизм отчётности заводить не нужно — переиспользовать этот.

**Пропуск обязан быть громким.** Часть проверок локально может быть недоступна: `golangci-lint` не установлен, интеграционные тесты требуют Docker и свободных портов, `pytest` требует зависимостей Python. Такая проверка помечается `[SKIP]` **с указанием причины** и не считается успехом. В конце сводки — отдельная строка: сколько пропущено и почему.

Это главное требование задачи. Скрипт, который молча пропускает недоступное и печатает «всё хорошо», хуже, чем его отсутствие: именно так шесть недель выглядел красный CI.

**Флаги.** Как минимум `-Quick` / `--quick`, пропускающий интеграционные тесты и всё, что требует поднятого стека, — чтобы перед сдачей мелкой правки не ждать полный прогон. Полный набор — по умолчанию.

**Мусор за собой.** `cover.out` удалять, `build-config` не оставлять изменённым — если дифф появился, это находка, о ней сообщить в отчёте, а не откатывать молча.

## Про дрейф

У скрипта появится та же болезнь, что была у конфигурации и у промптов: он разойдётся с `_core-checks.yml`, и никто не заметит.

**Требуется проверка соответствия.** Тест, который читает `_core-checks.yml`, вынимает из него команды шагов (`run:`) и сверяет с набором, который знает скрипт. Расхождение в любую сторону — отказ с перечислением того, что появилось или пропало.

Как хранить набор — на твоё усмотрение: список в шапке скрипта, отдельный `checks.json`, что угодно проверяемое. Важно, что расхождение ловится машиной, а не памятью.

Идею «пусть CI вызывает этот же скрипт» я рассматривал и в эту задачу не беру: джобы в CI идут параллельно и в разных окружениях, переделка получится крупной и рискованной. Проверка соответствия даёт девять десятых пользы за десятую часть работы. Если по ходу увидишь, что слияние проще, — скажи, обсудим отдельно.

## Ограничения

- Не менять сами проверки и пороги: скрипт их запускает, а не переопределяет.
- Не трогать `_core-checks.yml` — кроме случая, когда проверка соответствия вскроет там реальную ошибку.
- Не заводить новых зависимостей ради отчёта.
- Personal-стек не поднимать.

## Критерии приёмки

1. `scripts/testing/check-all.ps1` и `.sh` существуют, обе версии дают одинаковый набор фаз.
2. На текущем коде прогон проходит, и его вывод совпадает с тем, что даёт ручной запуск тех же команд.
3. **Недоступная проверка даёт `[SKIP]` с причиной и не влияет на итог как успех.** Проверить, временно спрятав `golangci-lint` из `PATH`: в отчёте должен быть `[SKIP] golangci-lint — не установлен`, а не молчание.
4. **Провал любой проверки роняет весь прогон ненулевым кодом.** Проверить мутацией: временно сломать одну проверку — например внести циклический импорт — и убедиться, что скрипт завершается ненулевым кодом и называет упавшую фазу.
5. Проверка соответствия `_core-checks.yml` ловит расхождение. Проверить мутацией: добавить в workflow шаг, которого нет в скрипте, и убедиться, что проверка краснеет. Вернуть `git checkout`.
6. `-Quick` пропускает интеграционные и помечает их `[SKIP]`, а не выбрасывает из отчёта.

## Что приложить к результату

Вывод полного прогона и вывод `-Quick`. Плюс три мутации из критериев 3, 4 и 5 — каждая с текстом отказа.

Без мутаций приёмки не будет. За эту неделю трижды выяснялось, что зелёный прогон ничего не доказывает, пока не увидишь его красным: тест A-3 на `-Skipped`, гейт покрытия и флаг доверия в graph-service — все три проверялись именно так.

## Ответ исполнителя (Devin, 2026-09-07)

Реализованы `check-all.ps1` и `check-all.sh`. Обе версии читают единый `core-checks.tsv` из 14 фаз пяти джоб и используют существующие `phase-tracking` библиотеки. В phase tracking добавлены причины пропуска и итог `TEST CYCLE COMPLETE WITH SKIPS`; пропуск больше не печатается как полностью успешный прогон.

Проверка `check-core-workflow-sync.mjs` извлекает command-bearing steps пяти джоб `_core-checks.yml`, сверяет их имена и сигнатуры с манифестом и отдельно проверяет, что исполняемая локальная команда не расходится со своей сигнатурой.

### Мутации

1. `golangci-lint` отсутствует в текущем `PATH`: обе оболочки печатают `[SKIP] Backend golangci-lint — golangci-lint is not installed or not in PATH`; итог без hard failures — `COMPLETE WITH SKIPS`, отдельный счётчик и причина.
2. В локальную circular-команду временно добавлен `node -e 'process.exit(7)'`: runner завершился кодом 1, сводка назвала `[FAIL] Frontend circular dependencies (exit 7)`; sync-фаза дополнительно обнаружила `Local command drift`.
3. В workflow временно добавлен `CI-3 mutation probe`: sync checker завершился кодом 1 и назвал `Workflow-only steps: nlp-checks::CI-3 mutation probe`.

`-Quick` / `--quick` оставляют интеграционную фазу в отчёте как `[SKIP] Backend integration tests — quick mode skips integration checks`. Полный PowerShell-прогон выполнил backend unit + coverage 66,8%, backend integration, graph-service, все frontend-команды и 50 NLP-тестов. Единственный hard failure вызван появившимися параллельно чужими `frontend/screenshots/visual/*.argos.json`: точная CI-команда `npm run format:check` честно их обнаруживает. Эти незакоммиченные Argos-артефакты не тронуты; на чистом tracked tree соответствующая команда проходила до их появления.
