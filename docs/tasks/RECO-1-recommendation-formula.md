# RECO-1. Формула рекомендаций: одна реализация, три компонента, один ответ

Постановка для Devin. Ставит Claude Code, реализует Devin, проверяет Claude Code.
Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

**Решение владельца, 2026-09-17: формулу переделать, чтобы работала.**

## Что есть сейчас — проверено по коду

Рекомендации задуманы как `score = α·граф + β·смысл + γ·слова`. Коэффициенты в
[`knowledge-graph.config.json`](../../knowledge-graph.config.json): **α = 0.5, β = 0.5, γ = 0.2**.
Формула реализована **дважды**, и обе реализации неполные.

**Воркер** — [`traversal_service.go:151`](../../backend/internal/domain/graph/traversal_service.go):

```go
// Пока semantic score не реализован — 0
semanticScore := 0.0
```

Считает граф и слова; **смысл — константа ноль**. β = 0.5 умножается на ноль. После
нормализации на α+β+γ = 1.2 фактическое соотношение — **граф 71 %, слова 29 %, смысл 0 %**.

**graph-service** — [`recommendations.go:82`](../../services/graph-service/internal/engine/recommendations.go):

```go
score := alpha*graphScore + beta*semanticScore
```

Считает граф и смысл (косинус из `note_embeddings`); **γ отсутствует**, ключевые слова не
участвуют вовсе.

**Что отдаётся пользователю** — [`note_handler.go:1548`](../../backend/internal/interfaces/api/notehandler/note_handler.go):
эндпоинт `GET /notes/:id/suggestions` сначала отдаёт **предрасчитанные** рекомендации из базы —
их считает воркер. Живой путь через graph-service — только когда предрасчитанных нет, то есть
для свежесозданной заметки до первого прогона `RefreshRecommendations`.

Итого: в карточке заметки почти всегда результат воркера — граф и слова, без смысла. Три
коэффициента, которые владелец помнит как единую формулу, **нигде не работают вместе**. Любое
вложение в модель эмбеддингов сегодня до β-компонента не доходит.

**Автосвязи.** [`gamma_link_generator.go`](../../backend/internal/application/recommendation/gamma_link_generator.go)
создаёт связи по близости эмбеддингов, ограничивая исходящую степень (по умолчанию 2 — комментарий
в коде объясняет, что больше взорвёт материализованное представление `note_links_closure`). Класс
написан, покрыт тестами и **не подключён**: ноль конструкторов вне тестов, ноль вызовов
`GenerateForNote`. Связи в графе создаются только руками ([`link_handler.go`](../../backend/internal/interfaces/api/linkhandler/link_handler.go))
и явным списком при импорте. Поэтому α-компонент считается только по ручным связям.

## Что сделать

### 1. Одна формула в одном месте

**Две реализации одной формулы запрещены** — это и есть дефект. Место — **graph-service**:
по ADR-013 он и есть аналитический периметр, читает базу напрямую под read-only учёткой, уже
ходит в `notes`, `links`, `note_links_closure`, `note_embeddings`; добавить чтение
`note_keywords` — в рамках того же периметра.

- В `Recommendations` добавить γ-компонент: Жаккар по `note_keywords` между исходной и
  каждым кандидатом. Метод сходства — из той же настройки, что сейчас у воркера
  (`RECOMMENDATION_KEYWORD_SIMILARITY_METHOD`), чтобы не завести третий источник правды.
- Коэффициенты α, β, γ — **из одной настройки**, читаемой обоими сервисами; сегодня
  graph-service держит свои `defaultRecAlpha/Beta`, а backend — свои. Один источник, один
  набор умолчаний, нормализация на сумму в одном месте.
- Предрасчёт в воркере (`RefreshService`) **вызывает graph-service**, а не считает сам.
  Воркеру нужен клиент graph-service — сейчас его там нет (`SetGraphServiceClient` в
  `cmd/worker/main.go` не вызывается).

### 2. Судьба резервного пути

`TraversalService.GetSuggestions` в backend остаётся только как **деградированный режим** на
случай недоступности graph-service, и тогда:

- он не содержит собственной копии формулы с другими компонентами — либо те же три, либо
  явно помеченный ответ «рекомендации по графу, деградированный режим» с записью в лог и
  полем в ответе, чтобы пользователь и тесты отличали его от полного;
- строка `semanticScore := 0.0` с комментарием «пока не реализован» **удаляется**: либо
  компонент реализован, либо его нет в формуле честно.

Что выбрать — решает Devin с обоснованием в этом файле; условие одно: по одним данным два
пути не могут давать **разный порядок**, не сказав об этом.

### 3. Автосвязи — решение владельца ожидается

Варианты:

- **Подключить** генератор в воркер после `ComputeEmbedding`, с ограничением исходящей степени
  2, как написано в коде. Тогда α-компонент начинает видеть смысловую близость через связи,
  а не только через β. Плюс: связи видны пользователю в графе. Минус: рост
  `note_links_closure`; автосвязи надо отличать от ручных в интерфейсе (`source_type = gamma`
  в домене уже есть).
- **Удалить** класс и тесты как незавершённый замысел. Плюс: меньше мёртвого кода. Минус:
  α остаётся исключительно ручным.

Рекомендация — подключить, но **после** RECO-1 и MODEL-1: автосвязи считаются по модели, и
смена модели их обесценит (решение 5). Владелец отдельно заметил: автосвязи не отменяют
проверок «связей нет» и «ключевых слов нет» — это сигналы качества заметки, см. NOTE-QUALITY-1.

**Не подключать в рамках RECO-1** без записи решения владельца в `DECISIONS.md`.

### 4. Доказать, что каждый компонент двигает выдачу

Фикстура из четырёх заметок, где кандидаты различимы **только одним** компонентом:

- A связана с B ручной связью, эмбеддинги и ключевые слова у всех одинаковые → B первая
  только благодаря α;
- эмбеддинг C ближе всех к A, связей и общих слов нет → C первая только благодаря β;
- у D три общих ключевых слова с A, связей нет, эмбеддинг далёкий → D первая только благодаря γ.

**Мутации:** обнулить α → B теряет первое место; обнулить β → C теряет; обнулить γ → D теряет.
Каждая мутация краснеет ровно один тест. Плюс: предрасчитанный путь и живой путь на этой
фикстуре дают **один и тот же порядок** — отдельный тест, который сравнивает оба ответа.

## Adversarial-фаза — по норме, находки сюда

- `JaccardSimilarity` возвращает **1.0 при двух пустых наборах** — две заметки без ключевых
  слов «полностью похожи». Записать, что происходит с такими парами после переноса γ в
  graph-service, и решить: 0.0 для пустых или исключать компонент.
- Заметка без эмбеддинга: β должен быть 0, а не ошибкой и не 0.5.
- Кандидат из `note_links_closure` с расстоянием 0 (сама заметка) — не должен попасть в выдачу.
- α, β, γ все нули в конфиге — сервис обязан упасть на старте с внятным сообщением, а не
  молча взять умолчания.

## Критерии приёмки

1. `git grep` по обоим сервисам находит **одну** реализацию `alpha*…+beta*…+gamma*…`.
2. Строки `semanticScore := 0.0` нет; комментария «пока не реализован» нет.
3. Коэффициенты читаются из одного источника; изменение в конфиге меняет выдачу обоих путей.
4. Три мутации краснеют по одному тесту каждая; тест равенства путей зелёный; вывод приложен.
5. Ответ `GET /notes/:id/suggestions` содержит все три составляющие (`graph`, `semantic`,
   `keyword`) с ненулевыми значениями там, где данные есть, — проверено живьём на тест-стеке,
   вывод приложен.
6. `docs/ARCHITECTURE_SUMMARY.md` и ADR-013 описывают, где формула и почему; старая
   картина «BFS в backend» из документов убрана.
7. `check-all` зелёный.

## Ограничения

- Автосвязи не подключать без решения владельца (п. 3).
- Модель эмбеддингов не менять — MODEL-1.
- `note_links_closure` не переделывать; если Жаккар по кандидатам из closure оказывается
  дорогим, ограничить кандидатов (`maxRecCandidates` уже есть), а не таблицу.
- Personal-стек не поднимать.
