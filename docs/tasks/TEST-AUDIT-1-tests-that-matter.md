# TEST-AUDIT-1. Тесты, которые проверяют нужное

Статус: **бэклог — Devin, большая; по этапам.** Постановка владельца 2026-09-29, запись — Claude Code.

**Решение владельца (2026-09-29, TEST-AUDIT-1):** Devin проверяет все тесты — не покрытие, а смысл:
тест действительно проверяет поведение, соответствует нашим нормам и скиллам и оправдан. Слова
владельца: «что мы действительно проверяем то, что нужно, а не просто ради того, чтобы проверить».

## Сколько

Около 380 тестовых файлов на 2026-09-29: фронтенд — 155 модульных (1 589 тестов) и 29 e2e, 15
BDD-сценариев, бэкенд — 155, граф-сервис — 12, NLP — 6, скрипты — 8.

## Вердикты

По файлу, у больших файлов — по группам:

- **проверяет поведение** — падает, когда ломается то, что тест называет;
- **проверяет реализацию** — ломается от переделки без смены поведения;
- **проверяет заглушку** — утверждения про мок, а не про код. Пример из жизни: тест `getSuggestions`
  подменял ответ голым массивом, а API отдаёт конверт — клиент был сломан при зелёном тесте
  (исправлено в `5a9de23`);
- **дублирует** — то же поведение держит другой тест (назвать какой);
- **лишний** — проверяет то, что не может сломаться, или неважное;
- **ломкий или дорогой** — нестабилен, или e2e там, где хватило бы модульного.

## Как

1. Реестр по образцу [`SPEC-AUDIT-1-register.md`](SPEC-AUDIT-1-register.md): файл, область, вердикт,
   доказательство.
2. Доказательство «проверяет поведение» — мутация: временно сломать правило, которое тест называет,
   тест краснеет, код возвращается через `git checkout`. Одна-две на файл, не на каждый тест.
3. Сверка с нормой: раздел тестирования [`.windsurfrules`](../../.windsurfrules) и скиллы
   `kg-regression`, `kg-layers`, `kg-graph-3d`, `kg-backup` — тест живёт на своём слое, e2e идут на
   изолированном стенде, снимки детерминированы.
4. Этапы: A — фронтенд модульные; B — бэкенд и граф-сервис; C — NLP и скрипты; D — e2e, BDD,
   визуальные. Каждый этап — отдельно на ревью.
5. Исправление: тест, который не ловит поломку, переписать так, чтобы ловил. Удаление — только с
   доказательством в реестре: какой тест держит это поведение или почему проверять нечего.

## Критерии приёмки

1. Реестр этапа полон — сторож сверяет тестовые файлы с реестром.
2. У каждого «проверяет поведение» — красная мутация или ссылка на уже записанную.
3. Переписанные тесты падают на поломке, которую раньше пропускали, — показано.
4. У каждого удалённого — что держит его поведение.
5. Сводка по вердиктам и областям — в разборе этапа.
