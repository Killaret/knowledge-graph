# W-1. Валидация и настройка формулы весов на ground truth

Родилась из обсуждения NLP-4/MODEL-2 с владельцем 2026-09-19: выяснилось, что
трёхкомпонентная формула рекомендаций существует в коде, но **ни разу не
работала целиком и никогда не проверялась на данных**.

## Что есть в коде (разведка 2026-09-19)

Три отдельные сущности, которые легко перепутать:

| Сущность | Где | Что делает |
|---|---|---|
| Вес связи `links.weight` | `backend/internal/application/linkweight/service.go` | косинус эмбеддингов `title+content` пары через NLP `/similarity` — **один параметр, без формулы** |
| Автолинк (gamma-связь) | `backend/internal/application/recommendation/gamma_link_generator.go` | pgvector-косинус → топ-2 → связь `related` с весом = косинус |
| Формула рекомендаций | `backend/internal/domain/graph/aggregation.go` + `traversal_service.go` | `score = α·graphScore + β·semanticScore + γ·keywordScore` |

Split-brain формулы рекомендаций:

| Путь | α (граф) | β (семантика) | γ (keywords) |
|---|---|---|---|
| in-memory `traversal_service.go` | есть | **заглушка `0.0`** (строка 160) | есть |
| graph-service `engine/recommendations.go` | есть | есть (pgvector-косинус) | **отсутствует** |

Дефолт: `α=1, β=0, γ=0` — живёт только графовый компонент. Веса никогда
не подбирались; семантический вход — MiniLM@128 по сырому тексту; keyword-вход —
YAKE-шум. Формула валидна как подход (стандартный гибридный скоринг), но не
проверена.

## Механика распространения веса (разобрано по коду 2026-09-19)

`runBFS` (`domain/graph/bfs.go:67-70`): вес узла = **произведение весов рёбер
по пути** × `decay` за каждый шаг глубже первого (decay=0.5 по умолчанию).
`max`-агрегация = лучший путь, `sum` = сумма путей. graph-service считает
то же на `note_links_closure`: `weight × decay^distance`.

**Критическое следствие** (`graph-service/db/postgres_client.go:408-414`):
кандидаты рекомендаций берутся **только из транзитивного замыкания связей** —
заметка без связей (прямых или через других) вообще не становится кандидатом,
независимо от векторной близости. Семантика лишь переранжирует уже достижимых
соседей. **По решению владельца это дефект архитектуры**: семантический канал
рекомендаций обязан работать по всему корпусу (векторные ближайшие соседи),
не завися от наличия рёбер — иначе система рекомендаций вырождается в
«перемешивание уже связанного».

## Топ-2 автолинков — техническое ограничение, отвергнуто как значение

`gamma_link_generator.go:19-21`: ограничение исходящей степени защищает
материализованное представление `note_links_closure` от экспоненциального
раздувания на плотных графах. «Две связи» — не подобранное значение, а
предохранитель; владелец его отверг как слишком малый. Единственный порог —
`Score > 0`, то есть его фактически нет (косинус почти всегда >0).
Правильные `maxOutDegree` и порог близости подбираются эмпирически на корпусе
владельца: ищем точку, где автолинк **начинает связывать вещи, которые
логически связаны не должны быть** — это и есть баланс качества.

## Семантика сущностей (решение владельца, 2026-09-19)

| | Ручная связь | Автолинк | Рекомендация |
|---|---|---|---|
| Что делает | пользовательское прямое ребро («курс → урок») | **эфемерная слабая связь** — материализованная подсказка системы | временная подсказка по запросу |
| Природа | намерение пользователя | часть системы рекомендаций: та же семантика, записанная в граф | ранкинг по запросу |
| Цена ошибки | пользователь сам отвечает | слабое ребро — дёшево, регенерируется | ничего не портит |
| Канал | — | семантика (+ возможно keywords) | семантика по всему корпусу + граф + keywords |

Ключевое: автолинк — это **часть системы рекомендаций**, а не пара графу.
Семантический канал подсказок — независим от связей; графовый канал —
дополнительный сигнал поверх него. Коэффициенты/пороги у материализации
(автолинк) и ранкинга (подсказка) — разные, подбираются на одном ground truth.

## Ground truth для валидации

`metadata.import.folder_path` у 87 заметок Personal-базы — структура папок
закладок владельца. Гипотеза проверки: заметки из одной папки должны получать

кластеризации.

## Состав работ

1. **Eval-харнес**: скрипт/команда, которая для каждой заметки с folder_path
   считает score против остальных, меряет precision@k / MAP против
   принадлежности к папке. Варианты формулы — параметризованы.
2. **Починить split-brain**: semantic-компонент в in-memory пути сейчас
   заглушен; keyword-компонент отсутствует в graph-service. Решить, где живёт
   каноническая реализация (graph-service — вероятно там, in-memory — fallback).
   Плюс архитектурный дефект: **семантический канал независим от связей** —
   кандидаты по векторам ищутся по всему корпусу, а не только по closure;
   графовый канал остаётся отдельным сигналом.
3. **Grid-search α/β/γ** на корпусе владельца по метрике из п.1. Варианты
   keyword-метода (jaccard/overlap/tversky/weighted_jaccard/cosine) — тоже
   ось поиска.
4. **Вес связи** — открытый вопрос: оставить косинус doc-векторов или перейти
   на парное сходство чанков (max/mean попарно) после MODEL-2. Парное
   теоретически лучше для длинных заметок — проверить тем же харнесом.
5. **Автолинк**: подбор порога близости и `maxOutDegree` на том же харнесе —
   отдельная операционная точка (строгая, см. выше); проверить, выдерживает
   ли `note_links_closure` степень >2 на реальном корпусе.
6. Зафиксировать найденные веса в `config/backend.json` + документировать
   методологию, чтобы повторить при смене модели.

## Зависимости

- **Ждёт MODEL-2 + NLP-4 (+ желательно NLP-2)**: настраивать веса на мусорных
  входах бессмысленно — сначала чистые векторы и ключевые слова.
- Связано: RECO-1 (формула рекомендаций), LINKS-1 (автолинки — пороги подбирать
  тем же харнесом).
