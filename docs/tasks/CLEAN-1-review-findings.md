## Блокер: `-WslOptimize` без прав администратора рапортует об успехе

`diskpart` требует повышения прав. Без них он **не запускается вовсе** — процесс не стартует, и PowerShell бросает `ResourceUnavailable`:

```
Program 'diskpart.exe' failed to run: The requested operation requires elevation.
код выхода: (пусто)
```

`$LASTEXITCODE` при несостоявшемся запуске **не выставляется**. Скрипт делает так (`cleanup-docker.ps1:274-278`):

```powershell
$output = & diskpart /s $scriptPath 2>&1
$code = $LASTEXITCODE
...
Register-Phase "optimize-disk" -ExitCode $code
```

Проверил, что из этого выходит:

```
$LASTEXITCODE после несостоявшегося запуска: []
  [PASS] optimize-disk
Test-AnyFailed: False
```

**Итог: `cleanup-docker.ps1 -WslOptimize` без админа печатает `[PASS] optimize-disk`, завершается нулём, и диск не сжат.** Ровно тот дефект, ради которого писалась задача, уцелел в единственном шаге, который без повышения прав работать не может.

Хуже того, поведение недетерминированное: `$LASTEXITCODE` сохраняет значение от предыдущей команды скрипта, поэтому результат зависит от того, что выполнялось раньше.

### Что нужно

Проверять повышение прав **до** запуска шага и отказываться внятно:

```powershell
$isAdmin = ([Security.Principal.WindowsPrincipal]
    [Security.Principal.WindowsIdentity]::GetCurrent()
).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)
```

Без прав — `[FAIL]` или `[SKIP]` с причиной «требуются права администратора», но не `[PASS]`. Пропуск допустим, если вы решите, что отсутствие админа — не ошибка; молчаливый успех недопустим.

Отдельно: `& diskpart` заворачивать в `try/catch`, потому что несостоявшийся запуск — это исключение, а не код возврата, и `$LASTEXITCODE` про него ничего не знает.

Приёмка следующего раунда — прогоном без повышения прав: шаг обязан быть красным или явно пропущенным, а общий код выхода — соответствовать.

Всё это следующим раундом: один связный раздел про очистку, с реальными командами, реальными флагами, требованием прав и рекомендацией по периодичности.

## Тест честности не ловит частичный откат

`test-cleanup-honesty.ps1` заявлен как якорь мутации для критерия 8. Проверил: вернул шаг 1 к безусловному рапорту (`if ($false)` вместо проверки кода) — **тест остался зелёным**, `ALL PASSED`, код 0.

Причина в гранулярности: проверка `[PASS] ps1 prints [FAIL] not [SUCCESS]` удовлетворяется тем, что *какой-нибудь* шаг покраснел. Откат одного шага из девяти проходит незамеченным.

Полный откат тест поймает, поэтому формально критерий 8 выполнен, и блокером это не считаю. Но защита слабее, чем выглядит: чинить стоит проверкой по каждой фазе, а не по наличию строки в выводе.

## Принято без замечаний

- **Пофазная проверка кода возврата** — девять мест, `$LASTEXITCODE` после каждой команды, `phase-tracking` переиспользован вместо третьего механизма отчётности.
- **Обе версии сошлись** — шелл тоже на фазах, поведение одинаковое.
- **`-DryRun` работает** — проверено тестом: ничего не удаляет и не зовёт `prune`/`rm`/`stop`.
- **Гейт по бэкапу** — `check-personal-backup.{ps1,sh}` перед шагами с томами, отказ при отсутствии свежего.
- **Порог свежести в одном месте** — `backup-policy.env`, читается и стражем, и проверкой. Просил не копировать значение; сделано лучше — заведён единый источник.
- **Страж честно описывает свою слепую зону** — комментарий про то, что вызов скрипта хук не видит и проверка живёт внутри скрипта.
- **VHD-цель починена** — только `%LOCALAPPDATA%\Docker\wsl`, чужие дистрибутивы больше не компактятся.
- **Процессы не убиваются** — вместо расстрела по маске ожидание освобождения файла до 60 секунд и отказ с сообщением. Это прямо снимает риск для томов Personal-стека.

## Предложение по существу задачи владельца

Проблема, из-за которой всё затевалось, — Docker разрастается, а `diskpart` требует админа и ручных танцев.

На этой машине **WSL 2.7.12**, а начиная с 2.0 поддерживается разреженный VHD:

```powershell
wsl --manage docker-desktop --set-sparse true
```

Диск начинает отдавать место обратно сам при завершении работы WSL — без прав администратора, без `diskpart`, без остановки Docker Desktop. Если это сработает, шаг `-WslOptimize` из ежедневного обихода уходит и остаётся аварийным инструментом.

Проверять не стал: команда меняет режим диска, а это не то, что ревьюер делает молча на машине владельца. Стоит попробовать до того, как вкладываться в починку `diskpart`-пути — возможно, чинить придётся то, чем перестанут пользоваться.
