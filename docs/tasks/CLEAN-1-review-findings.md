## Блокер: `-WslOptimize` без прав администратора рапортует об успехе

`diskpart` требует повышения прав. Без них он **не запускается вовсе** — процесс не стартует, и PowerShell бросает `ResourceUnavailable`:

```
Program 'diskpart.exe' failed to run: The requested operation requires elevation.
код выхода: (пусто)
```

`$LASTEXITCODE` при несостоявшемся запуске **не выставляется**. Скрипт делает так (`cleanup-docker.ps1:274-278`):

```powershell
$output = & diskpart /s $scriptPath 2>&1
$code = $LASTEXITCODE
...
Register-Phase "optimize-disk" -ExitCode $code
```

Проверил, что из этого выходит:

```
$LASTEXITCODE после несостоявшегося запуска: []
  [PASS] optimize-disk
Test-AnyFailed: False
```

**Итог: `cleanup-docker.ps1 -WslOptimize` без админа печатает `[PASS] optimize-disk`, завершается нулём, и диск не сжат.** Ровно тот дефект, ради которого писалась задача, уцелел в единственном шаге, который без повышения прав работать не может.

Хуже того, поведение недетерминированное: `$LASTEXITCODE` сохраняет значение от предыдущей команды скрипта, поэтому результат зависит от того, что выполнялось раньше.

### Что нужно

Проверять повышение прав **до** запуска шага и отказываться внятно:

```powershell
$isAdmin = ([Security.Principal.WindowsPrincipal]
    [Security.Principal.WindowsIdentity]::GetCurrent()
).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)
```

Без прав — `[FAIL]` или `[SKIP]` с причиной «требуются права администратора», но не `[PASS]`. Пропуск допустим, если вы решите, что отсутствие админа — не ошибка; молчаливый успех недопустим.

Отдельно: `& diskpart` заворачивать в `try/catch`, потому что несостоявшийся запуск — это исключение, а не код возврата, и `$LASTEXITCODE` про него ничего не знает.

Приёмка следующего раунда — прогоном без повышения прав: шаг обязан быть красным или явно пропущенным, а общий код выхода — соответствовать.

## Принято без замечаний

- **Пофазная проверка кода возврата** — девять мест, `$LASTEXITCODE` после каждой команды, `phase-tracking` переиспользован вместо третьего механизма отчётности.
- **Обе версии сошлись** — шелл тоже на фазах, поведение одинаковое.
- **`-DryRun` работает** — проверено тестом: ничего не удаляет и не зовёт `prune`/`rm`/`stop`.
- **Гейт по бэкапу** — `check-personal-backup.{ps1,sh}` перед шагами с томами, отказ при отсутствии свежего.
- **Порог свежести в одном месте** — `backup-policy.env`, читается и стражем, и проверкой. Просил не копировать значение; сделано лучше — заведён единый источник.
- **Страж честно описывает свою слепую зону** — комментарий про то, что вызов скрипта хук не видит и проверка живёт внутри скрипта.
- **VHD-цель починена** — только `%LOCALAPPDATA%\Docker\wsl`, чужие дистрибутивы больше не компактятся.
- **Процессы не убиваются** — вместо расстрела по маске ожидание освобождения файла до 60 секунд и отказ с сообщением. Это прямо снимает риск для томов Personal-стека.

## Про разреженный VHD: предложение проверено и снято

В первой редакции этого разбора я предложил заменить `diskpart` на разреженный диск WSL:

```powershell
wsl --manage docker-desktop --set-sparse true
```

**Проверил по просьбе владельца — не работает, и не должно.** WSL 2.7.12 отвечает:

```
Sparse VHD support is currently disabled due to potential data corruption.

To force a distribution to use a sparse VHD, please run:
wsl.exe --manage <DistributionName> --set-sparse true --allow-unsafe
```

Microsoft отключила режим из-за риска повреждения данных; включается только флагом `--allow-unsafe`. Внутри этого VHD лежат тома Personal-стека с реальными заметками владельца, поэтому форсировать я не стал и не рекомендую: у проекта отдельный хук и правило про бэкапы ровно затем, чтобы такого не делать.

**Путь `diskpart` остаётся единственным**, и блокер выше чинить нужно.

### Что показали замеры

Заодно посмотрел, насколько диск вообще раздут:

| Что | Размер |
|---|---|
| `docker_data.vhdx` на диске | 22,66 ГБ |
| Образы | 7,88 ГБ |
| Кэш сборки | **12,69 ГБ**, из них 6,51 ГБ высвобождаемо |
| Тома | 0,74 ГБ |

Двадцать два гигабайта VHD держат около двадцати одного гигабайта настоящих данных — то есть диск сейчас почти не раздут, и компактизации нечего возвращать. Основной объём даёт кэш сборки, накопленный пересборками стенда.

Отсюда правильный порядок, который стоит записать в документацию вместе с периодичностью: **сначала обычный прогон скрипта** — он и так делает `docker builder prune`, освобождая место *внутри* диска, — и только потом, если VHD остался заметно больше суммы из `docker system df`, компактизация с правами администратора. Компактизация без предварительной очистки бессмысленна: она возвращает Windows только то, что уже освободилось внутри.

**Замечание про тома в этом выводе.** `docker system df` показывает 6 локальных томов как «100 % reclaimable» — это включает тома Personal-стека, просто потому что их контейнеры не запущены. Ни `docker volume prune`, ни `-RemoveVolumes` по этой цифре запускать нельзя. Ровно от этой ловушки и защищает нынешняя тройная проверка в шаге 6.

### Гранулярность теста честности

В прошлом раунде откат одного шага проходил незамеченным. Появились пофазные проверки, но первую мою мутацию (`if ($false)` вместо проверки кода) они не поймали — и это не их вина: поток проваливается в `else`, где `Invoke-DockerStep` регистрирует отказ самостоятельно. То есть мутация была нерезультативной, дефекта не вносила.

Мутировал по-настоящему — заставил шаг проглотить отказ, `Register-Phase "stop-containers" -ExitCode 0`:

```
[FAIL] ps1 phase 'stop-containers' fails when docker is down
EXIT=1
```

Ловится. Замечание снято.

### Документация

Проверил всё, что перечислял, и **две мои претензии оказались ошибками**, о чём честно:

Плюс признак «пора»: файл `docker_data.vhdx` заметно больше суммы из `docker system df`.
