# DISK-1. Всё тяжёлое — на D:, системный диск не трогаем

Постановка: Claude Code, 2026-09-24. Исполнитель: Devin; шаги, которые требуют закрыть приложение
или прав администратора, делает владелец по готовым командам. **Первая в очереди Devin.**

**Решение владельца (2026-09-24, DISK-1):** «всё надо перенести на D» — кэши сборок, модели, данные
агентов, виртуальные машины. Модель в образ **не запекается**: общий кэш моделей на D: — единственное
место, куда ходят все стенды.

## Почему срочно

2026-09-23 на C: оставалось **7,1 ГБ** свободных; за час до этого — 14,5. Прогоны тестов на хосте,
сборки и сессии агентов пишут на C: по умолчанию, и никто этого не видит, пока диск не кончится.

## A. Модель не запекается в образ

`nlp-service/Dockerfile` по-прежнему качает снимок модели при сборке — строка 42,
`snapshot_download` в builder, и строка 66, `COPY` в итоговый образ. Так и в `ai-agents`, и в
`main`: последний раз Dockerfile правился 2026-09-20 (NLP-2). Общий кэш из `ba8914b` подключается
**только при запуске** (`${HF_CACHE_DIR:-./huggingface_cache}`) и перекрывает запечённую копию —
она не нужна, а каждая пересборка качает гигабайты: 2026-09-23 сборка тест-стенда ждала модель
больше получаса. Здесь же — прежняя строка бэклога NLP-BAKE-1.

1. Убрать запекание: ни `snapshot_download` при сборке, ни `COPY` кэша в образ.
2. Модель берётся только из смонтированного кэша. Если кэш пуст, а `HF_HUB_OFFLINE=1` — сервис
   падает сразу с понятным сообщением: какой каталог смонтирован, что задать в `HF_CACHE_DIR`, какой
   командой один раз скачать модель в общий кэш. Не молчаливый таймаут healthcheck.
3. `HF_CACHE_DIR=D:/kg-hf-cache` — умолчание для этой машины: в `.env.example` и `BOOTSTRAP.md`, а не
   закомментированным примером.

## B. Кэши инструментов — на D:

Одна корневая папка, например `D:\kg-build-cache\` (Claude Code уже пишет туда
`go-build`, `tmp`, `npm`, `logs`):

| Инструмент | Как переключить | Куда |
|---|---|---|
| Go, сборка | `go env -w GOCACHE=…` | `D:\kg-build-cache\go-build` |
| Go, модули | `go env -w GOMODCACHE=…` | `D:\kg-build-cache\go-mod` |
| Go, временные | `go env -w GOTMPDIR=…` | `D:\kg-build-cache\tmp` |
| npm | `npm config set cache … --location=user` | `D:\kg-build-cache\npm` |
| pip | `pip config set global.cache-dir …` | `D:\kg-build-cache\pip` |
| Playwright | переменная пользователя `PLAYWRIGHT_BROWSERS_PATH` | `D:\kg-build-cache\ms-playwright` |
| puppeteer | переменная `PUPPETEER_CACHE_DIR` | `D:\kg-build-cache\puppeteer` |
| torch | переменная `TORCH_HOME` | `D:\kg-build-cache\torch` |
| HuggingFace на хосте (скрипты замеров) | переменная `HF_HOME` | `D:\kg-hf-cache` |

Переменные пользователя — `setx` (владелец разрешил переносить всё). Общий `TEMP` Windows **не
трогать**: им пользуются все программы; нашим инструментам достаточно своих каталогов (`GOTMPDIR`).

Содержимое старых каталогов: модули Go — **перенести** (`robocopy /E`, потом удалить старое), чтобы
не качать 3 ГБ заново; остальное — удалить после переключения, соберётся на D: само. Старые
каталоги удалять **только после** зелёной сборки на новых путях. Удалять модули Go через
`go clean -modcache` можно, только указав старый путь явно (`GOMODCACHE=<старый> go clean -modcache`):
после переключения команда без него чистит уже новый каталог.

Перед переключением договориться, что второй агент в этот момент ничего не собирает: переезд кэша
под идущей сборкой её сломает.

## C. Сессии Devin CLI

`%APPDATA%\devin\cli\sessions.db` — 4 ГБ и растёт. Сначала выяснить, есть ли у Devin CLI
настройка каталога данных (переменная окружения или конфиг) — это надёжнее. Если нет — перенос
**при закрытом Devin CLI**: переместить каталог `%APPDATA%\devin` на `D:\agents\devin` и оставить на
старом месте связь (`mklink /J`). Себя Devin не перенесёт — он работает из этой базы. Devin готовит
точные команды и проверку, владелец выполняет их с закрытым CLI.

Отдельно — почему база 4 ГБ: если в ней копятся старые сессии, нет ли у CLI штатной очистки.

## D. VM Cowork (Claude Desktop)

`%APPDATA%\Claude\vm_bundles` — 9,4 ГБ: образ Linux-VM для режима Cowork (`rootfs.vhdx` 8,2 ГБ,
`sessiondata.vhdx`, ядро). Сессии Claude Code в этом проекте его не используют — они работают
прямо в Windows.

**Почему «постоянно скачивается».** По файлам каталога: приложение фоном качает новую версию образа
в `vm_bundles\warm\<хеш>` и при выходе подменяет ею рабочую — рядом появляются метки
`.cowork-adopted`, `.rootfs.vhdx.origin` с тем же хешем. Так бывает с каждым обновлением приложения,
отсюда 8+ ГБ повторно. Это вывод по именам и датам файлов, документации у меня нет.

Настройки места хранения у приложения нет — в `config.json` и `claude_desktop_config.json` её не
нашлось. Значит, путь один: **при закрытом Claude Desktop** перенести `vm_bundles` на
`D:\Claude\vm_bundles` и оставить связь `mklink /J`. Devin готовит команды и проверку; владелец
выполняет их, закрыв приложение: Claude Code живёт внутри этого приложения и перенести его под
собой не может. Проверка после запуска приложения — связь цела и не заменена обычным каталогом,
режим Cowork открывается. Если при следующем обновлении приложение пересоздаст каталог на C: —
записать, что junction приложение не переживает, и спросить владельца, нужен ли ему Cowork вообще.

## E. Дистрибутив WSL Ubuntu

3,6 ГБ на C:, дистрибутив по умолчанию, владелец не знает, что в нём. Порядок:

1. **Выяснить** и доложить: что внутри (`wsl -d Ubuntu -- du -xh --max-depth=2 / 2>/dev/null | sort -h | tail -20`),
   когда им пользовались, включена ли для него интеграция Docker Desktop.
2. Решение владельца по докладу:
   - **нужен** — перенести штатно: `wsl --terminate Ubuntu`, затем
     `wsl --manage Ubuntu --move D:\WSL\Ubuntu` (эта версия WSL, 2.7.12, умеет);
   - **не нужен** — сначала сохранить на D: (`wsl --export Ubuntu D:\WSL\backup\ubuntu.tar`), потом
     `wsl --unregister Ubuntu`. Без экспорта не удалять.

## F. Чтобы не вернулось

Скрипт `scripts/devops/check-disk-layout.ps1`:

- печатает размер каждого каталога из таблицы «Что лежит на C:»;
- **падает**, если хоть один настроенный путь ведёт на C:: `go env GOCACHE GOMODCACHE GOTMPDIR`,
  `npm config get cache`, `pip cache dir`, переменные из раздела B, `HF_CACHE_DIR` из `.env`;
- шаг «Диски» в `BOOTSTRAP.md` — настроить и прогнать этот скрипт на новой машине.

В `check-all` его **не** включать: на раннере GitHub своя раскладка дисков.

## Критерии приёмки

1. **A:** пересборка NLP-образа без скачивания модели — лог сборки без `snapshot_download`; размер
   образа до и после; стенд поднимается с `HF_CACHE_DIR=D:/kg-hf-cache`; с пустым кэшем и
   `HF_HUB_OFFLINE=1` — понятная ошибка, а не зависший healthcheck. Мутация: вернуть запекание — в
   логе сборки снова скачивание.
2. **B:** все пути из раздела B показывают D:; после переключения зелёные `go test ./...` бэкенда и
   юнит-тесты фронтенда; старые каталоги на C: удалены; размеры до и после в находках.
3. **C, D, E:** команды для владельца лежат в файле находок; после их выполнения — проверка, что
   связи целы и приложения работают; решение по Ubuntu — записано.
4. **F:** `check-disk-layout.ps1` зелёный на этой машине; мутация — вернуть `GOCACHE` на C: →
   скрипт красный.
5. **Итог в находках:** свободное место на C: до и после.
6. Personal-стек не поднимать; его тома и бэкапы не трогать.
