# AUTHOR-2. Хук авторства активен в каждом клоне без ручного шага

Постановка: Claude Code, 2026-09-21. Исполнитель: Devin. Следствие приёмки AUTHOR-1
([разбор](AUTHOR-1-review-findings.md), условие).

**Решение владельца (2026-09-21, AUTHOR-2):** хук авторства «должен быть везде, по идее,
активен». Активация — не ручной шаг владельца (`npm run prepare`), а свойство обвязки:
клон, в котором хук молчит, должен об этом сказать сам.

## Что не так сейчас

`.husky/pre-push` из AUTHOR-1 запускает `check-commit-authorship.mjs` до того, как коммиты
уходят на remote. Но git запускает хуки из `core.hooksPath`, а её выставляет только
`npm run prepare` (husky пишет `core.hooksPath=.husky/_`). Измерено 2026-09-21:

| Клон | `core.hooksPath` | Что реально запускается на `git push` |
|---|---|---|
| `D:\knowledge-graph` (владелец, `main`) | не задан | `.git/hooks/pre-push` — обёртка git-lfs (LFS-файлов в репозитории ноль) |
| `D:\knowledge-graph-ai-agents` (Devin) | не задан | то же: worktree делит `.git/hooks` с главным клоном |
| `D:\knowledge-graph-review` (Claude Code) | не задан | то же |

Итог: сторож, принятый как «pre-push», ни разу не выполнялся ни на одной машине.
Два из четырёх нарушений авторства, найденных на ревью AUTHOR-1, были коммитами владельца
из первого клона — как раз того, где хук молчит.

## Что сделать

1. **Второй сигнал в стороже чистого дерева.** `scripts/testing/check-agent-session-tree.mjs`
   запускается в начале каждой сессии агента (`/kg-work`, `.devin/skills/kg-work`). Добавить
   проверку: `git config --get core.hooksPath` пуст или указывает не на `.husky/_`, либо
   `.husky/_/pre-push` отсутствует → выход 1 с текстом «хуки не активированы: `npm run prepare`».
   Сессия не начинается, пока хук молчит — так же, как не начинается на грязном дереве.
2. **Фаза `check-all`.** Та же проверка как отдельная фаза раннера (`hooks-active`), чтобы
   зелёный `check-all` означал и «хуки стоят». В CI фаза пропускается с причиной: на раннере
   GitHub хуки не нужны, там авторство ловит `check-commit-authorship.mjs` напрямую.
3. **Активировать в трёх клонах** — `npm run prepare` в корне каждого worktree (husky создаёт
   `.husky/_` в каждом дереве отдельно, каталог в `.gitignore`). Клон владельца на `main`:
   там `.husky/pre-push` появится только после слияния `ai-agents`; до того сторож п. 1 будет
   на `main` молчать по конструкции — записать это в `COMMANDS.md` рядом с `npm run prepare`.
4. **Побочный эффект — назвать.** С `core.hooksPath=.husky/_` git перестаёт запускать
   `.git/hooks/*` (обёртки git-lfs, оставшиеся от старой настройки); LFS в репозитории не
   используется (`git lfs ls-files` пуст), потеря нулевая. `.husky/pre-commit` (`npx lint-staged`)
   при этом тоже оживает: для коммитов, трогающих только `docs/`, lint-staged ничего не
   делает, для `frontend/**` и `backend/**` — прогоняет линтеры. Это ожидаемое поведение,
   не регрессия; если оно мешает docs-only коммитам агентов, обсуждать отдельно, а не
   выключать хук.

## Критерии приёмки

1. В клоне с пустым `core.hooksPath` `check-agent-session-tree.mjs` выходит с кодом 1 и
   называет команду активации; после `npm run prepare` — код 0. Оба состояния показаны
   выводом, не описанием.
2. Мутация: временно `git config core.hooksPath .git/hooks` → сторож красный. Мутация:
   удалить `.husky/_/pre-push` при выставленной `hooksPath` → сторож красный.
3. `git push` из активированного клона с коммитом, у которого трейлер агента, а автор —
   человек, отклоняется хуком (`pre-push` красный) — это первый раз, когда хук AUTHOR-1
   виден красным; приложить вывод.
4. `check-all` показывает фазу `hooks-active` PASS локально и SKIP с причиной в CI.
5. `COMMANDS.md` и `docs/AI_AGENT_PROTOCOL.md` (раздел про pre-push) говорят, где хук активен,
   а где нет и почему.

## Границы

- `core.hooksPath` — общая настройка репозитория (`.git/config`), worktree её наследуют;
  `.husky/_` — на каждый worktree свой. Оба факта проверяются, а не предполагаются.
- Сторож не выставляет `hooksPath` сам: агент не меняет свои ограничения. Он только отказывает.
