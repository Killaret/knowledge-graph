## Как проверял

Не по отчёту. Прогнал обе оболочки целиком и проверил четырьмя мутациями, что прогонщик способен покраснеть.

Прогнал `check-all.ps1 -Quick` и `check-all.sh --quick`. Пятнадцать фаз, одинаковые имена, одинаковый порядок — общий `core-checks.tsv` держит это конструктивно, а не по совпадению. Шелл-версия работает на Windows под Git Bash без правок.

## Что принято без замечаний

- Переиспользование `phase-tracking` вместо второго механизма отчётности — как и просила постановка.
- `TEST CYCLE COMPLETE WITH SKIPS` как отдельное состояние: раньше пропуск был неотличим от полного успеха.
- Регрессионный тест `test-a3-exit-codes.ps1` дополнен проверкой сохранности причины пропуска и по-прежнему зелёный.
- `cover.out` убирается за собой; дрейф сгенерированного конфига остаётся в дереве и докладывается как отказ, а не откатывается молча.
- Документация (`COMMANDS.md`, `docs/TESTING.md`, `.windsurfrules`) описывает поведение честно, включая `COMPLETE WITH SKIPS`.

## Находки

### 1. Порог покрытия невидим для проверки соответствия

Самая существенная. `backend-coverage` — единственная фаза, чью логику прогонщик **переписывает**, а не исполняет: порог живёт в манифесте как `@coverage:64.8`, а в CI — тремя числами внутри тела шага.

Проверка соответствия сравнивает только `signature` (`go tool cover -func=cover.out`), в которой числа нет, и пропускает `command`, начинающийся с `@`. Мутация: поднял порог в `_core-checks.yml` с `64.8` до `80`, не трогая имя шага и манифест.

```
Workflow sync OK: 14 local phases match 14 CI steps.
EXIT=0
```

То есть CI требует 80 %, локальный прогон продолжает пускать при 64,8 %, и машина об этом молчит. От расхождения защищает только то, что в имени шага стоит `(min 64.8%)` — но это дисциплина автора правки, а не проверка. Ровно та болезнь, ради которой задача и ставилась.

Лечится дёшево: для записей вида `@coverage:N` дополнительно требовать, чтобы `N` встречалось в теле шага.

### 2. Дрейф команд ловится только в одну сторону

`commandDrift` проверяет, что `signature` — подстрока тела шага. Значит **сокращение** команды в CI ловится, а **дополнение** — нет. Мутация:

```
CI:        run: npm run lint -- --max-warnings=0
локально:  npm run lint
результат: Workflow sync OK  (EXIT=0)
```

Локальный прогон тихо выполняет более слабую команду, чем CI. Разумное направление — сравнивать нормализованную команду на равенство, а не на вхождение, оставив явные исключения там, где полное равенство недостижимо.

### 3. Пропуски дают нулевой код выхода

В тексте пропуск громкий, в коде возврата — нет: прогон с отсутствующим `golangci-lint` завершился нулём. Для человека, читающего сводку, всё честно; для любой обвязки, которая смотрит только на код (git-хук, другой скрипт), отсутствующий линтер выглядит зелёным — то самое, чего задача велела избегать.

Менять поведение по умолчанию не предлагаю: постановка просила громкости в сводке, и она есть. Достаточно необязательного флага строгого режима.

### 4. `npm run lint` правит исходники во время «проверки»

`frontend/package.json:lint` — это `eslint --cache --fix .`. Проверил пробой: файл с `let value = 41`, который нигде не переприсваивается, после прогона стал `const value = 41`. То есть команда, которую запускают **перед** коммитом, молча меняет то, что собираются коммитить.

Причина не в CI-3 — скрипт такой давно, и в CI на одноразовом checkout это безвредно. Но локальный прогонщик делает это ежедневной практикой, поэтому стоит либо развести `lint` и `lint:fix`, либо хотя бы предупредить в `docs/TESTING.md`.

### 5. `format:check` падает на артефактах, которых в CI не бывает

Отдельно подтверждаю правоту исполнителя: единственный отказ в его прогоне вызвали семь файлов `frontend/screenshots/visual/*.argos.json` из моей параллельной сессии. Они мои, я их удалил, после чего фаза стала зелёной.

Но причина шире одного случая: каталог перечислен в `.gitignore:187` и **не** перечислен в `frontend/.prettierignore`, поэтому Prettier его читает. Любой, кто прогонит визуальные тесты, а затем `check-all`, получит красную фазу форматирования, которой в CI быть не может — там checkout чистый. Ложный красный подрывает доверие к прогонщику так же, как ложный зелёный. Лечится строкой `screenshots/` в `frontend/.prettierignore`.

## Итог

Задача решена по существу: одна команда, честные пропуски с причинами, машинная проверка соответствия и доказанная способность краснеть. Находки 1 и 2 сужают зону, которую проверка соответствия реально видит, — их стоит закрыть следующим заходом; 3, 4 и 5 мелкие.

### Находка 1 — порог покрытия

Для записей `@coverage:N` число теперь требуется в теле `run:`-шага. Повторил свою мутацию: 64.8 → 80.

```
Command drift: backend-checks/Check backend coverage threshold (min 64.8%):
coverage threshold 64.8 not found in the CI step   EXIT=1
```

Раньше на этой же мутации было `Workflow sync OK`.

**Добавил свою третью мутацию, которой исполнитель не заявлял.** Оставил в echo-строке текст `required >= 64.8%`, а сравнение поднял до 90 — то есть спрятал старое число там, где наивный поиск подстроки его бы нашёл. Проверка всё равно упала: регэксп исключает совпадения, за которыми идёт `%` или цифра. Ловушка предусмотрена.

### Находка 2 — дрейф команд

Однострочные `run:` сравниваются с сигнатурой на равенство, а не на вхождение.

```
Command drift: frontend-checks/Run ESLint: CI runs 'npm run lint -- --max-warnings=0',
signature is 'npm run lint'   EXIT=1
```

Многострочные `run: |` и шаги через `uses:` из сравнения исключены — разумно, их к однострочной сигнатуре не свести; для них остаётся прежняя проверка вхождения.

- **Пропуски и код выхода.** Флаг `-Strict` / `--strict`. Проверил, спрятав `golangci-lint` из `PATH`: `Strict mode: 3 skipped phase(s) treated as failure`, `EXIT=1`. По умолчанию поведение не менялось — как я и просил.
