# REG-2. Пакетная близость: SQL не выполняется ни одним тестом

Постановка для Devin. Ставит Claude Code, реализует Devin, проверяет Claude Code.

**Исправление моей же недооценки.** В ревью REG-1 я назвал это «мелочью вне объёма».
Проверил по просьбе владельца — это не мелочь.

## Находка

`EmbeddingRepository.FindSimilarNotesBatch` (`embedding_repo.go:78`) используется в двух
местах, и одно из них на горячем пути:

- `application/graph/embedding_loader.go:79` — **загрузка графа**;
- `application/recommendation/gamma_link_generator.go:63` — генератор гамма-связей.

Тесты, упоминающие пакетную близость, есть в трёх файлах — `embedding_loader_test.go`,
`gamma_link_generator_test.go`, `handler_unit_test.go`. **Все три мокают репозиторий**,
ни один не имеет тега `integration`. То есть настоящий SQL не выполняется.

Интеграционный тест на репозиторий есть — `embedding_repo_test.go`, три сценария
(`UpsertAndFind`, `UpsertUpdate`, `ModelFiltering`). Слово `Batch` в нём встречается
**ноль раз**.

Итог: **запрос пакетной близости не выполняется ни одним тестом.** В нём тот же алиас
`as score` (`embedding_repo.go:90`), из-за которого в одиночном запросе оценка всегда
была нулём — это и чинила REG-1. Одиночный путь теперь защищён интеграционным тестом,
пакетный — нет, хотя именно он обслуживает построение графа.

## Что сделать

Интеграционный тест (`//go:build integration`) на `FindSimilarNotesBatch` против
настоящей pgvector-базы.

Проверять:

1. **Оценка ненулевая и в диапазоне [0,1]** — то есть алиас совпадает с полем структуры,
   а клампинг `GREATEST(0.0, LEAST(1.0, …))` работает.
2. **Возвращается по записи на каждый запрошенный id**, у которого есть соседи; на
   заметку без эмбеддинга — пусто, а не ошибка.
3. **Лимит соблюдается на каждый id**, а не на выдачу целиком. Это отдельный риск
   пакетного запроса: оконная функция легко режет глобально.
4. **Фильтрация по модели** работает так же, как в одиночном (`ModelFiltering` уже
   проверяет это для `FindSimilarNotes`).

### Как подключаться к базе

Не через testcontainers — это известная ловушка, ронявшая интеграционные фазы
(нужен доступ к реестру образов). Использовать `TEST_DATABASE_URL`, как это делает
`testutil.SetupTestVectorDB`. На локальном тест-стеке рабочая строка:

```
TEST_DATABASE_URL=postgres://kb_user:kb_password@127.0.0.1:15434/knowledge_test?sslmode=disable
```

### Доказать мутацией

1. Заменить `as score` на `as similarity` **в пакетном запросе** (`embedding_repo.go:90`,
   не в одиночном на строке 55) — новый тест краснеет.
2. Снять клампинг `GREATEST/LEAST` — тест краснеет на выходе за диапазон.
3. Применить лимит глобально вместо «на каждый id» — тест краснеет.

Мутации откатить, вывод приложить.

## Критерии приёмки

- Тест есть, помечен `//go:build integration`, проходит на живой pgvector-базе.
- Все три мутации ловятся; вывод приложен.
- Прогон не требует testcontainers: работает через `TEST_DATABASE_URL`.
- Документация обновлена по новой норме «Documenting New Functionality»: если
  поведение пакетной близости где-то описано — привести в соответствие; если нет —
  этого достаточно, сказать об этом явно в отчёте.

## Ограничения

- Не менять сам SQL, кроме как временно для мутаций.
- Одиночный путь и REG-1 не трогать.
