Статус: **в работе — 1.0 · Devin (этап A).** Постановка — Claude Code, 2026-09-27, по разговору с
владельцем. Черновик обсуждения 14.09 — в конце файла, как история.

## Этапность (решение Devin, 2026-10-01)

Задача целиком не влезает в один заход — делю на этапы, как NOTE-HEALTH-1 и SYNC-1:

- **A — поля и список (бэкенд):** миграция 038 (`due_at`, `remind_before_seconds`, `done_at` + индекс
  для ближайших), домен, GORM-модель, create/update API с валидацией (`remind_before` только при
  `due_at`), эндпоинт «Ближайшие дела» `GET /api/v1/comets` — просроченные, предстоящие, без даты.
  Поля хранятся у любой заметки (смена типа не теряет дату); форма и список работают только с
  `comet`. Обновление: ключ отсутствует — не трогаем, `null`/`""` — очищаем, значение — ставим.
- **B — форма и список (фронтенд):** поля даты/«напомнить за»/«сделано» в форме кометы; виджет
  «Ближайшие дела» (просроченные сверху красным, без даты отдельной группой); i18n.
- **C — напоминания:** asynq `comet:remind` на `due_at − remind_before`, перепланирование при переносе
  даты, отмена при «сделано»/удалении; доставка: in-app уведомления (нужна таблица `notifications` —
  отдельное решение в этом этапе) и письмо через `email.Sender`, факт — в лог.
- **D — `.ics`:** «Добавить в календарь» — файл с событием и `VALARM` по `remind_before`.
- **E — метафора и архив:** яркость/хвост по близости даты на 2D-графе; «прошла»/«сделано» — тусклая,
  предложение убрать в `debris` (предлагает, само не убирает).
- **F — живой прогон и доки:** комета с напоминанием за 2 минуты на тест-стенде, `.ics` в календаре,
  снимки в MANUAL_TEST_FEEDBACK; `CELESTIAL_BODY_SEMANTICS.md`, `openAPI.yaml`, CONFIGURATION EN/RU.

Критерии приёмки ниже распределяются по этапам: 1 и часть 5 — A/B; 2–3 — C; 4 — D; 5–6 — B/E; 7–8 — F.

## Разбор этапа A (Devin, 2026-10-01)

**Сделано.** Миграция 038: `due_at timestamptz`, `remind_before_seconds bigint`, `done_at
timestamptz` + частичный индекс `idx_notes_comet_upcoming (creator_id, due_at)` по живым
незакрытым датированным. Домен: поля на `Note`, `SetCometFields` (remind без due → ошибка),
`RemindAt` (done → nil). GORM-модель и маппинг в обе стороны; `FindComets` на конкретном
репозитории и outbox-декораторе — в `note.Repository` не включён (прецедент
`FindByIDIncludingDeleted`, потребитель объявляет узкий интерфейс).

**API.** `POST /notes` и `PUT /notes/:id` принимают `due_at`, `remind_before_seconds`, `done_at`.
Типы `nullableTime`/`nullableInt64` различают «ключа нет» (хранимое остаётся) и «null/""»
(очистка); отрицательный сдвиг отклоняется ещё в разборе. `GET /api/v1/notes/comets` →
`{overdue, upcoming, undated}`; просроченные первыми (due_at ASC), done и чужие исключены.
Валидация remind-без-due в домене, так что дырки между create и update нет.

**Тесты.** Домен: SetCometFields + RemindAt (нет даты/нет сдвига/сдвиг/done). Хендлер 7:
create с полями, remind без due → 400, отрицательный сдвиг → 400, merge (done_at при
хранимой дате), clear через null, remind без due → 400, группировка comets. Интеграционный
`TestFindComets_OrderingAndFilters`: порядок + исключение done/чужих/soft-deleted/не-comet.

**Мутации (красные).** «Снять done_at IS NULL» → закрытая комета просочилась (4 вместо 3).
«Абсентный ключ очищает» → merge-тест покраснел. Первая попытка мутации «безусловный вход в
мерж» была зелёной — семантика живёт внутри merge, не в guard; мутацию передвинул на
`req.value` без `present`.

**Прогоны.** `go test -count=1 ./...` бэкенд зелёный (sqlmock-ожидание INSERT дополнено тремя
колонками), интеграция на testcontainers зелёная, `go vet` чисто, openAPI.yaml валиден и
дополнен (Note, Create/UpdateNoteRequest, `GET /notes/comets`), `API_EN.md` раздел 12,
`CELESTIAL_BODY_SEMANTICS.md` — комета переписана как дело.

**Не в этапе A:** напоминания-asynq, `.ics`, метафора графа, форма/виджет фронтенда — этапы
B–E по списку выше.

**Решение владельца (2026-09-27, COMET-1):** комета — дело, которое нужно записать и не забыть: визит к
врачу, сходить в кино, посмотреть фильм. Дата необязательна, напоминание — по желанию, повторов в 1.0
нет. Новый тип не нужен — это `comet`. На графе комета «приближается»: чем ближе дата, тем ярче она и
длиннее хвост.

## Что есть сейчас

- `comet` в семантике типов — «событие: временные, привязанные к дате заметки»
  (`docs/product/CELESTIAL_BODY_SEMANTICS.md:32`). Полей даты нет ни в домене, ни в миграциях, ни во
  фронтенде.
- Отправка почты есть (`backend/internal/infrastructure/email`: SMTP и вывод в консоль). SMTP в
  `config/backend.json` не настроен — письма идут в лог.
- Быстрая запись — `dust`; комета отличается тем, что это дело.

## Что сделать

1. **Поля кометы** — отдельные колонки или таблица, не `metadata`, с индексом для списка ближайших:
   - `due_at` — дата и, по желанию, время; необязательно; хранится в UTC, часовой пояс — из браузера;
   - `remind_before` — за сколько напомнить: нет, 15 минут, час, день или своё; только при заданной дате;
   - `done_at` — когда отмечено «сделано». Предложение Claude Code: у дел это естественно; владелец
     подтверждает при приёмке.
2. **Форма кометы:** дата и время — необязательные, «напомнить за», флажок «сделано». Комету без даты
   можно записать одним полем, как при быстрой записи.
3. **Напоминание:** отложенная задача asynq `comet:remind` на `due_at − remind_before`. Перенос даты
   перепланирует, «сделано» и удаление отменяют. Доставка: всплывающее уведомление, если приложение
   открыто, и список «Напоминания» с непрочитанными; письмо — если настроен SMTP. Факт отправки — в лог.
4. **«Добавить в календарь»:** у кометы с датой — файл `.ics` с событием и напоминанием по
   `remind_before`. Напоминает календарь телефона, даже когда приложение закрыто.
5. **Список «Ближайшие дела»:** кометы с датой по порядку, просроченные — сверху, красным; без даты —
   отдельной группой.
6. **После даты или «сделано»:** комета тускнеет с пометкой «прошла» или «сделано», приложение
   предлагает убрать её в архив (`debris`). Предлагает, само не убирает.
7. **Метафора на графе, 2D (3D — после 1.0, решение 82):** чем ближе дата, тем ярче комета и длиннее хвост; прошедшая или
   сделанная — тусклая, без хвоста; без даты — как сейчас.
8. **Цепочки дел:** кометы, связанные `dependency`, — это цепочка дел из LINK-TYPES-1. На будущее, не в
   1.0: предупреждать, если дело стоит в календаре раньше того, от которого зависит.

## Не в 1.0

Повторы, место, участники, синхронизация с внешними календарями, распознавание дат в тексте, Telegram.

## Критерии приёмки

1. Комета без даты создаётся и не получает напоминания — тест.
2. Напоминание уходит в `due_at − remind_before` — тест с фиксированными часами. Перенос даты
   перепланирует, «сделано» и удаление отменяют — тесты; мутация «без отмены» — красная.
3. Доставка: уведомление в приложении — тест компонента; письмо — через консольного отправителя.
4. `.ics`: файл разбирается, начало события — в UTC, напоминание (`VALARM`) — по `remind_before` —
   тест.
5. «Ближайшие дела»: порядок, просроченные сверху, группа без даты — тест.
6. Метафора: яркость и хвост зависят от близости даты — тест отрисовки; снимки «через месяц»,
   «завтра», «прошла» — в `docs/agents/MANUAL_TEST_FEEDBACK.md`.
7. Живьём на стенде: комета с напоминанием через 2 минуты — уведомление пришло; `.ics` открывается в
   календаре — свидетельство.
8. Документы: `CELESTIAL_BODY_SEMANTICS.md` (комета — дело), API в `openAPI.yaml`, SMTP для
   напоминаний — в `CONFIGURATION_EN.md` и `CONFIGURATION_RU.md`.

## Черновик обсуждения 2026-09-14

Исходное название: «COMET-1: Расширенные поля и функциональность для событийно-временных / напоминалочных заметок».


**2026-09-14 — обсуждение.** Владелец предложил: у нас есть тип, который по сути «напоминалка» (временная/событийная заметка), и для него нужен расширенный функционал записи и обработки данных, возможно — с настоящими напоминаниями.

### Зачем

В текущей таксономии:

- `comet` — «temporary / event-bound note» (sprints, meetings, releases);
- `satellite` — «utility» (checklists, templates, configs, snippets);
- `asteroid` — raw fragment/quote/TODO.

Но сейчас у `comet` (и других типов) нет полей даты, времени, повторения и механизма напоминаний. Пользователь не может сказать: «напомни мне об этой заметке в понедельник в 10:00» или «это встреча 15 сентября, напомнить за день».

### Вопрос, который надо решить с владельцем и Claude Code

Какой тип берём под «напоминалку»?

| Вариант | За | Против |
|---------|----|--------|
| `comet` | Уже «временная/событийная заметка»; семантически ближе всего к событию с датой. | Сейчас `comet` — это скорее «временная заметка» без строгой привязки к календарю; может размыть границу. |
| `satellite` | Чек-листы и шаблоны часто имеют дедлайны и recurring-напоминания. | `satellite` — это utility/орбитальный объект, а не событие. |
| Новый тип (`reminder`) | Чёткое разделение; можно специализировать UI. | Ещё один тип в таксономии; нужна миграция/селекторы. |

### Предварительный набор функциональности

1. **Поля заметки (для `comet`/выбранного типа)**:
   - `event_at` — дата/время события (RFC 3339).
   - `timezone` — IANA timezone (`Europe/Moscow` и т.д.).
   - `reminder_at` — когда напомнить.
   - `recurrence_rule` — iCal RRULE для повторений.
   - `duration` — продолжительность (ISO 8601 duration).
   - `location` — строка или координаты.
   - `attendees` — список email/имён (если встреча).
2. **Напоминания**:
   - asynq-задача `reminder:send`, откладываемая на `reminder_at`.
   - Метод доставки: in-app уведомление, email, push (опционально).
   - Лог факта отправки и снooze.
3. **UI**:
   - Date/time picker, timezone auto-detect, recurrence builder, location input.
   - В списке/графе — badge «через N часов» / «просрочено».
4. **Обработка/конвертация**:
   - `comet` с прошедшим `event_at` → предложить `debris` или ручной архив.
   - Авто-определение даты из текста заметки (NLP) — позже, после `NOTE-QUALITY-1`.

### Технические вопросы

1. Где хранить поля — отдельные колонки в `notes` или JSON `metadata`? (Миграции, индексы, SQL-запросы.)
2. Как интегрировать напоминания с asynq/worker? Worker должен обрабатывать отложенные задачи и уметь переносить `reminder_at` при редактировании.
3. Нужна ли синхронизация с внешними календарями (iCal/CalDAV/Google Calendar)?
4. Безопасность: email-адреса `attendees` не должут литься в лог/ответы, если пользователь публично делится заметкой.
5. Timezone: брать из браузера/профиля пользователя или из системы?
