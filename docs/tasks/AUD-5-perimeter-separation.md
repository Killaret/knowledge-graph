# AUD-5. Разделить публичный периметр и внутренний канал graph-service

Постановка для Devin. Источник: [`../EXTERNAL_AUDIT_2026-09.md`](../EXTERNAL_AUDIT_2026-09.md), находки S-3 и S-7. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code на живом тест-стеке.

**Очерёдность:** последняя незакрытая находка из критической четвёрки аудита. С треком P11 не пересекается.

**Это изменение модели доверия, а не правка.** Трогает три compose-файла, `nginx.conf` и auth graph-service. Читать раздел «Что выяснено» целиком до начала.

## Проблема

`nginx.conf:52` передаёт в graph-service заголовок `X-Internal-Auth` **в том виде, в каком его прислал клиент**:

```nginx
proxy_set_header X-Internal-Auth $http_x_internal_auth;
```

`nginx.conf:36` и `:57` дополнительно разрешают этот заголовок браузеру через CORS — то есть браузеру прямо позволено его слать.

На той стороне `services/graph-service/internal/api/auth.go:109-128`: при совпадении внутреннего токена сервис доверяет заголовку `X-User-Id` и отдаёт граф названного пользователя.

Итог: **публичный слушатель и внутренний канал не разделены**. Кто угодно, кому известен внутренний токен, представляется любым пользователем через обычный браузерный запрос. Прочие клиентские заголовки nginx тоже не вычищает, поэтому `X-User-Id` доходит без препятствий.

Сейчас смягчено тем, что `GRAPH_SERVICE_INTERNAL_TOKEN` по умолчанию пуст, а пустой токен отбрасывается (`auth.go:110-112`). То есть защита держится на том, что функцию не включили.

Вторая половина (S-7): у nginx нет ни TLS, ни `client_max_body_size`, ни ограничения скорости на входе, ни одного заголовка безопасности — `Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security` отсутствуют.

## Что выяснено в коде

**1. Внутренний канал нужен SSR, а не браузеру.** Заголовок ставит серверная часть SvelteKit: `docker-compose*.yml` передают фронтенду `GRAPH_SERVICE_INTERNAL_TOKEN`, а `hooks.server.ts` ходит в graph-service напрямую по `GRAPH_SERVICE_URL`, минуя nginx. Значит браузеру этот заголовок не нужен **никогда**, и его пропуск через публичный слушатель — не функциональность, а недосмотр.

**2. Браузерный путь самодостаточен.** Клиентские запросы идут на `/graph-service/` с обычным `Authorization: Bearer`, и `auth.go:57-64` его обрабатывает. Отрезание `X-Internal-Auth` на публичном входе браузерный сценарий не ломает.

**3. `X-User-Id` в gRPC-пути тоже принимается** (`auth.go:161-172`), но gRPC-порт наружу через nginx не проброшен. Поправить стоит для симметрии, срочности нет.

**4. Комментарий в nginx уже признаёт проблему**, но не решает её: «x-internal-auth is provided by the trusted SvelteKit proxy when running SSR» — при том что SSR ходит мимо nginx, а через nginx идёт как раз браузер.

## Что сделать

### 1. Отрезать внутренние заголовки на публичном входе

`nginx.conf`, локация `/graph-service/`:

- перестать пробрасывать клиентский `X-Internal-Auth` — заменить `$http_x_internal_auth` на пустую строку, чтобы заголовок гарантированно не доходил;
- так же обнулить `X-User-Id`;
- убрать `X-Internal-Auth` из `Access-Control-Allow-Headers` в обеих директивах CORS: браузеру этот заголовок не нужен.

То же самое в `nginx.personal.conf`, если там есть аналогичная локация.

### 2. Сделать доверие к `X-User-Id` явным на стороне сервиса

`services/graph-service/internal/api/auth.go`. Сейчас `X-User-Id` принимается всегда, если внутренний токен совпал. Это должно быть осознанной настройкой, а не поведением по умолчанию.

Ввести признак — например `GRAPH_SERVICE_TRUST_USER_HEADER`, по умолчанию **выключен**. При выключенном признаке `X-User-Id` игнорируется, и внутренний вызов без собственного `user_id` в подписанном токене доступа к чужим данным не даёт.

Симметрично поправить gRPC-ветку.

### 3. Базовая гигиена nginx (S-7)

В обоих серверах:

- `client_max_body_size` — осмысленный предел вместо умолчания;
- заголовки `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`;
- `server_tokens off`.

`Content-Security-Policy` и TLS **в эту задачу не входят**: CSP требует отдельной работы по инвентаризации источников, TLS — решения о сертификатах. Завести обе отдельными строками на доске.

Белый список CORS (`nginx.conf:11-15`) покрывает только порт 18081, тогда как фронт живёт ещё на 5173 и 18084 — привести в соответствие.

## Ограничения

- Не менять способ, которым SSR ходит в graph-service: он идёт мимо nginx и работает.
- Не трогать разбор `Authorization: Bearer` — он корректен и проверен в аудите.
- Не вводить TLS и CSP в этой задаче.
- Не трогать `.claude/`, `docs/tasks/AUD-*`, `docs/EXTERNAL_AUDIT_2026-09.md`.
- Personal-стек не поднимать.

## Критерии приёмки

1. `go test ./...` в `services/graph-service` и в `backend` зелёные; `npm run test:unit` без новых замечаний.
2. **На живом тест-стеке запрос через nginx с подделанными заголовками не даёт чужих данных.** Главный критерий: `curl` на `/graph-service/api/v1/graph/...` с `X-Internal-Auth: <токен>` и `X-User-Id: <чужой uuid>` обязан получить отказ или публичный ответ, но не граф названного пользователя.
3. Браузерный сценарий не сломан: страница графа под авторизованной сессией по-прежнему показывает приватный граф (100 узлов на сидированных данных против 20 публичных).
4. SSR-путь не сломан: серверный рендер по-прежнему получает данные.
5. Заголовки безопасности присутствуют в ответе nginx, `server_tokens` выключен.
6. Тест на стороне graph-service: при выключенном `GRAPH_SERVICE_TRUST_USER_HEADER` заголовок `X-User-Id` игнорируется. Проверить **мутацией** — вернуть прежнее поведение и убедиться, что тест краснеет.

## Что приложить к результату

Вывод `curl -D -` по критерию 2 — до и после правки, с одинаковыми заголовками. До: сервис отдаёт граф указанного пользователя. После: не отдаёт. Это единственное доказательство, что периметр действительно разделён; конфигурация, которая «выглядит правильно», здесь не считается — ровно этот случай мы уже проходили с `depguard`.

### Критерий 2 — главный

Один и тот же поддельный запрос по двум путям:

| Путь | Ответ |
|---|---|
| Напрямую в сервис `:19091`, минуя nginx | `200`, **100 узлов** — внутренний канал работает |
| Через публичный nginx `:18086` | **`401 Unauthorized`** — подделка не проходит |
| Публичный эндпоинт через тот же nginx | `20 узлов` — обычный сценарий не сломан |

Заголовки в обоих случаях одинаковые: `X-Internal-Auth: test-internal-token` и `X-User-Id: 00000000-…-000000000000`. Разница только в том, проходит ли запрос через публичный слушатель. Это и есть разделение периметра.

### Мутация по критерию 6

Заменил `if cfg.TrustUserHeader {` на `if true {` в HTTP-ветке `auth.go` — пакет `internal/api` упал. Защита действительно покрыта тестом, а не только описана. Файл восстановлен.

### Два решения исполнителя, которые стоит отметить

**Защита двухслойная, и это лучше, чем просил я.** nginx обнуляет `X-Internal-Auth` и `X-User-Id` на публичной локации, а сервис независимо гейтит доверие флагом `GRAPH_SERVICE_TRUST_USER_HEADER` со значением по умолчанию `false`. Отказ любого одного слоя не открывает дыру.

**`GRAPH_SERVICE_TRUST_USER_HEADER: "true"` в `docker-compose.test.yml`** — сознательный выбор, а не недосмотр: внутренний путь SSR в тестовом контуре этим заголовком пользуется. Публичный вход при этом всё равно закрыт nginx, что прямая проверка и подтвердила. Замечаний нет, но это стоит помнить: **на тест-стенде серверный слой защиты выключен намеренно**, и проверять разделение нужно именно через nginx, как я и делал.
