# SPEC-AUDIT-1. Постановки против кода: всё ли заказанное есть в коде

Статус: **бэклог — Devin, в составе 1.0.** Постановка — Claude Code, 2026-09-26, по просьбе владельца.

**Решение владельца (2026-09-26, SPEC-AUDIT-1):** Devin перепроверяет код всего приложения по всем
постановкам — «прям точно всего», включая принятые задачи. Дорого — владелец идёт на это
сознательно.

## Почему

- **Принятое теряется молча.** Постепенная загрузка графа была сделана (`d6b0658`, 2026-04-15) и
  удалена при чистке (`86e66d9`, 2026-05-20) без решения. Четыре месяца этого никто не замечал
  (UI-LOAD-1).
- **Часть замысла не становится задачами.** SSE из ADR 014 так и не стал задачей, а путь импорта
  обошёлся без событий (SYNC-1).
- **Ревью проверяет задачу один раз, в момент приёмки.** Регрессии после поздних правок ничто не
  ловит.

## Объём

- **Все постановки и рабочие заметки в `docs/tasks/`** — 105 файлов на 2026-09-26, включая принятые и
  отменённые.
- **Незакрытые хвосты в разборах ревью** (`*-review-findings.md`, 62 файла): пункты «мелочь», «хвост»,
  «в бэклог». Разобраны ли они или потерялись.

Граница с DOC-AUDIT-2: та задача сверяет с кодом описательные документы (архитектура, продукт,
эксплуатация, API), эта — постановки, то есть что было заказано. Постановки из этапа D DOC-AUDIT-2
переходят сюда.

**Предусловие — выполнено.** История git должна читаться целиком, иначе `git log -S` по всей
истории падает и «потеряно» не доказать. 2026-09-26 в хранилище нашлись два испорченных объекта —
старые версии двух отчётов от апреля. Владелец заменил их целыми копиями с GitHub, после этого
`git fsck --full` проходит без ошибок.

## Метод — на каждую постановку

1. **Выписать требования и критерии приёмки**, пронумеровать.
2. **Для каждого найти:** место в коде (файл:строка), тест, который его держит (имя), и результат
   прогона этого теста. Поведение проверяется исполнением, а не чтением — норма «Verifying a
   Finding».
3. **Вынести вердикт:**

   | Вердикт | Что значит | Что делать |
   |---|---|---|
   | есть, держится тестом | требование выполнено, тест упадёт при поломке | ничего |
   | есть, без теста | работает, но ничто не мешает потерять | в список на тесты, первыми — видимое пользователю |
   | сделано иначе | поведение отличается от постановки | есть решение владельца — ссылка; нет — владельцу |
   | **потеряно** | было и исчезло | коммит, где появилось, и коммит, где исчезло (`git log -S`); было ли решение. Владельцу: вернуть в 1.0, после 1.0 или вычеркнуть |
   | **не сделано** | не было никогда | владельцу: сделать в 1.0, после 1.0 или вычеркнуть |

4. **Молча ничего не чинить и не удалять.** Эта задача — реестр и решения владельца. Починка — отдельными
   задачами после его решения.

## Этапы — каждый сдаётся на ревью отдельно

0. **Скелет реестра:** все 105 постановок и все файлы разборов с хвостами распределены по этапам
   A–E. Ревьюер сверяет полноту с `docs/tasks/README.md`.
1. **A. Граф и интерфейс:** 2D, 3D, туман, панели, связи в интерфейсе, загрузка и синхронизация (UI,
   UX, VIS, FE, E2E, SYNC, визуальная часть LINKS).
2. **B. Сбор и заметки:** импорт, букмарклет, пакетное создание, типы, напоминания (IMP, URL,
   BATCH, NOTE, COMET, API).
3. **C. NLP, связи, рекомендации** (NLP, MODEL, CHUNK, LINKS, W, RECO, P11).
4. **D. Безопасность, данные, эксплуатация** (AUD, SEC, PUB, BACKUP, DISK, DEPLOY, DB, GORM, MONGO,
   CLEAN, LOG, CSP, CI, COVERAGE, REG, DEPENDABOT).
5. **E. Процесс и инструменты:** сторожа доски, индекса, авторства, документов (BOARD, TASKS,
   AUTHOR, DOC, DECISIONS, WORKTREE и прочее).

## Результат

- Реестр `docs/tasks/SPEC-AUDIT-1-register.md`, раздел на постановку. Колонки: требование, вердикт,
  доказательство (файл:строка, тест и его результат, коммит), действие.
- Сводка по этапу: сколько «есть с тестом», «есть без теста», «иначе», «потеряно», «не сделано».
- Список владельцу: все «потеряно» и «не сделано» с историей. Решения по ним принимаются вместе с
  составом 1.0 ([`RELEASE-1-scope-1.0.md`](RELEASE-1-scope-1.0.md)).

## Критерии приёмки — на каждый этап

1. Каждая постановка этапа — в реестре, у каждого её требования есть вердикт.
2. Доказательство повторяемо: ревьюер воспроизводит его по записи.
3. Ревьюер проверяет выборку из 10 случайных вердиктов «есть, держится тестом»: ломает код и
   убеждается, что названный тест краснеет. Хотя бы один промах возвращает этап.
4. У каждого «потеряно» указаны коммит появления и коммит исчезновения.
5. В коде продукта нет изменений; в документах — только пометки «не реализовано — SPEC-AUDIT-1» там,
   где постановка утверждает сделанное.
6. Сторожа зелёные.
