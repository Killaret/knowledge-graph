# MODEL-2. Миграция на `intfloat/multilingual-e5-base` (черновик)

Создано по итогам замера MODEL-1 и обсуждения с владельцем 2026-09-19.
Статус: **черновик, ждёт обсуждения с Claude Code** — владелец склоняется
к e5-base («качество важнее скорости»), но формальное решение принимается
после консультации с Claude Code, а не только владельцем.

## Почему e5-base приемлем: уточнение после замера

Первичная оценка «24× медленнее — непрактично» была пересмотрена после проверки
кода: **NLP-сервис работает только в асинхронном контуре**. Поиск
(`/api/notes/search`) — полнотекстовый по Postgres, NLP-клиент вызывается
только воркером (`queue/worker.go`, `linkweight/service.go`). Медленная модель
удорожает фоновое обогащение, а не UX. Импорт редкий, добавление асинхронно,
пересчёт ночной — латентность терпима.

## Что даёт замер (MODEL-1-review-findings.md)

| | current@128 | e5-base |
|---|---|---|
| embed p50 / p95 | 95 / 158 мс | 2320 / 3427 мс |
| корпус 113 заметок | 11 с | 235 с |
| RSS контейнера | 1091 МБ | 1768 МБ |
| размерность | 384 | **768** |
| окно | 128 | 512 |
| качество выдачи | базовая | лучшая визуально |

## Обязательный состав работ

1. **Схема**: колонка pgvector `vector(384)` → `vector(768)` — миграция
   + полный пересчёт эмбеддингов (`cmd/embed-recompute` уже существует).
2. **Префиксы E5**: `passage: ` для документов при индексации, `query: ` для
   запросов — без них e5 деградирует; точки — оба места кодирования в nlp-service.
3. **Чанкование**: окно 512 < медиана корпуса (1310 символов ≈ 300+ токенов,
   макс 5329). Encode по кускам + mean-pool; иначе e5 видит только начало —
   то же ограничение, что у current@128, только мягче. Объединено с NLP-4:
   чанк-векторы персистентны (`note_chunk_embeddings: note_id, chunk_idx,
   vector(768), model_version`) — дают парное сходство чанков для формулы
   весов и выборочный пересчёт; текст и происхождение чанков (heading_path,
   char_span) — в Mongo `nlp_artifacts`.
4. **Сборка**: `NLP_MODEL_NAME` уже параметр Dockerfile (build-arg) —
   образ собирается с e5-base без правки кода; имя модели в `nlp_utils.py`/config.
5. **Память/запуск**: RSS ~1.8 ГБ на воркер; пересмотреть `start_period`
   healthcheck (модель ~1.1 ГБ грузится дольше); офлайн-старт с кэшированным
   snapshot обязателен как в P11-2.
6. **Масштабирование**: один воркер ≈ 0.4 заметки/с ≈ ~37K/сутки; 2 воркера
   ≈ 69K/сутки против ~10K/сутки пиковой потребности 100 пользователей
   (оценка владельца: до 100 заметок/сутки на юзера) — запас ×7. Рычаг роста —
   `uvicorn --workers N` (+~2 ГБ RAM каждый) или реплики контейнера
   (stateless за asynq-очередью). Для ~100 пользователей: ВМ YC **4 vCPU /
   8 ГБ ≈ 6–8К₽/мес** — NLP ×2 ≈ 3.6 ГБ + Postgres ≈ 1 ГБ + Mongo/Redis ≈ 0.7 ГБ
   + backend/фронт ≈ 0.4 ГБ + ОС/Docker ≈ 1 ГБ.
7. **Производные хранилища** (по решению NLP-4): Mongo `nlp_artifacts`
   (логическая форма, чанки с происхождением, метрики, история версий с флагом
   `nlp.history.enabled`), таблица `note_chunk_embeddings`, каскадное удаление
   при delete заметки, инвалидация по `source_hash`, `pipeline_version`/
   `model_version` раздельно.

  медленнее current), current@512 (отвергнут: дороже без прироста),
  rubert-tiny2 (миграция + слабый английский).

## Критерии приёмки (набросок)

1. Все заметки пересчитаны e5-base, `embedding` = 768-dim, `extractor`-метка обновлена.
2. Поиск/похожие заметки на 10 фиксированных запросах MODEL-1 — выдача приложена,
   владелец подтверждает визуально.
3. Офлайн-старт `HF_HUB_OFFLINE=1` проходит; RSS ≤ ~2 ГБ/воркер.
4. `git diff` по `.env`/compose — только осознанные параметры модели.
5. Воркер прогоняет очередь без деградации таймаута клиента (10 с — граница NLP-2).
