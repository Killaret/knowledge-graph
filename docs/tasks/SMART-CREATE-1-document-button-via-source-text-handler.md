## Зачем

«＋» создаёт одну заметку из того, что человек напечатал. Длинный текст, статью по ссылке или
файл удобнее отдать обработчику документов: он сам разделит их на заметки и придумает названия
(ТЗ §1, §5, §10). Сейчас из интерфейса до него не добраться: в Go нет ни отправителя в его
очередь, ни читателя ответов, а в шапке нет кнопки.

## Решения владельца (2026-10-18, решение 106)

1. **Отдельная кнопка, «＋» не меняется.** Новая кнопка стоит в шапке **слева** от «＋»: плюс
   и три маленькие плитки — текст, ссылка, файл. Она читается как улучшенная версия «＋».
   Звёздочки нет.
2. **Без живого слушателя Java кнопка неактивна.** Она серая, с подсказкой. Запасного пути нет:
   обычную заметку человек создаёт через «＋».
3. **Готовность определяет слушатель очереди, а не процесс.** Если слушатель жив, но занят
   другим документом, задача всё равно уходит в очередь, и человек видит «В очереди».
4. **Контракт — по ТЗ, буквально.**
   - Задача — plain JSON по §3.
   - Ответ — plain JSON по §4.
   - Заметки создаются пакетом через `/import/batch` по §11.

   Код Java на `origin/java-source-text-handler` (`919d4cb`) с ТЗ расходится: в нём конверт
   asynq. Его приведут к ТЗ позже. Go под этот код **не подстраивается**.
5. **Тип частей — `unknown`** (ТЗ §11). Выбора типа в окне нет.
6. **Статус задачи — в кеше**, как у массового импорта: `TaskStatus` и
   `GET /import/:task_id/status`. Таблицу `import_tasks` из ТЗ §1 не заводим: ТЗ не определяет
   её схему.
7. **Доработка `raw_chunks`** (ТЗ §1) — позже, отдельной задачей.

## Как это работает

1. При показе шапки и затем раз в 15 с фронт спрашивает
   `GET /api/v1/import/document/availability`. Go отвечает `available: true`, если в Redis
   есть ключ слушателя `source-text-handler:alive`.
2. Человек выбирает плитку и отправляет. Фронт шлёт `POST /api/v1/import/document`.
3. Go проверяет ключ (нет → `503`), проверяет вход и кладёт задачу по ТЗ §3 в
   `import:document:pending`. В кеш он заводит `TaskStatus` со статусом `pending` и отвечает
   `202 {task_id}`.
4. Java забирает задачу, режет текст, создаёт заметки одним вызовом `/import/batch` с JWT из
   задачи и кладёт ответ по §4 в `import:responses:pending`. Это сторона Java, в эту задачу она
   не входит.
5. Worker Go читает ответ и обновляет `TaskStatus` по `correlation_id`.
6. Фронт опрашивает статус и показывает итог.

## Что сделать

### Бэкенд

Слои — по `kg-layers`: хендлер тонкий, решение «можно ли отправлять» и сборка задачи — в
`application`, Redis-очереди и ключ — в `infrastructure`.

**Адаптер Redis** (`backend/internal/infrastructure/…`, рядом с `queue/` или `cache/` — на
усмотрение Devin):

- `IsListenerAlive(ctx) bool` — `EXISTS source-text-handler:alive`;
- `PushTask(ctx, task)` — `RPUSH import:document:pending <json>`;
- `PopResult(ctx, timeout)` — `BLPOP import:responses:pending`.

**Сценарий** в `backend/internal/application/import/` (или в соседнем пакете — на усмотрение
Devin):

- **Задача — поля ТЗ §3 и только они:**

  | Поле | Значение |
  |---|---|
  | `event_id`, `correlation_id` | новые UUID |
  | `user_id` | из токена |
  | `jwt` | токен из заголовка `Authorization` |
  | `type` | `FILE`, `URL` или `TEXT` |
  | `content` | base64 для `FILE`, URL или текст для остальных |
  | `content_type` | только для `FILE`, по файлу |
  | `import_options` | значения из примера §3 |
  | `metadata` | `{"filename": …, "source": "web"}` |

- **Статус** — `TaskStatus` в кеше, `task_id = correlation_id`, статус `pending`.
  Дополнительно в статусе:
  - `user_id` владельца;
  - `notes: [{id, title}]` — Go заполняет их по `note_ids` из ответа, чтобы фронт не ходил
    за каждой заметкой;
  - `raw_chunks_count`;
  - `errors`.

**Маршруты** — в `backend/cmd/server/router.go`, рядом с остальными `/import/*`:

- `GET /import/document/availability` → `{"available": bool}`.
- `POST /import/document` под `writeLimiter`, `multipart/form-data`, поля `type`, `content`,
  `file`.
  - Нет ключа → `503`, код `source_text_handler_unavailable`, в очередь ничего не кладётся.
  - URL проходит политику `importer`: схема, хост, IP, `backend/internal/application/import/service.go`.
  - Текст не пустой.
  - Файл не больше **8 МБ**. ТЗ этот предел не задаёт, он следует из `client_max_body_size 10m`
    в `nginx.conf` и `nginx.personal.conf`.
  - Успех → `202 {"task_id"}`.

**Читатель ответов** — горутина в `backend/cmd/worker/main.go`. Она читает
`import:responses:pending` (формат ТЗ §4) и обновляет статус по `correlation_id`:

| Ответ Java | Статус |
|---|---|
| `COMPLETED` | `done` |
| `PARTIAL` | `done`, `raw_chunks_count = len(raw_chunks)` |
| `FAILED` | `failed`, `errors` из ответа |

- Ответ с неизвестным `correlation_id` пишется в лог без содержимого и отбрасывается.
- Нет ответа за **10 мин** → статус `failed`, `reason: "timeout"`. Это только сторона Go, ТЗ
  об этом молчит.

**Владелец статуса.** Сейчас `ImportBookmarksStatus` (`note_handler.go`) не проверяет, чья
задача: `userID` отбрасывается. В новый статус Go кладёт имена созданных заметок, поэтому для
задач этой задачи статус отдаётся **только владельцу**, чужому — `404`. Чинить проверку для
массового импорта — на усмотрение Devin, записать в notes.

**Следствие решения 6.** Статус живёт в кеше `cacheTTL` = 1 час, и вместе с ним через час
пропадают `raw_chunks`. Задача доработки (решение 7) начнётся с того, где их хранить. Здесь
Go их не сохраняет, сохраняется только число.

## Дополнение к ТЗ для Java-стороны

ТЗ не определяет, как Go узнаёт, что слушатель жив, а решение 3 требует именно этого. Сейчас
`/health/readiness` проверяет только связь с Redis. В коде `919d4cb` слушатель и `/health`
работают в разных потоках. Если `OutOfMemoryError` в Tika убьёт поток слушателя, процесс
продолжит работать и readiness будет отвечать 200.

Предлагаемый текст дополнения. Согласовать с Alximac, внести в ТЗ до реализации на стороне Java:

> Слушатель очереди пишет `SET source-text-handler:alive <ISO-время> EX 15` на каждом обороте
> цикла чтения и во время обработки документа — не реже раза в 5 секунд.

Ключ обновляется и во время разбора, поэтому занятый Java не выглядит мёртвым. Пока Java ключ
не пишет, кнопка неактивна. Это и есть безопасное состояние до приведения Java к ТЗ, отдельный
флаг в настройках не нужен.

## Критерии приёмки

Каждый пункт подтверждается тестом, который краснеет на мутации. Мутация и вывод — в notes.

1. **Нет ключа:**
   - `availability` → `false`;
   - `POST /import/document` → `503`, очередь пуста;
   - кнопка `aria-disabled`.

   Мутация «ключ не проверяется» → красный.
2. **Задача по ТЗ.** Сообщение в `import:document:pending` разбирается в ту же структуру, что
   пример §3:
   - набор полей и имена совпадают;
   - `snake_case`;
   - конверта нет.

   Фикстура — JSON из ТЗ, тест на miniredis.
3. **Читатель ответов:**
   - фикстуры §4 `COMPLETED`, `PARTIAL` и `FAILED` дают статусы из таблицы выше, `notes`
     заполнены названиями;
   - без ответа через срок ожидания — `failed/timeout`.
4. **Чужой статус** → `404`.
5. **Логи.** В них нет JWT и содержимого документа — проверка на захват вывода логгера.
6. **«＋» не изменилась.** Тесты `CreateNoteModal` и шапки зелёные. Новая кнопка стоит
   перед `create-note-button` — тест на порядок в DOM.
7. **Слои** — `kg-layers` проходит.
8. **Регрессия** — полный цикл `kg-regression` зелёный.
