## Что сейчас

Квадратичное время в двух местах `nlp-service/app/core/chunking.py`. Абзац для чанкера — всё до
пустой строки, поэтому страница со строками через один перевод — это один абзац.

### 1. `_is_false_boundary` — на каждой точке читается абзац от начала

`_sentence_spans` на каждом знаке конца предложения вызывает `_is_false_boundary`. Та копирует
абзац от начала до точки (`prefix = text[block_start:punctuation_index]`), переводит его в нижний
регистр (`prefix.lower()`) и ищет последнее слово `rsplit` по всему префиксу. Когда одно «слово»
тянется через весь абзац («www.www.…»), его заново переводят в нижний регистр и ищут в нём `www.`
на каждой точке.

### 2. `_char_spans` — проба токенизирует остаток абзаца

Кусок длиннее окна без пробелов и без `; : ,` режется по символам двоичным поиском в диапазоне
`[cursor + 1, end]`, где `end` — конец абзаца. Каждая проба токенизирует текст от курсора до
середины этого диапазона — сотни килобайт ради куска в несколько сотен символов. Сюда попадают
склеенный текст, длинные числа, base64, URL и **весь китайский и японский текст**: `。` и `，`
чанкер знаками не считает.

Место 2 видно только после починки места 1: пока первое съедает время, второе в профиле теряется.

### Место 1: индекс абзаца без состояния

Перед проверкой точек абзаца за один проход строится `_ParagraphIndex` — четыре массива позиций:

| Массив | Что хранит для позиции x |
|---|---|
| `last_space` | последний пробельный символ до x |
| `marker_start` | самое позднее начало `http://`, `https://`, `www.`, закончившегося не позже x |
| `last_bad` | последний символ до x, который не может быть в числе: не цифра и не `.` `,` |
| `last_pair` | последний разделитель до x, стоящий сразу за другим разделителем |

Проверка точки — чтения из массивов и окно в несколько символов у точки:
«в слове есть `www.`» — это `marker_start[конец] >= начало`, «слово — число» — первая и последняя
цифры плюс `last_bad[конец] < начало` и `last_pair[конец] < начало`.

Строковые правила собраны в одну таблицу `_TOKEN_RULES`. Каждое объявляет самое длинное слово,
которое может совпасть: одна буква — 1, инициалы `a.b.c.d.e` — 9, сокращение — длина самого
длинного в `_ABBREVIATIONS`. Слово длиннее — правило пропускается без `lower()`. `str.lower()`
никогда не укорачивает строку, поэтому граница по исходной длине безопасна.

Два требования к реализации — способ можно менять, их нельзя:

1. **Нет состояния между точками.** Ответ для точки не зависит от того, какие точки спрашивали до
   неё и в каком порядке. Сверка спрашивает точки в перемешанном порядке. Вариант со сканером,
   который идёт только вперёд и копит факты о текущем слове, отклонён: порядок вызовов становится
   частью контракта, а в Java его легко нарушить.
2. **Строковое правило описано один раз, со своей границей.** Порог «длинного слова»
   вычисляется из таблицы (`_LONGEST_TOKEN_RULE`), а не задаётся числом. Новое правило — одна
   строка таблицы; второй ветки, где его можно забыть, нет.

Тонкое место — нижний регистр. Прототип переводит в нижний регистр окно, а не абзац. Это даёт тот
же ответ, потому что `İ` (единственная буква, которая при `lower()` становится двумя символами) и
`Σ` (`σ`/`ς` по контексту) не совпадают ни с одним проверяемым символом. В `_marker_starts`
для текста, длина которого после `lower()` меняется, сравнение идёт посимвольно.

Цена: индекс строится для каждого абзаца циклом на Python. 1000 обычных заметок по ~1,3 КБ —
1,75 с против 1,19 с, то есть +0,6 мс на заметку; пик памяти на абзаце в 400 КБ — 21 МБ.
Эмбеддинг заметки занимает десятки миллисекунд, поэтому это принято. Если будет мешать, индекс
можно строить через `re.finditer` и двоичный поиск по спискам позиций — без состояния.

### Место 2: поиск с удвоением окна

Окно пробы растёт от курсора: 1, 2, 4, 8… символов, пока кусок влезает. Затем двоичный поиск
между последним влезшим и первым невлезшим. Проба больше не читает остаток абзаца.

### Немонотонный счётчик

Двоичный поиск опирается на то, что более длинный кусок даёт не меньше токенов. Счётчик по словам
так себя ведёт. Токенизатор MiniLM (SentencePiece) подбирает разбиение всей строки, и новая буква
может уменьшить число токенов:

```
'заметкасвяз'   → 4: ▁замет | ка | свя | з
'заметкасвязь'  → 3: ▁замет | кас | вязь
```

Доля шагов, где добавленный символ уменьшает счёт: base64 — 0,03 %, URL — 0,6 %, китайский — 0,
русский без пробелов — 14 %, «1.1.1…» — 25 %.

При таком счётчике и старый, и новый поиск находят **какую-то** влезающую точку, а не самую
дальнюю, и точки разные: пробы разные. На русском без пробелов и «1.1.1…» все куски сдвинулись на
2–5 символов, оба варианта ровно по 126 токенов, ни один не длиннее окна. На base64, URL и
китайском куски совпали. Старая первая проба зависит от длины всего абзаца: дописанный в конец
текст сдвигал точки разреза в начале. Новая зависит только от текста у курсора. Поэтому «выход не
меняется» с настоящим токенизатором недостижим ни для одной быстрой резки, и критерий 3 заменяет
его на инварианты.

Затронуты только куски длиннее окна без пробелов и `; : ,`. При следующем пересчёте вектор такой
заметки сдвинется на доли процента; обычный текст режется так же.

### Найдено критерием 3 (дефект вне этой задачи — нужно решение владельца)

Первая редакция теста критерия 3 брала текст с пробелами и показала: **`_force_split`
может выдать чанк длиннее окна.** Куски пакуются по сумме их счётчиков
(`buffered_tokens + token_count ≤ max_tokens`), но выдаваемый спан — непрерывный
`buffer[0].start .. buffer[-1].end`, включающий пробелы между кусками. Под счётчиком,
считающим пробелы (`len`, chars, настоящий токенизатор), слитый чанк длиннее окна.
Воспроизведение: `'x'*5 + ' ' + 'y'*5`, `token_counter=len`, `max=10` — чанк
`('xxxxx yyyyy', 11)` и на эталоне, и после правки. На корпусе сверки под `--counter chars`
эталон нарушает окно в 2098 из 18 000 текст-окно комбинаций (~12 %).

Симметричная проверка есть у `_pack_units` (`actual_tokens <= max_tokens` перед выдачей
слитого чанка) — в `_force_split` она отсутствует: асимметрия, похожая на пропуск.
Починка — пересчёт слитого спана с фолбэком на поштучную выдачу — под `--counter words`
выход не меняет (пробелы дают 0 слов), но под `--counter chars` и настоящим
токенизатором меняет в тысячах текстов — прямой конфликт с критерием 2 «выход не
меняется», поэтому в эту задачу не вошла. Тест критерия 3 работает на сплошном
непробельном токене, где путь упаковки не задействован.

`pytest tests/` — зелёный; `tests/test_chunking.py` — 30/30.
