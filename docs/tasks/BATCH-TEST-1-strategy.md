# BATCH-1 follow-up: стратегия adversarial-тестирования для batch-роутов

## Статус

**2026-09-13.** Devin и владелец обсудили, что процесс покрытия batch-роутов должен вестись в определённом цикле: сначала регрессионные/позитивные тесты, потом намеренно падающие, затем исправления. Этот документ фиксирует договорённости и открытые вопросы.

## Согласованный процесс

1. **Ретроспективное покрытие (зелёные тесты).** Пишем позитивные и очевидные негативные тесты на текущую реализацию. Убеждаемся, что существующий функционал покрыт.
2. **Adversarial-фаза (красные тесты).** Осознанно проектируем тесты, которые *должны упасть*, исходя из знания реализации, OpenAPI и ожидаемых инвариантов.
3. **Исправление.** Любой падающий тест либо выявляет дефект (фиксим), либо показывает, что тест был некорректен (переписываем).
4. **Повтор.** Продолжаем, пока можем находить осмысленные падающие тесты.

## Практика из BATCH-1

Найдено через падающие тесты:
- `note.NewContent` ограничен 10 000 rune, API/OpenAPI — 50 000.
- `metadata.type` не валидировался по `ValidCelestialBodyTypes`.
- `source_url` в `/import/batch` не сохранялась.
- `/import/batch` создавал связи на несуществующие заметки.
- Пустой массив `notes` в `/import/batch` возвращал 200.

## Структура тестов

Позитивные и негативные тесты не дробятся по разным файлам: разделение идёт по **уровням**:

| Уровень | Что тестируем | Примеры |
|---|---|---|
| Unit (domain) | Value objects, entity invariants | `note.NewContent`, `note.NewTitle`, `note.NewNote` |
| Handler/integration | HTTP-контракт, DTO, репозиторий | `note_handler_test.go`, `note_handler_import_test.go` |
| Contract/regression | OpenAPI ↔ роутер, фронтенд-типы | `cmd/server/router_test.go` |

Решение 34: adversarial-тесты не получают суффикс или маркер. После исправления дефекта это обычные регрессионные тесты, и маркер быстро начинает врать. Происхождение фиксируется не в имени, а в файле задачи: какая атака или мутация сначала покраснела и какой дефект найден.

Разница фаз — в способе обнаружения. Очевидный негатив первой фазы следует из уже известного контракта: обязательное поле, max+1, запрос без прав. Adversarial-фаза начинается после чтения реализации и атакует её конкретные предположения: обратное направление, старый NULL, потеря поля промежуточным mapper, отсутствие обещанного побочного эффекта. Итоговый тест в обеих фазах остаётся зелёной регрессией.

## Практическое прохождение второй фазы

Проверяется применимый набор категорий:

- границы длины (0, 1, max, max+1);
- валидность enum и fallback;
- пустые/максимальные массивы;
- IDOR/владение;
- дубли (id, link);
- side effects (postprocess, metadata, `source_url`);
- промежуточные преобразования данных и устаревшие значения в хранилище.

Файл задачи перечисляет реально выполненные атаки/мутации и находки. Если после применимых атак новых дефектов нет, это записывается явно. Машинный guard не может восстановить происхождение уже зелёного теста и потому не подменяет это свидетельство.
