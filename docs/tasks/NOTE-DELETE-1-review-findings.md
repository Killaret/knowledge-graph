# NOTE-DELETE-1 — разбор ревью

Ревьюер: Claude Code. Дата: 2026-09-27. Реализация: Devin, `a6b99e3`, `22b9949`; удаление после SYNC-1 A2
идёт через outbox-декоратор (`49c2de3`). Постановка: [`NOTE-DELETE-1-soft-delete.md`](NOTE-DELETE-1-soft-delete.md).

**Вердикт: отклонено.** Удаление устроено правильно: строка остаётся, связи помечаются и возвращаются
только свои. Но с включённой авторизацией «Восстановить» не работает, удалённая заметка остаётся в
рекомендациях соседей, а срок хранения 90 дней не держит ни один тест.

## Блокер 1: восстановление отвечает 404 при включённой авторизации

**Живьём**, стенд из `4a11a3e` через `start-test.ps1`, `SKIP_AUTH=false`, одноразовый пользователь:
`DELETE /notes/{id}` — 204, строка в `notes` осталась, `POST /notes/{id}/restore` — **404**, заметка на
граф не вернулась, живых связей до удаления 2, после — 0.

Причина: маршрут `POST /notes/:id/restore` стоит за `RequireNoteAccess` (`cmd/server/router.go:185`,
`noteWrite`). Проверка прав ищет заметку обычным `FindByID`
(`interfaces/api/middleware/note_access.go`), а он после перехода на `gorm.DeletedAt` удалённые заметки
не находит — ответ 404 до обработчика. При `SKIP_AUTH=true` проверка пропускается, поэтому у
исполнителя восстановление прошло.

Personal-стек владельца работает с `SKIP_AUTH=false` (`docker-compose.personal.yml`: `${SKIP_AUTH:-false}`).
Значит, кнопка «Восстановить» у владельца не сработает. Данные не теряются: строка живёт 90 дней.

**Что нужно:** проверка прав для восстановления ищет заметку с учётом удалённых и сверяет владельца;
тест маршрута с настоящей проверкой прав: удалить → восстановить → 204, чужая удалённая заметка → 404.
Живьём — с `SKIP_AUTH=false`.

## Блокер 2: удалённая заметка остаётся в рекомендациях соседей

**Живьём:** у заметки X в рекомендациях была Y; сразу после удаления Y — `GET /notes/X/suggestions`
по-прежнему отдаёт Y, **с пустым названием**.

Причина: `GetSuggestions` берёт готовые рекомендации из `note_recommendations`
(`recommendation_repo.go`, без соединения с `notes`) и для каждой ищет название через `FindByID`
(`note_handler.go:1538–1547`). Удалённая заметка не находится, но подсказка всё равно добавляется —
с пустым `title`. Раньше жёсткое удаление убирало такие строки каскадом (FK `ON DELETE CASCADE`), мягкое
их не трогает.

Постановка, пункт 2: «удалённые заметки нигде не видны: список, поиск, граф, рекомендации, ключевые
слова, векторы, экспорт. Каждый путь чтения — с тестом». Тесты есть на поиск и чтение связей; на
рекомендации, граф, ключевые слова, векторы и экспорт — нет.

**Что нужно:** рекомендации не отдают удалённые заметки (фильтр в запросе или пропуск в обработчике);
тест на каждый путь чтения из пункта 2.

## Блокер 3: срок хранения 90 дней не держит ни один тест

Мутация: значение по умолчанию в `NewCleanupSoftDeletedTask` (`queue/tasks/cleanup.go:82`) 90 → 1 —
**зелёная**: тесты `queue/...` и `cmd/worker` проходят. `TestNewCleanupSoftDeletedTask` проверяет только
тип задачи. Граница 89/91 проверена в `TestNoteSoftDelete_PurgeHorizon` на вручную посчитанной отсечке —
а число, которое реально уходит в чистку, не проверено.

Это ключевое число обещания P-11 («удалённую заметку можно восстановить в течение 90 дней»).

**Что нужно:** тест, который проверяет срок в полезной нагрузке задачи чистки (или в итоговой
отсечке) — мутация «90 → 1» красная.

## Критерии

| # | Критерий | Вердикт | Чем проверен |
|---|---|---|---|
| 1 | удалить → восстановить: заметка и связи байт в байт; мутация «жёсткое удаление» красная | **тест есть, живьём не работает** | мутации «жёсткое удаление» и «без `deleted_via_note_id`» — красные (4 теста каждая); живьём с авторизацией — блокер 1 |
| 2 | тест на каждый путь чтения | **не выполнен** | блокер 2 |
| 3 | уборка: 89 дней есть, 91 нет | **частично** | граница — тестом; срок в задаче — блокер 3 |
| 4 | живьём: удалить → «Восстановить» → заметка в списке и на графе | **не выполнен** | блокер 1 |
| 5 | ADR 004 и `ARCHITECTURE_SUMMARY.md` | проверен | обновлены |

## Принято без замечаний

- Одна транзакция: заметка и её живые связи помечаются удалёнными, связи получают
  `deleted_via_note_id` (миграция 035); восстановление возвращает только свои связи и только когда живы
  оба конца — тесты и две мутации.
- Отдельно удалённая связь не воскресает — тест.
- Сервис графа удалённые заметки и связи отсекает во всех запросах, включая поиск пути.
- Сырые запросы бэкенда (`embedding_repo.go`, `keyword_repo.go`) фильтруют `deleted_at`.
- Чистка через 90 дней уносит связи каскадом и оставляет событие в outbox.
