## Постановка v1 (Claude Code, 2026-09-23)

Смысл v1: **собрать конвейер и начать копить артефакты, не трогая векторы.** Нормализованный
текст и чанки ложатся в Mongo и доступны для проверки глазами; эмбеддер продолжает читать сырой
`notes.content`. Переключение векторов на нормализованный текст — в MODEL-2, вместе с новой
моделью и чанкингом, одним пересчётом (решение владельца 2026-09-23, см. CHUNK-1).

### Что решено замером и черновиком

- **Один детерминированный проход**, `metrics.iterations = 1`, `stop_reason = "single_pass"`.
- **Два предохранителя, откат к исходнику** при срабатывании любого:
  `len(result) < 100` символов **или** `cos(emb(result), emb(source)) < θ`. Порог θ — параметр
  `nlp.normalization.min_cosine`: **зависит от шкалы модели** (у e5 близости выше), поэтому в v1
  умолчание 0.7 — из замера на e5-base, а калибровка под выбранную модель — задача MODEL-2. Оба
  сигнала пишутся в `metrics` — видно, что и почему откатилось.
- Хранилище, документ, история с выключателем `nlp.history.enabled`, каскад — как в «Решении» ниже.

### Устройство

```
worker, задача nlp:normalize (после сохранения заметки, как extract:keywords)
  -> nlp-service  POST /normalize  {text, title}
        нормализатор (app/core/normalization.py, чистый модуль, один проход + предохранители)
        чанкер CHUNK-1 (app/core/chunking.py)
     <- {normalized_text, chunks[], metrics, rolled_back, rollback_reason}
  -> Mongo nlp_artifacts  (документ по эскизу ниже; source_hash, pipeline_version = "norm-v1")
```

nlp-service остаётся вычислителем без хранилища; хранит backend. **У воркера сегодня нет
подключения к Mongo** — оно есть только у сервера (`cmd/server/main.go:78`). Подключить в
`cmd/worker` и в compose всех трёх стеков — часть задачи.

### Выключатель

`nlp.pipeline.enabled` (env → конфиг, по умолчанию **`false`**): при `false` задача не ставится в
очередь и `/normalize` не вызывается — прод ведёт себя как сейчас. Команда
`nlp-artifacts-recompute` (с `--dry-run`, пропуск по неизменному `source_hash`) — чтобы заполнить
артефакты для уже существующих заметок.

### Что не входит

Векторы по нормализованному тексту и таблица `note_chunk_embeddings` — MODEL-2 (размерность
зависит от выбора модели). Выборочный пересчёт изменившегося раздела — бэклог (CHUNK-1: единица
пересчёта — заметка).

### Критерии приёмки

1. **Инвариант владельца:** после прохода конвейера `notes.content` байт в байт прежний — тест.
   Исходный текст священен; нормализованная форма никогда его не заменяет.
2. **`/normalize`:** контракт и тесты на фикстурах `work-nlp4/fixture_boilerplate.json` и сиде; класс
   худшего случая замера (страница товара, дрейф 0.452) — откат по косинусу; короткий остаток —
   откат по длине.
3. **Mongo:** документ по эскизу; `(note_id, pipeline_version)` уникален для `current`; правка
   заметки → прежний документ `superseded`, новый `current`; при `nlp.history.enabled = false`
   `superseded` не копятся.
4. **Каскад:** удаление заметки удаляет её документы `nlp_artifacts` — тест.
5. **Выключатель:** при `false` ни задачи, ни вызова `/normalize` — тест.
6. `nlp-artifacts-recompute`: `--dry-run` печатает, сколько создаст и сколько пропустит; второй
   прогон ничего не создаёт.
7. **Мутации, каждая обязана краснеть:** снять оба предохранителя; игнорировать
   `nlp.history.enabled`; убрать каскад; записать нормализованный текст в `notes.content`.
8. **Живьём на тест-стенде:** выключатель включён, сид → артефакты у всех заметок; в находках —
   медиана сжатия и число откатов. Personal не трогать.
9. Документация: конвейер и выключатели — в `docs/architecture/ARCHITECTURE_SUMMARY.md`,
   параметры — в `docs/operations/CONFIGURATION_{EN,RU}.md`.

## Черновик (Devin, 2026-09-19)

## Проблема

Заметка эмбеддится «как есть»: один вектор от начала текста (усечение окна),
бойлерплейт импортированных страниц идёт в вектор наравне со смыслом. Идея
владельца: перед расчётом эмбеддинга и ключевых слов приводить заметку к
**логическому виду** — выкинуть мусор, оставить смысл.

## Инвариант UX (жёсткое требование владельца)

**Исходный текст заметки — священен.** Нормализованная форма — производный
артефакт, хранится отдельно и никогда не заменяет пользовательский контент.
Сценарий-антипример, который нельзя допустить: «заметка была, зашёл — осталось
20 слов друг за другом».

Следствие: где-то должна жить вторая версия текста — `note.content` (оригинал)
и нормализованная форма для индексации. Это и есть главный архитектурный вопрос.

## Два подхода из обсуждения

### A. Итеративная нормализация

Процесс приводит текст к логическому виду за несколько проходов (сжатие,
дедупликация фраз, выкидывание шаблонных блоков, структурирование).
**Открытый вопрос — критерий остановки**: сходимость (дельта смысла < порога),
фиксированное число итераций, бюджет времени/токенов. Без останова —
либо бесконечная работа, либо деградация до пустого текста.

### B. Чанкование (split → process → merge)

Делить заметку на куски по окну модели (512 токенов для e5-base), обрабатывать
каждый, объединять результат:
- для эмбеддинга — encode каждого чанка + mean-pool (или взвешенный: title/первый
  абзац весомее);
- для нормализации — нормализовать чанки независимо, склеить, разрешить
  дубли на стыках.

Проще, детерминированнее, без вопроса «когда остановиться» — но теряет связность
между чанками.

Гибрид из NLP-2 уже задуман для ключевых слов («вектор документа — по кускам») —
NLP-4 обобщает это на уровень нормализации текста.

## Хранение нормализованной формы — открытый вопрос

| Вариант | За | Против |
|---|---|---|
| Postgres (колонка/таблица `note_normalized`) | одна СУБД, транзакционная целостность с `notes`, бэкап покрыт | схема на каждый артефакт; текст дублируется рядом с оригиналом |
| MongoDB (денормализованный документ) | уже есть в стеке; гибкая схема под версии/итерации нормализации; тяжёлые производные тексты вне OLTP | вторая точка консистентности; нужен жизненный цикл (версия модели нормализатора, пересчёт) |

Что хранить в любом случае: текст логической формы, версия конвейера
(`normalizer-v*`), модель эмбеддинга, дата, хэш исходного контента (для
инвалидации при правке заметки), метрики сжатия (было → стало символов/токенов).

## Решение (зафиксировано владельцем 2026-09-19)

### Хранилище: MongoDB, коллекция `nlp_artifacts`

Нормализованная форма — технический rebuildable-артефакт, не пользовательская
сущность. Решено: **Mongo**. Аргументы: гибкая схема под версии конвейера и
метрики без миграций; OLTP-база и `notes` не раздуваются двойным текстом;
производные данные восстановимы пересчётом — распределённые транзакции не
нужны, достаточно инвалидации. CHECK-ограничения не нужны: валидация структуры
в коде конвейера (Go-структуры), JSON Schema validator опционален.

«Здоровье заметки» (откат, метки, пользовательский контроль) — отдельная
domain-сущность в Postgres, не путать с NLP-артефактом.

### Конвейер и сведение хранилищ

```
Postgres notes.content (сырьё, неизменно)
   -> 1. Нормализатор (итеративный)
        Mongo nlp_artifacts.normalized_text + метрики
   -> 2. Чанкер (резка по структуре, окно модели)
        Mongo nlp_artifacts.chunks[] {idx, text, heading_path, char_span, token_count}
   -> 3. Эмбеддер
        pgvector note_chunk_embeddings (note_id, chunk_idx, vector(N), model_version)
   -> 4. Агрегация
        pgvector doc-level вектор заметки (mean/weighted по чанкам)
   -> 5. Формула весов связей читает только pgvector
```

Ключ сведения Mongo ↔ pgvector: `note_id + chunk_idx`. Mongo хранит «что это
за чанк» (текст, происхождение), pgvector — «где он в векторном пространстве».

### Чанки: хранить, со структурой

Чанкование обязательно уже технически (окно e5-base 512 < медианы корпуса).
Чанк-векторы хранятся персистентно — дают парное сходство чанков для формулы
весов (длинная заметка связывается по совпавшему фрагменту, mean-pool размывает).
Каждый чанк несёт **происхождение**: `heading_path` (резка по заголовкам —
задел URL-HEADING-1), `char_span` в нормализованном тексте, `token_count`.
Бонусы: отладка связей («почему связались — вот два куска»), структурное
сравнение, выборочный пересчёт изменившегося раздела.

### История версий: включена, с выключателем

На время разработки история хранится: новый `pipeline_version` или правка
заметки → новый документ, старый `status: superseded`. Флаг
`nlp.history.enabled` (config JSON, default true): выключен — superseded не
пишутся/чистятся; позже возможен TTL-индекс Mongo на superseded-документы.

### Жизненный цикл

- Инвалидация: `source_hash` (хэш оригинала) — правка заметки → пересчёт.
- Каскад: удаление заметки → worker удаляет `nlp_artifacts`, чанк-эмбеддинги
  и doc-вектор. Один обработчик, три хранилища, порядок некритичен
  (всё rebuildable кроме сырья).
- `pipeline_version` — версия нормализатора (`norm-v1`, `norm-v2`), бамп →
  пересчёт; `model_version` — отдельно (смена нормализатора ≠ смена модели).

### Эскиз документа

```json
{
  "note_id": "uuid",
  "source_hash": "sha256",
  "pipeline_version": "norm-v1",
  "model_version": "e5-base",
  "normalized_text": "...",
  "chunks": [{"idx": 0, "text": "...", "heading_path": ["H1", "H2"],
              "char_span": [0, 480], "token_count": 120}],
  "metrics": {"raw_tokens": 1100, "norm_tokens": 700,
              "compression": 0.64, "iterations": 2, "stop_reason": "delta<5%"},
  "status": "current|superseded|processing",
  "created_at": "...", "updated_at": "..."
}
```

Индексы: `(note_id, pipeline_version)` unique для current; `(note_id)` для истории.

### Масштабирование (~100 пользователей) — справочно

Оценка владельца нагрузки: до 100 заметок/сутки на пользователя → 10K
обогащений/сутки худший случай. Два воркера e5-base ≈ 69K/сутки — запас ×7.
Реальная средняя ~0.5–1K/сутки тянет и один воркер; второй — под пики импорта
и ночной пересчёт. ВМ YC **4 vCPU / 8 ГБ ≈ 6–8К₽/мес** покрывает весь стек
(NLP ×2 ≈ 3.6 ГБ, Postgres ≈ 1 ГБ, Mongo+Redis ≈ 0.7 ГБ, backend+фронт ≈ 0.4 ГБ,
ОС+Docker ≈ 1 ГБ). Рост — линейный: реплики NLP-контейнера за asynq, +~2 ГБ RAM
на воркер. Узкое место — всплески импорта (10K заметок ≈ 3.5 ч очереди), но это
асинхронно, юзер не ждёт.

## Связи с другими задачами

- **MODEL-1/MODEL-2**: e5-base (окно 512) не снимает вопрос — половина заметок
  длиннее. Чанкование нужно в любом случае; нормализация может отодвинуть
  чанкование (сжатый текст влезает в окно целиком).
- **NLP-2**: keybert-гибрид уже хочет «вектор по кускам» — конвейеры должны
  делить общий препроцессор, иначе два разных пайплайна чистки.
- **IMP-8**: уроки нормализации импорта (логин-стены, бойлерплейт доменов,
  стаб-детекция) — это входные правила для нормализатора.
- **RECO-1/LINKS-1**: качество векторов напрямую задаёт качество связей.

1. ~~Postgres vs Mongo~~ — **решено: Mongo** (см. «Решение»).
2. ~~Чанки и их хранение~~ — **решено: хранить, векторы в pgvector, текст +
   происхождение (heading_path, char_span) в Mongo**.
3. ~~История логической формы~~ — **решено: да, с флагом `nlp.history.enabled`**.
4. ~~Итеративная нормализация: критерий остановки~~ — **закрыто замером**

   (108 заметок) итерации 2–4 не изменили ни одного текста — ruleset
   сходится за один проход. **v1 = один детерминированный проход**,
   `metrics.iterations=1`, `stop_reason='single_pass'`. Предохранители:
   откат при `len < 100` и предложенный страж `cos(emb_result, emb_source)
   < 0.7` (поймал бы худший случай — дрейф 0.452, правила вырезали контент
   как «навигацию»). Итеративность возвращается только с LLM-переписыванием.
   **Срок годности замера:** перепроверить после NOTE-QUALITY-1 — входной
   корпус изменится, выводы могут не устоять.
5. ~~Локально или LLM~~ — **решено: только локально** (правила из IMP-8 +
   экстрактивная обработка). LLM-вариант был гипотезой агента, не владельца;
   в стеке LLM нет, внешний вызов = приватность/стоимость — не рассматривается.
6. ~~Inline или фон~~ — **решено: фон** (асинхронное обогащение, как сейчас);
   inline-нормализация при сохранении — только как опция на будущее, если
   понадобится показывать качество заметки сразу (пользовательский flow,
   не конвейер).
7. Что делает нормализатор для title-only стабов и коротких заметок — пропускать.

## Находки реализации (Devin, 2026-09-25)

### Архитектура как сдано

- `nlp-service/app/core/normalization.py` — чистый модуль: один
  детерминированный проход (boilerplate-строки, голые URL, навигационные
  пробеги >=3 коротких строк, точные дубли строк, схлопывание whitespace),
  `iterations=1`, `stop_reason="single_pass"`. Оба предохранителя
  (length<100 -> `too_short`, cos<min_cosine -> `low_cosine`) откатывают к
  исходнику; `embed_fn` инжектируется — предохранитель покрыт юнит-тестами
  без модели. Вход короче 100 символов пропускается (`skipped=true`).
- `POST /normalize` — stateless: принимает `{text,title}`, отдаёт
  `normalized_text`, `chunks` (чанкер CHUNK-1), `metrics`, `rolled_back`,
  `rollback_reason`, `skipped`, `pipeline_version="norm-v1"`.
- Backend: `NLPClient.Normalize`, `nlp_artifacts` MongoDB-репозиторий
  (частичный уникальный индекс `(note_id, pipeline_version)` по
  `status='current'` + индекс `note_id` для каскада), задачи asynq
  `nlp:normalize` и `nlp:artifacts_cleanup`, воркер с Mongo-клиентом,
  команда `cmd/nlp-artifacts-recompute` (`--dry-run`, пропуск по
  source_hash).
- Выключатели: `nlp.pipeline.enabled` (JSON/env, default false — backend не
  ставит задачу, `/normalize` не вызывается), `nlp.history.enabled`
  (default true), `nlp.normalization.min_cosine` (default 0.7, шкала
  e5-base, перекалибровка — MODEL-2; значения вне (0,1] откатываются к
  умолчанию). Эмбеддинги по-прежнему строятся по сырому `notes.content`;
  переключение векторов — MODEL-2.
- Enqueue-точки: create, update (при смене текста), batch create/update,
  импорт; удаление (одиночное и batch) ставит cleanup-задачу.

### Ограничения и расхождения

- Артефакты пишутся, но не читаются никем — переход векторов на
  нормализованную форму это MODEL-2. До него весь конвейер — «тёплый»
  контур: пишет, не влияет.
- Сидовый корпус слишком чистый для оценки сжатия в массе (p50=1.0);
  реальная медиана — только на корпусе владельца после NOTE-QUALITY-1.
- Порог 0.7 — со шкалы e5-base-замера; на MiniLM косинусы смещены вверх,
  реальный запас меньше. Перекалибровка в MODEL-2.
- Поле `emb_cosine` в метриках null при `too_short`-откате и при пропуске —
  намеренно: косинус не считался.

Полный `check-all.ps1` (без `-Quick`) — сводка в журнале AI_LOG при сдаче.
