# NLP-4. Логическая нормализация заметки перед эмбеддингом

Черновик постановки, родился из обсуждения MODEL-1 с владельцем 2026-09-19.
Статус: **частично решено** — хранилище, чанки и история зафиксированы
владельцем 2026-09-19 (секция «Решение»); критерий остановки итеративной
нормализации и способ нормализации — открыты.

## Проблема

Заметка эмбеддится «как есть»: один вектор от начала текста (усечение окна),
бойлерплейт импортированных страниц идёт в вектор наравне со смыслом. Идея
владельца: перед расчётом эмбеддинга и ключевых слов приводить заметку к
**логическому виду** — выкинуть мусор, оставить смысл.

## Инвариант UX (жёсткое требование владельца)

**Исходный текст заметки — священен.** Нормализованная форма — производный
артефакт, хранится отдельно и никогда не заменяет пользовательский контент.
Сценарий-антипример, который нельзя допустить: «заметка была, зашёл — осталось
20 слов друг за другом».

Следствие: где-то должна жить вторая версия текста — `note.content` (оригинал)
и нормализованная форма для индексации. Это и есть главный архитектурный вопрос.

## Два подхода из обсуждения

### A. Итеративная нормализация

Процесс приводит текст к логическому виду за несколько проходов (сжатие,
дедупликация фраз, выкидывание шаблонных блоков, структурирование).
**Открытый вопрос — критерий остановки**: сходимость (дельта смысла < порога),
фиксированное число итераций, бюджет времени/токенов. Без останова —
либо бесконечная работа, либо деградация до пустого текста.

### B. Чанкование (split → process → merge)

Делить заметку на куски по окну модели (512 токенов для e5-base), обрабатывать
каждый, объединять результат:
- для эмбеддинга — encode каждого чанка + mean-pool (или взвешенный: title/первый
  абзац весомее);
- для нормализации — нормализовать чанки независимо, склеить, разрешить
  дубли на стыках.

Проще, детерминированнее, без вопроса «когда остановиться» — но теряет связность
между чанками.

Гибрид из NLP-2 уже задуман для ключевых слов («вектор документа — по кускам») —
NLP-4 обобщает это на уровень нормализации текста.

## Хранение нормализованной формы — открытый вопрос

| Вариант | За | Против |
|---|---|---|
| Postgres (колонка/таблица `note_normalized`) | одна СУБД, транзакционная целостность с `notes`, бэкап покрыт | схема на каждый артефакт; текст дублируется рядом с оригиналом |
| MongoDB (денормализованный документ) | уже есть в стеке; гибкая схема под версии/итерации нормализации; тяжёлые производные тексты вне OLTP | вторая точка консистентности; нужен жизненный цикл (версия модели нормализатора, пересчёт) |

Что хранить в любом случае: текст логической формы, версия конвейера
(`normalizer-v*`), модель эмбеддинга, дата, хэш исходного контента (для
инвалидации при правке заметки), метрики сжатия (было → стало символов/токенов).

## Решение (зафиксировано владельцем 2026-09-19)

### Хранилище: MongoDB, коллекция `nlp_artifacts`

Нормализованная форма — технический rebuildable-артефакт, не пользовательская
сущность. Решено: **Mongo**. Аргументы: гибкая схема под версии конвейера и
метрики без миграций; OLTP-база и `notes` не раздуваются двойным текстом;
производные данные восстановимы пересчётом — распределённые транзакции не
нужны, достаточно инвалидации. CHECK-ограничения не нужны: валидация структуры
в коде конвейера (Go-структуры), JSON Schema validator опционален.

«Здоровье заметки» (откат, метки, пользовательский контроль) — отдельная
domain-сущность в Postgres, не путать с NLP-артефактом.

### Конвейер и сведение хранилищ

```
Postgres notes.content (сырьё, неизменно)
   -> 1. Нормализатор (итеративный)
        Mongo nlp_artifacts.normalized_text + метрики
   -> 2. Чанкер (резка по структуре, окно модели)
        Mongo nlp_artifacts.chunks[] {idx, text, heading_path, char_span, token_count}
   -> 3. Эмбеддер
        pgvector note_chunk_embeddings (note_id, chunk_idx, vector(N), model_version)
   -> 4. Агрегация
        pgvector doc-level вектор заметки (mean/weighted по чанкам)
   -> 5. Формула весов связей читает только pgvector
```

Ключ сведения Mongo ↔ pgvector: `note_id + chunk_idx`. Mongo хранит «что это
за чанк» (текст, происхождение), pgvector — «где он в векторном пространстве».

### Чанки: хранить, со структурой

Чанкование обязательно уже технически (окно e5-base 512 < медианы корпуса).
Чанк-векторы хранятся персистентно — дают парное сходство чанков для формулы
весов (длинная заметка связывается по совпавшему фрагменту, mean-pool размывает).
Каждый чанк несёт **происхождение**: `heading_path` (резка по заголовкам —
задел URL-HEADING-1), `char_span` в нормализованном тексте, `token_count`.
Бонусы: отладка связей («почему связались — вот два куска»), структурное
сравнение, выборочный пересчёт изменившегося раздела.

### История версий: включена, с выключателем

На время разработки история хранится: новый `pipeline_version` или правка
заметки → новый документ, старый `status: superseded`. Флаг
`nlp.history.enabled` (config JSON, default true): выключен — superseded не
пишутся/чистятся; позже возможен TTL-индекс Mongo на superseded-документы.

### Жизненный цикл

- Инвалидация: `source_hash` (хэш оригинала) — правка заметки → пересчёт.
- Каскад: удаление заметки → worker удаляет `nlp_artifacts`, чанк-эмбеддинги
  и doc-вектор. Один обработчик, три хранилища, порядок некритичен
  (всё rebuildable кроме сырья).
- `pipeline_version` — версия нормализатора (`norm-v1`, `norm-v2`), бамп →
  пересчёт; `model_version` — отдельно (смена нормализатора ≠ смена модели).

### Эскиз документа

```json
{
  "note_id": "uuid",
  "source_hash": "sha256",
  "pipeline_version": "norm-v1",
  "model_version": "e5-base",
  "normalized_text": "...",
  "chunks": [{"idx": 0, "text": "...", "heading_path": ["H1", "H2"],
              "char_span": [0, 480], "token_count": 120}],
  "metrics": {"raw_tokens": 1100, "norm_tokens": 700,
              "compression": 0.64, "iterations": 2, "stop_reason": "delta<5%"},
  "status": "current|superseded|processing",
  "created_at": "...", "updated_at": "..."
}
```

Индексы: `(note_id, pipeline_version)` unique для current; `(note_id)` для истории.

### Масштабирование (~100 пользователей) — справочно

Оценка владельца нагрузки: до 100 заметок/сутки на пользователя → 10K
обогащений/сутки худший случай. Два воркера e5-base ≈ 69K/сутки — запас ×7.
Реальная средняя ~0.5–1K/сутки тянет и один воркер; второй — под пики импорта
и ночной пересчёт. ВМ YC **4 vCPU / 8 ГБ ≈ 6–8К₽/мес** покрывает весь стек
(NLP ×2 ≈ 3.6 ГБ, Postgres ≈ 1 ГБ, Mongo+Redis ≈ 0.7 ГБ, backend+фронт ≈ 0.4 ГБ,
ОС+Docker ≈ 1 ГБ). Рост — линейный: реплики NLP-контейнера за asynq, +~2 ГБ RAM
на воркер. Узкое место — всплески импорта (10K заметок ≈ 3.5 ч очереди), но это
асинхронно, юзер не ждёт.

## Связи с другими задачами

- **MODEL-1/MODEL-2**: e5-base (окно 512) не снимает вопрос — половина заметок
  длиннее. Чанкование нужно в любом случае; нормализация может отодвинуть
  чанкование (сжатый текст влезает в окно целиком).
- **NLP-2**: keybert-гибрид уже хочет «вектор по кускам» — конвейеры должны
  делить общий препроцессор, иначе два разных пайплайна чистки.
- **IMP-8**: уроки нормализации импорта (логин-стены, бойлерплейт доменов,
  стаб-детекция) — это входные правила для нормализатора.
- **RECO-1/LINKS-1**: качество векторов напрямую задаёт качество связей.

## Открытые вопросы к обсуждению

1. ~~Postgres vs Mongo~~ — **решено: Mongo** (см. «Решение»).
2. ~~Чанки и их хранение~~ — **решено: хранить, векторы в pgvector, текст +
   происхождение (heading_path, char_span) в Mongo**.
3. ~~История логической формы~~ — **решено: да, с флагом `nlp.history.enabled`**.
4. Итеративная нормализация: критерий остановки и защита от деградации.
   Текущая гипотеза из обсуждения — не сходимость, а бюджет: максимум N проходов,
   стоп при дельте <5% токенов, страховка «результат < X символов → откат
   к предыдущей итерации» (защита от сценария «осталось 20 слов»).
5. Нормализация делается локально (правила/экстрактивная суммаризация) или
   через LLM-вызов — в стеке LLM нет, внешний вызов = приватность/стоимость.
6. Нормализация при создании заметки (inline) или фоном как обогащение —
   скорее второе, чтобы не влиять на UX записи.
7. Что делает нормализатор для title-only стабов и коротких заметок — пропускать.
