## Блокер

`run-full-test-cycle.ps1`, финальная агрегация:

```powershell
$anyFailed = $script:PhaseResults.Values -contains 1
```

`-contains 1` ловит только код выхода, равный единице. Проверено на pwsh:

```
anyFailed при exit=2 : False
anyFailed при exit=1 : True
```

`go test` при панике отдаёт 2, `pytest` — 2, 4 или 5, `docker compose` — 125, 126, 127. При таком коде `[Final Summary]` печатает по фазе `[FAIL]`, а шапка сообщает `TEST CYCLE COMPLETE`, и скрипт завершается нулём. Это тот же дефект, ради устранения которого задача и ставилась, просто срабатывающий реже.

Замена:

```powershell
$anyFailed = @($script:PhaseResults.Values | Where-Object { $_ -ne 0 }).Count -gt 0
```

**Про способ проверки.** Предложенная подмена `seed-test-data.ps1` на `exit 1` этот дефект не поймает: с кодом ровно 1 проверка пройдёт. Стенд должен падать с кодом **2**.

## Мелкое

1. `Register-Phase` завершается `return $ExitCode -eq 0`, а вызывается как обычная команда — булево уходит в поток вывода, и после каждой фазы печатается лишняя строка `True`. Убрать `return` либо погасить через `$null =`.
2. В `run-full-test-cycle.sh` провал сидирования (около строки 107) не выставляет `any_failed`, тогда как в `.ps1` эта фаза регистрируется. Поведение версий должно совпадать.
3. Нумерация шагов рассинхронизирована: ранние шаги остались `[Step 4/28]`, очистка стала `[Step 27/27]`.

## Принято без замечаний

Структура `Register-Phase` / `Write-FinalSummary` / `Stop-TestCycle`; `throw` вместо `exit 1` внутри `try`, чтобы отчёт печатался из `catch`; сохранённый `finally` с остановкой тест-стека и восстановлением стеков; полная чистка автокоммита, `git add -A` и маркера «successful regression cycle» в обеих версиях; чистые `bash -n` и разбор pwsh.

## Блокер раунда 2

**Регрессионный тест не проверяет проверяемый скрипт.**

`scripts/testing/test-a3-exit-codes.ps1` не запускает, не читает и не подключает `run-full-test-cycle.ps1` — поиск по имени файла внутри теста даёт ноль совпадений. Вместо этого функции `Register-Phase`, `Write-FinalSummary` и выражение агрегации **скопированы внутрь теста**, и проверяется эта копия.

Следствие: верните в боевом скрипте прежнее `$script:PhaseResults.Values -contains 1` — тест продолжит проходить. Дефект, ради которого тест написан, он поймать не способен.

Это тот же класс проблемы, что и в находках A-1 и A-3 аудита: механизм проверки, который ничего не измеряет.

**Как чинить.** Вынести `Register-Phase`, `Write-FinalSummary` и вычисление `$anyFailed` в отдельный файл, например `scripts/testing/lib/phase-tracking.ps1`, подключать его из `run-full-test-cycle.ps1` через dot-sourcing и из теста — тоже. Тогда тест работает с тем же кодом, что и продакшен.

## Прочие находки

**1. Тест возвращает 1 при успешном прохождении.** Проверено запуском: `pwsh -NoProfile -File scripts/testing/test-a3-exit-codes.ps1` даёт код выхода 1 на ожидаемо-хорошем сценарии, потому что скрипт зеркалит код имитируемого цикла вместо собственного результата. В CI такой тест будет постоянно красным. Тест должен выходить с нулём, когда утверждение выполнено.

**2. `catch` теряет причину падения.** `run-full-test-cycle.ps1:692` печатает отчёт и выходит, ни разу не выведя `$_`. Все двенадцать мест жёсткой остановки бросают `throw "<причина>"`, и ни одна причина до оператора не доходит. Добавить вывод `$_.Exception.Message` в `catch`.

**3. Бросок без регистрации фазы.** `run-full-test-cycle.ps1:576` — `throw "Dev stack restoration failed (health endpoint)"` не сопровождается `Register-Phase`, в отличие от остальных двенадцати мест. При недоступности health-эндпоинта после восстановления получится отчёт, где шапка сообщает о провале, все перечисленные фазы помечены `[PASS]`, а причина не названа.

**4. Пропущенные проверки печатаются как пройденные.** Строки 540, 560, 663, 674 вызывают `Register-Phase ... -ExitCode 0` из ветки, которая выполняется, когда стек не был запущен. Прогон при остановленных стеках печатает `[PASS] Restore dev stack`, `[PASS] Dev stack health check`, `[PASS] Personal stack health check`, хотя ни восстановления, ни проверок не было. Честная форма уже есть в строке 430 — пометка «skipped» в имени фазы.

**5. Версии разошлись по семантике выхода.** `run-full-test-cycle.sh:399` при изменении состояния dev-стека выставляет `any_failed=true` и роняет прогон. В `run-full-test-cycle.ps1:646` то же условие только печатает предупреждение и фазой не регистрируется, прогон завершается нулём. Одно условие — разный результат на Linux и Windows. Нужно выбрать одну семантику.

**6. В `.sh` нет пофазного отчёта.** `run-full-test-cycle.sh:408` печатает только общий вердикт. В `.ps1` выводится статус каждой фазы. Оператор шелл-версии не увидит, какая именно фаза выставила `any_failed`, — то есть ровно ту диагностику, ради которой задача и ставилась.

**7. Ловушка ошибок может оборвать восстановление стеков.** `run-full-test-cycle.sh:9` ставит `trap '...; exit 1' ERR` вместе с `set -E`, распространяющим ловушку на функции, а строка 40 — `trap restore_stacks EXIT`. Отказ любой команды внутри `restore_stacks`, например тайм-аут `docker compose up -d --wait`, вызовет ERR внутри EXIT-ловушки и выход, пропустив остаток восстановления. Стеки останутся поднятыми частично.

**8. Мёртвая функция.** `run-full-test-cycle.ps1:87` — `Stop-TestCycle` объявлена и не вызывается ни разу; все места остановки используют встроенную пару «Register-Phase плюс throw».

**9. Ловушка подписана чужим именем.** Сообщение ERR-ловушки начинается с `[Final Summary]`, хотя настоящий итоговый блок на этом пути не выполняется: ни каталог снимков, ни накопленное состояние `any_failed` не печатаются.

**10. Критерий приёмки не выполнен.** Раздел «Ответ исполнителя» утверждает, что вывод показывает `[FAIL] Seed test data (exit 2)` и `TEST CYCLE FAILED`, но вывод не приложен, а тест, на который дана ссылка, боевой скрипт не запускает. Утверждение опирается на свидетельство, которого нет.

## Критерий приёмки раунда 2

1. Тест подключает общий код из боевого скрипта, а не копирует его. Проверка: временно вернуть в скрипте `-contains 1` — тест обязан упасть.
2. Тест выходит с кодом 0, когда утверждение выполнено.
3. Причина жёсткой остановки печатается в отчёте.
4. Пропущенные проверки помечены как пропущенные, а не как пройденные.
5. Приложен вывод прогона.
