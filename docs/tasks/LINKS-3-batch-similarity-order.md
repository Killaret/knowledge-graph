# LINKS-3. Пакетный подбор соседей берёт наименьшие UUID вместо ближайших

Постановка: Claude Code, 2026-09-23. Исполнитель: Devin. **Срочно:** до исправления
`gamma-links-regenerate` нельзя запускать нигде — ни на стенде, ни на Personal.

Найдено на ревью LINKS-2 (живой прогон пересчёта). Дефект старше LINKS-2: запрос написан в
апреле (`260764b`), пересчёт автосвязей построен на нём в LINKS-1, а тест REG-2 закрепил его
поведение как ожидаемое. Ревьюер пропустил его дважды — см. «Как это прошло мимо».

## Что сломано

`EmbeddingRepository.FindSimilarNotesBatch` (`backend/internal/infrastructure/db/postgres/embedding_repo.go`):

```sql
SELECT DISTINCT ON (e1.note_id, e2.note_id) e1.note_id AS source_id, e2.note_id, <score>
...
ORDER BY e1.note_id, e2.note_id, score DESC
```

а затем в Go: «первые `limit` строк на источник». Строки каждого источника идут в порядке
**`e2.note_id`**, а не близости, — `score DESC` после пары `(e1, e2)`, у которой одна строка,
ни на что не влияет. Итог: на каждую заметку возвращаются `limit` соседей **с наименьшими
UUID**, какой бы далёкой они ни были.

## Доказательство — живой стенд, 2026-09-23

Сид: 100 заметок, 60 ручных связей, автосвязи от воркера. После `gamma-links-regenerate`
(настоящий прогон, `Completed: 193 deleted, 200 created`):

```
SELECT target_note_id, count(*) FROM links WHERE source_type='gamma' GROUP BY 1 ORDER BY 2 DESC;
025b7473-…  99
014d8361-…  99
03bb1719-…   2        ← всего 3 различных цели на 200 связей

три наименьших UUID среди заметок с эмбеддингом: 014d8361-…, 025b7473-…, 03bb1719-…

доля пересозданных связей, попавших в настоящую пару ближайших по косинусу:  3 из 200
```

Пересчёт превращает граф в звезду вокруг двух заметок с наименьшими идентификаторами.
Косвенный след был и раньше: в находках LINKS-1 после пересчёта `note_links_closure`
сократилась с 1 114 до 297 строк — «топология другая»; звезда даёт мало пар.

Тот же дефект делает неверным счётчик `--dry-run` из LINKS-2: после отказа от пары, которая
заведомо в первой двойке соседей, dry-run пишет `0 candidates discarded` — кандидаты не те.

| `GammaLinkGenerator.GenerateForNotes` | `gamma-links-regenerate` (настоящий прогон) | **да** — проверено живьём |

## Что сделать

1. **Запрос.** Отбор первых `limit` по близости на каждый источник — в SQL, окном:

   ```sql
   SELECT source_id, note_id, score FROM (
     SELECT e1.note_id AS source_id, e2.note_id,
            GREATEST(0.0, LEAST(1.0, 1 - (e1.embedding <=> e2.embedding))) AS score,
            row_number() OVER (PARTITION BY e1.note_id
                               ORDER BY e1.embedding <=> e2.embedding, e2.note_id) AS rn
     FROM note_embeddings e1
     JOIN note_embeddings e2 ON e1.note_id <> e2.note_id AND e1.model_name = e2.model_name
     WHERE e1.note_id = ANY(?) AND e1.model_name = ? AND e2.model_name = ?
   ) t
   WHERE rn <= ?
   ORDER BY source_id, rn
   ```

   Второй ключ `e2.note_id` — только для детерминизма при равной близости. Заодно из базы
   перестаёт уходить N² строк: сейчас Go получает все пары и выбрасывает лишние.
2. **Тест REG-2 перевернуть.** Сейчас `TestEmbeddingRepository_FindSimilarNotesBatch`
   утверждает, что при `limit=2` отсекается близкая заметка с большим UUID, а выбирается
   **далёкая** («the selected far target proves clamping»). Правильное ожидание: две близкие
   заметки, далёкая отброшена. Проверку ограничения `[0, 1]` оставить отдельным утверждением
   на запросе без лимита или с лимитом 3.
3. **Оракул эквивалентности.** Интеграционный тест на настоящем pgvector: векторы подобраны
   так, что порядок UUID и порядок близости **противоположны**; для каждого источника
   `GenerateForNotes` (пакет) выбирает те же цели, что `GenerateForNote` (одиночный путь,
   который верен). Это тот тест, которого не хватало: два пути к одному ответу обязаны
   совпадать.
4. **Самоисключение** (мелочь из разбора REG-2): утверждение, что источник не входит в свои
   результаты.

## Критерии приёмки

1. Живой стенд: сид → `gamma-links-regenerate` → запрос выше показывает **десятки** различных
   целей, а доля связей в настоящей паре ближайших (запрос из «Доказательства») — **200 из 200**,
   за вычетом кандидатов, отсечённых порогом, ручными связями и отказами; отсечённые
   перечислены. Приложить оба запроса и их вывод.
2. После отказа от связи, которая в первой двойке соседей, `--dry-run` пишет
   `≥ 1 candidates discarded by recorded rejections` — счётчик LINKS-2 начинает говорить правду.
3. Мутации, каждая обязана краснеть:
   - вернуть `ORDER BY e1.note_id, e2.note_id` (порядок по UUID) → тест REG-2 и оракул;
   - убрать `WHERE rn <= ?` → тест на лимит;
   - убрать `e1.note_id <> e2.note_id` → тест самоисключения.
4. Находки: вызывал ли кто-нибудь `GetNeighborsBatch` в рабочем коде — ответ с `grep` и
   выводом.
5. `check-all` без `-Quick` зелёный — сводка в строке доски или журнале.

## Как это прошло мимо

- **REG-2 (21.09).** Ревьюер прогнал мутацию `score DESC → score ASC`, увидел, что тест
  остаётся зелёным, и записал её как «холостую: сортировка идёт по `e1.note_id, e2.note_id`
  раньше score». Причина была названа верно, вывод — нет: это значило не «мутация ни на что не
  влияет», а «запрос не выбирает ближайших вообще». Тест при этом прямо утверждал выбор далёкой
  заметки, и это было принято как проверка ограничителя.
- **LINKS-1 (21–22.09).** Пересчёт проверялся по числам — «удалено 197, создано 200, повтор
  идемпотентен» — и по времени обновления closure. **Какие** цели выбраны, не проверял ни
  исполнитель, ни ревьюер. Число связей было правильным, связи — нет.

Урок для ревью пакетных путей: сверять не количество, а содержимое — с независимым путём
к тому же ответу.

## Реализация — Devin, 2026-09-23

**Запрос.** `FindSimilarNotesBatch` переписан на оконный отбор по спецификации:
`row_number() OVER (PARTITION BY e1.note_id ORDER BY e1.embedding <=> e2.embedding,
e2.note_id)` + `WHERE rn <= ?` в SQL; `e2.note_id` остался только тай-брейком.
Go-слой больше не ограничивает и не выбрасывает строки — база отдаёт ровно
`limit` ближайших на источник.

**REG-2 перевёрнут.** `TestEmbeddingRepository_FindSimilarNotesBatch`: при
`limit=2` выбираются две близкие заметки (`targetCloseSmallID`,
`targetCloseLargeID`, обе score 1.0), далёкая отброшена — хотя её UUID меньше.
Проверка клампа `[0,1]` перенесена в утверждение на широком запросе (limit=10):
далёкая заметка должна быть последней со score 0.0.

**Оракул.** `TestFindSimilarNotesBatch_MatchesSinglePath` — интеграционный на
pgvector: порядок UUID противоположен порядку близости (у ближайшей заметки
наибольший UUID `f000…`, у далёкой наименьший `1000…`); batch обязан выбрать те
же цели в том же порядке, что одиночный `FindSimilarNotes`. Найден побочный
эффект: у одиночного пути нет тай-брейка при равном score — при ничьей порядок
недетерминирован. В тесте оставлены различимые score.

**Самоисключение** — уже покрыто утверждением №5 REG-2 (широкий запрос,
источник не входит в свои результаты); мутацией №3 подтверждено, что оно
ловит.

**Мутации — все красные:**
- `ORDER BY e1.note_id, e2.note_id` в окне → оракул: batch выбрал `1000…`
  (наименьший UUID = самая далёкая) вместо `f000…` — FAIL.
- Убран `WHERE rn <= ?` → REG-2: 4 результата на источник вместо 2 — FAIL.
- Убрано `e1.note_id != e2.note_id` → REG-2 №5: self-match просочился — FAIL.

**Находка №4 — `GetNeighborsBatch` в рабочем коде.** `grep` по
`backend/{cmd,internal/interfaces}` и `services/`: вызывается только из
`compositeNeighborLoader.GetNeighborsBatch` (`composite_loader.go:65`), а его —
нигде: `traversal_service.go` зовёт одиночный `GetNeighbors`. Пакетный путь
embedding-соседей жив, но рабочего вызывателя нет — исправление запроса тем не
менее корректно, потому что им пользуется `GammaLinkGenerator` напрямую через
репозиторий.

**Живой стенд и `--dry-run` счётчик** — критерии 1–2 приёмки требуют пересчёта
на стенде; стенд после прогона Клода стоит звездой, пересоздаётся
`start-test.ps1`. За ревьюером.
