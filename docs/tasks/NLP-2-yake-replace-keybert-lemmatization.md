## Почему сейчас, а не потом

Исходное обсуждение (2026-09-12, сохранено в конце файла) исходило из того, что `yake 0.4.8`
приемлем, а проблема — только в `0.7.3` с его AGPL. **Это неверно, и проверено по пакету,
а не по памяти.**

| поле `License` в метаданных `yake 0.4.8` | `LGPLv3` |
| классификатор PyPI там же | `GNU General Public License v3 (GPLv3)` |
| **файл `LICENSE` внутри пакета** | «under the terms of the **GNU General Public License**, either version 3, or any later version» и «a **commercial license** is also available for industrial projects… contact INESC TEC» |

коммерческой альтернативой. Никакого LGPL.

Проект — MIT (`LICENSE` в корне). Образы `killaret/knowledge-graph-*` лежат на Docker Hub
с `yake` внутри — это распространение, то есть триггер копилефта. Разница между `0.4.8` и
`0.7.3` не «чисто / грязно», а «GPL / GPL плюс сетевая оговорка». Оставаться на `0.4.8`

## Что есть сейчас — по коду, не по описанию

`nlp-service/app/nlp_utils.py`:

- `kw_extractor = yake.KeywordExtractor(lan="ru", top=20, stopwords=stop_words)` — создаётся
  **при импорте модуля**, язык захардкожен `ru`, стоп-слова свои (ru + en из NLTK).
- `extract_keywords(text, top_n)`: у `yake` меньше — лучше, поэтому `weight = clamp(1 - score, 0, 1)`.
- Модель эмбеддингов грузится **лениво** через `_load_embedding_model()` под замком — это
  синглтон, который `keybert` обязан переиспользовать.

`nlp-service/app/models.py`: `text` ограничен 10 000 символами на входе API; ответ —
`{keywords: [{keyword, weight}]}`.

`backend/internal/infrastructure/queue/worker.go`, `HandleExtractKeywords`: `top_n` считается
от длины текста (5…20 по числу слов / 100), результат сохраняется через
`KeywordRepository.SaveAll` — **удалить все ключевые слова заметки и вставить новые** в одной
транзакции. Таймаут HTTP-клиента к NLP — 10 секунд.

Схема (`003_create_note_keywords_table`): `note_keywords(note_id, keyword, weight)`,
первичный ключ `(note_id, keyword)`. Колонок про происхождение или форму слова нет.

**Как ключевые слова связывают граф** —
`backend/internal/application/recommendation/keyword_similarity.go`, `JaccardSimilarity`:
`|A ∩ B| / |A ∪ B|` по **точному совпадению строк**. «дерево», «деревья» и «Дерево» — три
разных ключа с нулевым пересечением. Именно поэтому лемматизация — не улучшение, а условие,
при котором эта метрика вообще что-то измеряет. Взвешенный вариант (`WeightedJaccardSimilarity`)
использует `weight`, поэтому семантика веса тоже должна сохраниться: `[0, 1]`, больше — сильнее.

## Что сделать

### 1. Экстрактор

- `requirements.txt`: убрать `yake`, добавить `keybert`, `pymorphy3` (тянет `pymorphy3-dicts-ru`).
- `KeyBERT` создаётся **лениво, поверх уже загруженного** `SentenceTransformer` из
  `get_embedding_model()`, а не при импорте и не второй копией модели. Импорт `nlp_utils`
  не должен грузить модель — сейчас это так, и так должно остаться.
- `keyphrase_ngram_range=(1, 2)`, стоп-слова — те же ru + en, что сейчас.
- Вес: `keybert` отдаёт косинусную близость, больше — лучше: `weight = clamp(score, 0, 1)`.
  Формула `1 - score` уходит вместе с `yake`.
- Сигнатура `extract_keywords(text, top_n)` и место вызова в `main.py` не меняются.

### 2. Лемматизация — после извлечения, по каждому ключевому слову

Вариант A из обсуждения: `keybert` возвращает поверхностную форму, лемматизируем результат,
а не исходный текст — иначе пользователь увидит «дерево» там, где написал «деревьев».

- Маршрутизация **по алфавиту токена**, не по языку документа: кириллица → `pymorphy3`,
  латиница → `nltk.stem.WordNetLemmatizer` (уже в проекте); остальное — как есть.
  Смешанный ru+en текст для этого проекта — норма, документ одним языком не описывается.
- Многословная фраза лемматизируется потокенно и склеивается пробелом.
- Лемма приводится к нижнему регистру.
- **Дедупликация по лемме**: несколько поверхностных форм с одной леммой схлопываются в одну
  запись; остаётся форма с наибольшим `weight`.
- Анализаторы `pymorphy3` и WordNet создаются один раз (синглтон), как модель.

### 3. Хранение: лемма — ключ, поверхностная форма — рядом

Миграция `NNN_note_keywords_lemma_and_extractor`:

- `keyword` **становится канонической леммой**. Первичный ключ `(note_id, keyword)` остаётся —
  он же бесплатно гарантирует дедупликацию по лемме на уровне базы. `JaccardSimilarity`
  и репозиторий продолжают ключеваться на `keyword` без правок.
- Новая колонка `surface TEXT NOT NULL DEFAULT ''` — форма для показа пользователю.
  Для существующих строк `surface = keyword` (до пересчёта лемма и форма совпадают).
- Новая колонка `extractor TEXT NOT NULL DEFAULT 'yake-0.4.8'` — чем посчитано. Новые строки
  пишутся с `keybert-<версия>`; строка версии — в одном месте, константой в `nlp-service`,
  и **возвращается в ответе API**, а не дублируется в Go.
- `down`-миграция снимает обе колонки; данные в `keyword` не откатываются — это пересчёт,
  а не переименование, обратной операции у него нет, и в `down` так и написать.

### 4. Контракт API — расширение, не замена

`/extract_keywords` отвечает `{extractor: "keybert-0.9.0", keywords: [{keyword, surface, weight}]}`.
Поле `keyword` — лемма, `surface` — как было в тексте. Старое поле сохраняет имя, поэтому
существующий потребитель не ломается, но его **семантика меняется** — записать это в
`docs/API_EN.md` и в OpenAPI явно, а не оставить читателю догадываться.

`backend/internal/infrastructure/nlp/client.go`: `Keyword{Keyword, Surface, Weight}` плюс
`extractor` из ответа; `worker.go` сохраняет все три колонки.

### 5. Пересчёт существующих заметок — это миграция данных

Смена экстрактора меняет ключевые слова у **каждой** заметки. Без пересчёта старые заметки
останутся с `yake`-словами в старых формах, новые придут с леммами от `keybert`, и Жаккар
между старой и новой заметкой обнулится там, где раньше находил связь. Это ровно то, что
P11-2 решал для эмбеддингов через `embed-recompute`; делать по тому же образцу.

`backend/cmd/keyword-recompute/main.go`, зеркально `cmd/embed-recompute/main.go`:

- Выборка: заметки с непустым содержимым, у которых **нет ни одной строки** `note_keywords`
  с `extractor` = текущий. Заметки, для которых `keybert` честно вернул пустой список,
  будут попадать в выборку при каждом запуске — это допустимо, пересчёт разовый, и это
  записать в шапку скрипта.
- Ставит `ExtractKeywords` в очередь с задержкой, как `embed-recompute`; `--dry-run` печатает
  список; `--batch-delay` для больших объёмов.
- `--post`: те же пост-шаги, что у `embed-recompute` — пересчёт весов связей, сброс
  устаревших рекомендаций, инвалидация Redis. Не дублировать код: вынести `runPostSteps`
  в общий пакет и вызывать из обоих.
- Идемпотентен: повторный запуск после успешного ничего не ставит в очередь.

**Порядок: лемматизация и `keybert` выезжают одним изменением, пересчёт — один.** Два
пересчёта — это дважды прогнать все заметки через модель.

**Пересчёт ждёт решения по модели (MODEL-1, решение владельца 2026-09-17).** Ранжирование
keybert зависит от модели эмбеддингов; если её сменят после пересчёта, считать придётся
снова. Разработку это не задерживает: модель для keybert — параметр, код пишется и
проверяется на текущей. Задерживается только запуск `keyword-recompute` на живых данных.

На Personal-стеке пересчёт запускает **владелец**, при свежем бэкапе — сторож
`guard-personal-data.py` и так не даст иначе. Тест-стек — Devin, с приложенной сводкой.

### 6. Два риска, которые надо измерить, а не прикинуть

**Окно модели.** `paraphrase-multilingual-MiniLM-L12-v2` обрезает вход на **128 токенов**
(проверено по `sentence_bert_config.json`; сеть физически умеет 512, см. MODEL-1).
`yake` видит весь текст; `keybert` с этой моделью считает эмбеддинг документа по его началу —
для заметки в 10 000 символов это первый абзац. Кандидаты берутся из всего текста, но
ранжируются близостью к обрезанному документу. **Вариант по умолчанию — гибрид:** кандидатов отбирает статистика по всему тексту
(частота и позиция, ~100 штук), а keybert только **ранжирует** этот список через параметр
`candidates=` — так шорт-лист собран по всему документу, а число прогонов модели ограничено
по построению. Вектор документа — по кускам текста, а не только по началу. Замер на 20
самых длинных заметках тест-сида — **три выдачи рядом**: `yake` как есть, keybert «в лоб» по
всему тексту, гибрид. Решение по выдачам, глазами владельца.

**Скорость.** `yake` — статистика, `keybert` — инференс модели по документу и по каждому
кандидату. Замерить p50/p95 `/extract_keywords` до и после на тест-сиде; таймаут клиента
10 секунд — жёсткая граница, к которой нельзя подходить ближе половины. Если не влезает —
уменьшить шорт-лист гибрида (это и есть ограничение кандидатов; `nr_candidates` в keybert
управляет другим — диверсификацией при `use_maxsum`) и снова замерить, а не поднимать таймаут.

## Тесты

По норме `.windsurfrules` «Adversarial Phase»: сначала зелёные, потом намеренно красные,
находки — в этот файл, тесты не маркируются.

**Юнит, `nlp-service`:**

- лемматизация: `деревья → дерево`, `running → run`, `Дерево → дерево`, `graph databases →
  graph database`, смешанная фраза `база данных graph → база данных graph`, число `2026 → 2026`;
- дедупликация: `[("деревья", 0.8), ("дерево", 0.6)]` → одна запись, `surface="деревья"`,
  `weight=0.8`;
- вес: для любого входа все `weight` в `[0, 1]`, и у более близкого кандидата вес больше;
- ленивость: импорт `nlp_utils` не вызывает загрузку модели (мок `_load_embedding_model`
  с проверкой, что не звали).

**Интеграция, Go:** `keyword-recompute` на базе с тремя заметками — одна с `extractor=yake-0.4.8`,
одна с `keybert-*`, одна без строк и с текстом — ставит в очередь ровно две; повторный
запуск после обработки — ноль.

**Adversarial — пройти и записать, что нашлось:**

- пустой текст; один токен; текст из одних стоп-слов; текст ровно в 10 000 символов и в 10 001;
- ключевое слово, которое лемматизируется в стоп-слово (`был → быть`) — должно отфильтроваться
  **после** лемматизации, а не только до;
- два кандидата с одной леммой и **одинаковым** весом — какой `surface` выживает и стабилен ли выбор;
- токен с кириллицей и латиницей вместе (`GPT-модель`);
- `JaccardSimilarity` при двух пустых наборах возвращает `1.0` — «полное сходство» двух заметок
  без ключевых слов. Это уже в коде и не по этой задаче, но `keybert` может давать пустой
  результат чаще `yake`: **замерить, сколько заметок тест-сида остаются без ключевых слов**
  до и после, и если число растёт — это находка в этот файл.

**Мутации, приложить вывод:**

1. Убрать вызов лемматизации → тест `деревья → дерево` краснеет.
2. Вернуть `weight = 1 - score` → краснеет тест направления (у более близкого кандидата
   вес должен быть больше; тест одного лишь диапазона такую мутацию пропустит).
3. Убрать условие по `extractor` из выборки `keyword-recompute` → тест идемпотентности краснеет.
4. Заменить `pymorphy3` на `str.lower` → тест `деревья → дерево` краснеет.

## Состояние

- **Решение владельца:** в будущем заменить `yake` на `keybert` (MIT) и сразу добавить лемматизацию ключевых слов, потому что это критично для качества графа.

## Почему `keybert`

| Критерий | `yake 0.4.8` | `yake 0.7.3` | `keybert` |
|---|---|---|---|
| Лицензия | GPL-3.0-only (по LICENSE) | AGPL-3.0-or-later | MIT |
| Подход | статистический на уровне документа | тот же + лемматизация | BERT-эмбеддинги + cosine similarity |
| Мультиязычность | `lan` (ru/en) | `lan` + `lemmatize` | через мультиязычную SentenceTransformer-модель |
| Качество | среднее | среднее+ | выше по исследованиям |
| Интеграция | отдельная библиотека | отдельная | переиспользует тот же `sentence-transformers` |

Проект уже использует `paraphrase-multilingual-MiniLM-L12-v2` для эмбеддингов. `keybert` может работать с той же моделью, поэтому новые тяжёлые зависимости не требуются.

## План реализации (черновик)

### 1. Замена в `nlp-service`

- `requirements.txt`: убрать `yake`, добавить `keybert`.
- `nlp-service/app/nlp_utils.py`:
  - создать `kw_model` на базе уже загруженной модели `SentenceTransformer`;
  - заменить `kw_extractor.extract_keywords(text)` на `kw_model.extract_keywords(...)`;
  - `keybert` возвращает `(keyword, similarity)`, где `similarity` — 0..1, чем больше, тем лучше (в отличие от `yake`, где меньше лучше).
- Сигнатура `extract_keywords(text, top_n=10)` остаётся; возвращаемый формат `[(keyword, weight)]` тоже.

### 2. Лемматизация

Лемматизация критична, потому что из ключевых слов строятся узлы графа. Без неё «дерево» и «деревья» будут разными узлами.

**Вариант A — лемматизация после `keybert` (рекомендуется):**

1. `keybert` возвращает ключевые слова в оригинальной форме.
2. Лемматизировать каждое ключевое слово:
   - русский — `pymorphy2` / `pymorphy3` (MIT);
   - английский — `nltk.stem.WordNetLemmatizer` (уже есть в проекте).
3. Группировать по лемме: если несколько форм имеют одну лемму, оставлять одну (например, с лучшим `keybert`-score).
4. В API возвращать **оригинальную форму** для читаемости, но в графе использовать **лемму** как canonical node label.

**Вариант B — лемматизация всего текста перед `keybert`:**

- Быстрее, но ломает читаемость результата: `keybert` будет выдавать «дерево» вместо «деревьев».
- Не рекомендуется для пользовательских меток.

**Язык:** в проекте два языка — русский и английский. `pymorphy2`/`pymorphy3` работает только для русского/украинского. Для английского достаточно `nltk.WordNetLemmatizer`. Если появятся другие языки — нужен spaCy или аналог.

### 3. Неизбежные правки

- `nlp-service/Dockerfile`:
  - убрать/заменить `yake`;
  - `keybert` не требует отдельных data-артефактов, кроме уже скачиваемой модели.
- `nlp-service/tests/test_api.py`:
  - моки `extract_keywords` остаются, но реальные тесты могут дать другие score и наборы ключевых слов.
- `docs/ARCHITECTURE_*`:
  - убрать упоминания `yake`, заменить на `keybert`.
- `backend/internal/infrastructure/nlp/client_test.go`:
  - endpoint `/extract_keywords` не меняется, но ожидаемые тестовые значения могут отличаться.

### 4. Открытые вопросы для обсуждения с Claude Code

- Подтвердить выбор лемматизатора: `pymorphy2` vs `pymorphy3` (последний — активный форк).
- Подтвердить `keyphrase_ngram_range`: `(1, 2)` для unigrams + bigrams? `(1, 3)`?
- Как обрабатывать смешанные (ru+en) тексты: одна модель `paraphrase-multilingual-MiniLM-L12-v2` покрывает оба языка, но лемматизация требует разных анализаторов.
- Нужна ли кэширование `keybert`-модели (отдельный singleton), чтобы не загружать повторно?
- Как влияет на перформанс: `keybert` медленнее `yake` за счёт embedding inference. Нужно ли ограничивать длину текста?
- Нужно ли обновить формулу веса связей? `keybert` score — `cosine similarity`, `yake` score — 0..∞, в `nlp_utils.py` уже нормализуется `weight = 1.0 - score`. Для `keybert` формула будет `weight = score` (или `max(0.0, min(1.0, score))`).
