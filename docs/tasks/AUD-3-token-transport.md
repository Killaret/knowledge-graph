# AUD-3. Транспорт токена: query-параметр, PKCE методом plain, state на чужом флаге

Постановка для Devin. Источник: [`../EXTERNAL_AUDIT_2026-09.md`](../EXTERNAL_AUDIT_2026-09.md), находки S-5, S-6. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code.

**Очерёдность:** после AUD-2. Задача небольшая и не пересекается с AUD-2 по файлам, кроме общей области auth — брать последней в партии, чтобы не смешивать диффы.

## Проблема

Три ослабления в том, как переносится и проверяется учётный материал.

1. Access-токен принимается из строки запроса и потому попадает в логи, историю браузера и `Referer`.
2. PKCE отправляется методом `plain`, при котором challenge равен verifier — защита от перехвата кода почти обнуляется.
3. Проверка `state` выполняется внутри ветки PKCE: выключение PKCE молча снимает и CSRF-защиту OAuth.

## Что выяснено в коде

**1. Query-параметр никем не используется.** `middleware/jwt.go:140-144` — третий способ извлечения:

```go
token := c.Query("token")
if token != "" {
    return token, nil
}
```

Поиск по фронтенду не находит ни `EventSource`, ни `text/event-stream`, ни передачи токена в URL. В бэкенде SSE-эндпоинтов нет. То есть **обычная причина держать query-токен здесь отсутствует**, и ветка удаляется без замены. SSE в роадмапе есть (TD-3), но не реализован; когда дойдёт — решать отдельно и осознанно.

**2. `extractToken` не возвращает ошибку ни на одном пути.** `jwt.go:121-147` — все ветки отдают `(значение, nil)`, финальная — `("", nil)`. Поэтому обработка `err != nil` на `jwt.go:75-79` недостижима, и пустой токен вместо быстрого отказа уходит в проверку чёрного списка Redis (`jwt.go:82-94`) на каждом анонимном запросе. Это находка F-3; чинится здесь же, потому что переписывается ровно эта функция.

**3. Заголовок без `Bearer` принимается как сырой токен.** `jwt.go:126-130`: если префикса нет, всё содержимое `Authorization` считается токеном. Не уязвимость, но лишняя вольность в разборе.

**4. PKCE включён по умолчанию.** `config.go:458` — дефолт `true`. Значит `state` сейчас проверяется, и это **не активная дыра**, а связанность двух независимых защит. Формулировка находки должна остаться честной: чиним конструкцию, а не тушим пожар.

**5. Verifier и challenge генерируются вместе.** `handlers/auth/handler.go:615-621` вызывает `authpkg.GeneratePKCE(...)` и кладёт пару в Redis через `StorePKCE`. Перевод на `S256` — это изменение в генераторе (`internal/auth`), а не только в хендлере: challenge должен стать base64url(SHA-256(verifier)) без выравнивания, verifier остаётся как есть.

**6. `state` генерируется всегда.** `handler.go:612` — `GenerateRandomToken(32)` вызывается независимо от PKCE, но сохраняется только вместе с PKCE-парой. Значит для отвязки нужно отдельное хранение `state`, а не переиспользование `StorePKCE`.

## Что сделать

**Извлечение токена** (`internal/interfaces/api/middleware/jwt.go`)

- Удалить ветку `c.Query("token")`.
- Требовать префикс `Bearer` в заголовке `Authorization`; заголовок без префикса токеном не считать.
- Дать `extractToken` возвращать реальную ошибку, когда токена нет, и обрывать запрос до обращения к Redis. Ветка `jwt.go:75-79` должна стать достижимой.
- Куку `access_token` оставить как есть — это валидный транспорт.

**PKCE** (`internal/auth`, генерация пары)

- Считать `code_challenge` как base64url без выравнивания от SHA-256 верификатора.
- В `handlers/auth/handler.go:635` заменить `code_challenge_method=plain` на `S256`.
- Проверить, что обмен кода (`provider.Exchange(ctx, code, codeVerifier)`) по-прежнему передаёт **verifier**, а не challenge.

**Отвязка `state`** (`handlers/auth/handler.go`)

- Хранить `state` отдельно от PKCE-пары, с собственным TTL (10 минут, как сейчас у PKCE).
- В `YandexCallback` проверять `state` **всегда**, до и независимо от ветки PKCE. Отсутствие или несовпадение — `400`, обмен кода не выполняется.
- При включённом PKCE verifier по-прежнему достаётся по `state`.

**Конфигурация и документация**

- `.env.example` и `docs/CONFIGURATION_EN.md`: убрать упоминания query-токена, если есть; отразить, что PKCE использует `S256`.

## Ограничения

- Не менять формат и время жизни самих JWT, не трогать `JWTManager.ValidateToken`.
- Не трогать `internal/auth` в части Argon2 и refresh-токенов.
- Не менять маршрут `/api/v1/auth/yandex` и список `SkipPaths` — это AUD-4, отдельная задача. Здесь правится только содержимое OAuth-запроса и проверка `state`.
- Не трогать graph-service: его auth разбирается в AUD-5.
- Не трогать `.claude/`, `.devin/`, `docs/EXTERNAL_AUDIT_2026-09.md`, `docs/tasks/AUD-*.md`, `README.md`, `docs/TESTING.md`, `ROADMAP.md`.
- Personal-стек не поднимать.

## Критерии приёмки

1. `go test ./...` и `go vet ./...` зелёные.
2. Табличный тест на `extractToken`: заголовок с `Bearer` — принимается; заголовок без префикса — отвергается; кука — принимается; `?token=` — **игнорируется**; пустой запрос — ошибка, и она достигает ветки `jwt.go:75-79`.
3. Тест, доказывающий, что при отсутствии токена обращения к `TokenStore.IsTokenBlacklisted` не происходит.
4. Тест на PKCE: для известного verifier challenge равен base64url без выравнивания от SHA-256, и в запрос уходит `code_challenge_method=S256`.
5. Тест на `state`: при `PKCE_ENABLED=false` колбэк с чужим или отсутствующим `state` получает `400` и обмен кода не выполняется. Это главный критерий — сейчас в этой конфигурации проверки нет вовсе.
6. `npm run test:unit` на фронтенде зелёный: убедиться, что удаление query-токена ничего не сломало.

## Что приложить к результату

Вывод теста из пункта 5 в двух конфигурациях — `PKCE_ENABLED=true` и `PKCE_ENABLED=false`. Обе должны отвергать чужой `state`; до правки вторая его принимает.
