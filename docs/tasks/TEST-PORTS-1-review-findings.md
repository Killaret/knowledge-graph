## Мелочи

1. **Резерв плавает.** Сегодня 19090 в резерв уже не входит: зарезервированы 18901–19000 и
   19201–19400. Мутация «вернуть 19090» проходит проверку, и это правильно. Значит, 29090 выбран по
   сегодняшней картине и надёжен не навсегда. Защищает именно проверка, поэтому при следующем сбое
   читать её сообщение, а не переносить порт вслепую.
2. **`.windsurfrules` перезаписан с концами строк CRLF**: дифф на 591 строку, настоящих правок две
   (порты). `.gitattributes` не покрывает файлы без расширения. Изменённую целиком норму в ревью не
   прочитать, а слияние `ai-agents → main` при любой правке файла в `main` даст конфликт на весь
   файл. Починка: строка `.windsurfrules text eol=lf` в `.gitattributes` и
   `git add --renormalize .windsurfrules`. Сделать ближайшим коммитом Devin, до слияния.
3. Запрос с хоста сделан позже, на моём стенде для ревью LINKS-2 (ревизия `bf790fe`, compose тот
   же): `curl 127.0.0.1:29091/health` → 200 `{"status":"ok","service":"graph-service"}`, TCP к
   29090 открывается. Первый стенд Devin погасили раньше, чем я до него дошёл, а поднимать свой,
   пока Devin работал со стендом, я не стал (см. ниже).

## Инцидент: мой запуск стенда удалил чужие контейнеры

В 17:43 я запустил `start-test.ps1` из своего дерева. Скрипт делает `down` своему проекту, а затем
удаляет **все** контейнеры `kg-test-*`, «оставшиеся от другого compose-проекта» (`d004fa2`,
2026-08-05; тогда клон был один). В моём логе есть строка `Removing orphaned test containers...`:
удалено было что-то чужое. Чьё именно, по логу не видно, а историю событий Docker за это время уже
вытеснили события `check-all`. Косвенные признаки: в дереве Devin шла работа над LINKS-2, а в 17:46
его стенд (проект `knowledge-graph-ai-agents`) был создан заново. Вероятнее всего, я снёс его
работающий стенд. Моя сборка закончилась позже и упала на конфликте имени `kg-test-nlp`. Процесс
Devin перед запуском я не проверил, хотя новая норма протокола о живости агента требует именно этого.

Дело не только в невнимательности. Имена контейнеров фиксированные (`container_name: kg-test-*`),
порты тоже, поэтому второй запуск молча убивает первый. Двум агентам на одной машине нужен замок.

**TEST-LOCK-1 (бэклог, Devin).** `start-test.ps1` не трогает контейнеры `kg-test-*` другого
compose-проекта. Если такие есть, скрипт выходит с сообщением: чей это проект (метка
`com.docker.compose.project.working_dir`) и с какого времени он запущен. Захватить стенд можно только
осознанно, ключом `-Force`. В `start-test.sh` принудительного удаления нет. Там нужна та же проверка,
иначе второй запуск просто упадёт на конфликте имени без объяснения. Проверка: два дерева, второй
запуск падает с сообщением и не трогает первый стенд. Мутация: снять проверку — первый стенд удалён.

## TEST-LOCK-1 — Devin, 2026-09-24

Инцидент закрыт ownership guard-ом до первого разрушительного действия:

- общий `check-test-stack-ownership.mjs` читает все `kg-test-*`, их label
  `com.docker.compose.project.working_dir`, имя и `StartedAt`;
- `start-test.ps1` и `start-test.sh` вызывают guard **до** `compose down -v`;
- чужой или отсутствующий owner-label блокирует запуск и перечисляет контейнеры;
- Windows допускает только явный `start-test.ps1 -Force`; shell force не имеет;
- прежнее удаление orphan-контейнеров выполняется только после успешной проверки.

Проверено живьём временным `kg-test-lock-probe` с owner `D:/foreign-tree`:
`start-test.ps1` и `start-test.sh` вышли с кодом 1 до `down -v`, сообщили owner и
`StartedAt`; контейнер остался running. `--force` у guard exit 0 и сам по себе
контейнер не удалил. Временный контейнер удалён после проверки.

Автоматическое покрытие подключено отдельной фазой `test-stack-ownership-tests` в
`core-checks.tsv` и `_core-checks.yml`: нормализация Windows/Linux путей, свой owner,
чужой owner, отсутствующий label, порядок guard до `down -v`/`docker rm -f`, наличие
`-Force` только в PowerShell. Мутация удаления **вызова** guard из `start-test.ps1`
красная; первая версия теста ошибочно смотрела только наличие имени файла в скрипте
