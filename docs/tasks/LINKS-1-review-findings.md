## Блокер 1: обновление closure на реалистичном графе — минуты, и оно синхронное

Сид по умолчанию (`seed-test-data.ps1`: 100 заметок, 60 ручных связей) плюс 197 автосвязей.
`REFRESH MATERIALIZED VIEW CONCURRENTLY note_links_closure`:

- мой ручной запуск — снят через **5 мин 46 с**, не дождавшись;
- запуск самого graph-service (pid 81, по событию `LinkCreated`) — **~8,5 минут** до конца.

Причина — не 032 и не pgvector, а рекурсивный CTE из 027, который перечисляет **все простые
пути** до длины 10 ради колонки `path`. На этом графе рост по глубине:

| глубина | путей в CTE | различных пар |
|---|---|---|
| 3 | 4 804 | 1 367 |
| 4 | 20 063 | 1 846 |
| 5 | 81 048 | 2 108 |
| 6 | 308 632 | 2 200 |

×4 на каждый уровень; до глубины 10 — порядка 8·10⁷ строк с массивами uuid, ради 2 200 пар.
Потребители же берут `distance <= depth` при `depth` по умолчанию 2 и максимум 5
(`services/graph-service/internal/engine/recommendations.go:12,17`); `path` нужен одному
запросу «путь между двумя заметками» (`db/postgres_client.go:356`).

Почему это блокер LINKS-1, а не «старый долг 027»: до автосвязей граф был редким (60 рёбер
на 100 узлов) и CTE не взрывался. Автосвязи дают **каждой** заметке две исходящие — граф
становится плотным, и та же формула перестаёт работать. Постановка это предвидела («поднимать
степень без замера нельзя», критерий 3), но замер сделан на сиде без ручных связей — на нём
33–125 мс, и вывод «на сиде refresh дешёвый» оказался выводом про другой граф. Обработчик
событий graph-service (`subscriber/pubsub.go:248`) зовёт refresh синхронно на каждое
`LinkCreated` — при генерации на библиотеке владельца подписчик встанет на первом же событии.

Что нужно:

1. **CTE.** Ограничить рекурсию максимальной глубиной потребителя (5) и перестать
   перечислять все пути: закрытие по уровням с дедупликацией пар (`UNION` по
   `(ancestor, descendant)` без `path`) либо один путь на пару через `DISTINCT ON` на каждом
   уровне; «путь между двумя заметками» считать по запросу, не хранить.
2. **graph-service.** Refresh — асинхронно и с дебаунсом (одно обновление на пачку событий),
   обработчик не блокирует подписчика.
3. **Замер на настоящем графе.** Сид по умолчанию (60 ручных + автосвязи) и синтетический
   граф на 1 000 заметок со степенью 3: время refresh в находках. Ожидание — секунды.
   Тест на границу (например, 1 000 узлов, refresh < 10 с) обязан краснеть на возврате
   CTE «все пути до 10».

## Блокер 2: порог молча превращается в ноль

`getJSONFloatOrDefault` (`config.go:570`) отдаёт значение из JSON всегда, когда файл загружен;
отсутствующий ключ — `0.0`. JSON вшит в образ (`backend/Dockerfile:24`), так что умолчание
`0.6` в Go не применяется никогда, а «тройка env → json → default» из постановки на деле
двойка. Стек с `knowledge-graph.config.json` без ключа `gamma_link_min_score` (старый
смонтированный конфиг, `docker-compose.yml:145`) получит порог 0 — то самое «каждая заметка
свяжется с любыми соседями», ради чего порог вводился. Devin сам нашёл этот класс в
DOC-AUDIT-1 и записал как нюанс документации; для порога это дефект.

Что нужно: `GammaLinkMinScore <= 0` → умолчание 0.6 с строкой в логе; тест с JSON-конфигом
без ключа. Класс целиком (все `getJSON*OrDefault`) — отдельной строкой бэклога CONFIG-1.

## Мелочи — не чинить в ущерб очереди

- Ошибка генерации связей роняет всю задачу `compute:embedding` (`worker.go`, `return err`):
  asynq повторит и NLP пересчитает эмбеддинг, хотя он уже сохранён. Достаточно логировать и
  возвращать nil — либо отдельная задача на связи.
- `EnqueueRefreshRecommendations` на цель, у которой задача уже в очереди, возвращает
  `asynq.ErrTaskIDConflict`, и воркер пишет это как «failed to enqueue» — ожидаемая
  дедупликация выглядит ошибкой в логе.
- Бинарник `gamma-links-regenerate` только в target `cli`; в тест-compose нет сервиса, из
  которого его можно вызвать, — ревьюеру пришлось бы собирать образ отдельно. Сервис
  `cli-test` с профилем, как `cli_personal`, снял бы это.

## Доработка Devin, 2026-09-22

### Блокер 1 — CTE и синхронный refresh

- **Миграция 033** (`033_bounded_note_links_closure`): рекурсия ограничена глубиной 5
  (максимум потребителей: `engine/recommendations.go`, `engine/neighbors.go` — второй теперь
  тоже клампит). Вместо перечисления всех простых путей — два CTE: `levels` дедуплицирует
  `(ancestor, descendant, distance)` через `UNION`, `paths` продлевает обходы только пока
  они могут остаться кратчайшими (join на `pairs` с `p.distance < pr.distance`; цикл не
  проверяется — достигнутая за минимальное число шагов пара проста по построению).
  `weight` = MAX произведения по кратчайшим путям. Колонка `path` убрана — хранение путей и
  было причиной взрыва; `GetShortestPath` считает путь по запросу (одно-источниковый BFS по
  живым `links`, глубина ≤ 5, `ORDER BY distance, weight LIMIT 1`), регрессия —
  `postgres_client_integration_test.go` → `GetShortestPath_OnDemand` (прямое и обратное
  направление). Down-миграция восстанавливает определение 032.
- **Асинхронный refresh** (`subscriber/pubsub.go`): события сигналят в канал ёмкостью 1,
  фоновый `closureRefreshLoop` дебаунсит 2 с и делает один `REFRESH ... CONCURRENTLY` на
  пачку; обработчик события больше не блокируется. `NoteDeleted` — тот же путь. Отмена
  контекста останавливает цикл. Тест `TestLinkEvents_DebounceClosureRefresh`: 10 событий
  подряд → ровно 1 refresh; событие после окна тишины → второй. Мутация «вернуть
  синхронный вызов» — красная (10 refresh на 10 событий).

### Блокер 2 — порог

- `resolveGammaLinkMinScore` (`config.go`): env → JSON → 0.6, плюс сторож: `<= 0` → 0.6 со
  строкой в логе. Тест `TestGammaLinkMinScore_MissingJSONKey`: JSON без ключа → 0.6,
  явное 0.7 побеждает. Общий класс `getJSON*OrDefault` остаётся на CONFIG-1.

### Мелочи — не блокеры

1. `closureRefreshLoop` сбрасывает таймер на каждый запрос: поток событий чаще, чем раз в 2 с,
   откладывает обновление неограниченно. На пачке (регенерация) это ровно то, что нужно, но
   потолок («не позже N секунд с первого запроса») дешевле, чем разбираться потом.
2. Кламп в `neighbors.go` тестом не охраняется — единственное изменение доработки без мутации.
3. `GetShortestPath` на паре без пути отдаёт **500** вместо 404/пустого ответа (проверено
   живьём). Поведение прежнее, не этой доработки, но теперь запрос «есть ли путь» стал
   осмысленным, и 500 на нормальный ответ «пути нет» будет мешать.
