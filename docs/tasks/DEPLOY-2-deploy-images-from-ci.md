## Находка: образы на Hub отстали от контракта на пять дней

```
killaret/knowledge-graph-backend:2026-09-08  создан 2026-09-08 18:57 UTC
e4d5d14  2026-09-12 23:11  feat: implement batch routes for notes and import (#37)
072153a  2026-09-13 07:59  feat(note-type): DDD NoteType value object and canonical taxonomy
```

В образе, который получит второй разработчик, **нет** `POST /notes/batch/create`,
`POST /notes/batch/delete`, `POST /import/batch`, нет типа `moon` и нет правок импорта
из IMP-5. А `backend/openAPI.yaml` на `main` всё это описывает, и `docs/api/API_EN.md`
отправляет разработчика именно к этой спецификации.

То есть договор, который мы ему передаём, и сервер, который мы ему передаём, — из
разных недель. Хуже всего с batch-маршрутами: по IMP-4 они нужны Java-сервису в первую
очередь. Он напишет клиента по спеке и получит 404 от поднятого стека.

Причина структурная, а не чья-то забывчивость: образы публикуются руками, а workflow,
который каждый push собирает и проверяет свежие образы, их **удаляет** после проверки
(`docker rmi` в `deploy.yml`). Механизма «проверено → опубликовано» нет.

### Критерии приёмки

- Push в `main` после зелёной проверки оставляет на Hub пять образов с датированным
  тегом и двигает `main`; push в `ai-agents` не публикует ничего — проверить обоими
  push'ами, показать `docker manifest inspect` до и после.
- Без секретов workflow зелёный, шаг публикации `skipped` с сообщением.
- `docker compose -f docker-compose.deploy.yml up -d --wait` на чистой машине (или в CI)
  поднимает стек, и `GET /openapi.yaml` с него совпадает с `backend/openAPI.yaml` того
  же коммита — это и есть проверка, что контракт и сервер снова из одной недели.
- `check-all` зелёный.

### Ограничения

- Не публиковать из веток кроме `main`.
- Не трогать `docker-compose.personal.yml`.
