## PUB-1 — **постановку нельзя брать в работу как есть: одно допущение ложно**

### Блокер постановки: `Get` не проходит через `applyNoteScope` вовсе

Постановка утверждает: «слой данных уже готов — `applyNoteScope` фильтрует по `is_public` при пустом пользователе; мешает только глобальный `JWTAuth`» и «работа меньше, чем кажется — пропустить запрос с пустым пользователем, а не писать новую логику доступа».

Это верно для поиска: `NoteRepository.Search` и сопутствующие выборки идут через `applyNoteScope` (`note_repo.go:218,247,265`), и анониму они отдадут только публичное.

Но для чтения по id это **неверно**:

- `NoteRepository.FindByID` (`note_repo.go:90-101`) вообще не принимает `userID` и не вызывает `applyNoteScope` — `Where("id = ?", id)` без всякого scope.
- `Handler.Get` (`notehandler/note_handler.go:1002-1036`) после `FindByID` не проверяет ни владельца, ни `IsPublic` — отдаёт 200 с содержимым любой найденной заметки.

Следствие: если просто добавить `/api/v1/notes/:id` в `SkipPaths`, аноним получит **содержимое любой приватной заметки по id** — ровно та утечка, которую постановка велит не допустить. Постановку надо дополнить пунктом: в `Get` (или в скоупленной выборке для него) нужна проверка — анониму непубличная заметка отвечает `404`, как несуществующая. Это новая логика доступа, а не «пропустить запрос».

### Смежное наблюдение (вне PUB-1, но фиксирую)

`Get` сегодня не проверяет владельца и для авторизованных: любой залогиненный пользователь читает чужую приватную заметку по `id` — `creator_id` в ответе, а проверки нет. Это существующий IDOR вне периметра задачи; предлагаю вынести отдельной строкой на доску, чтобы не растворился.

### Что в постановке подтверждено

- `applyNoteScope` при `userID == uuid.Nil` добавляет `WHERE is_public = true` — `note_repo.go:46-48`. Для `Search`/`List`/`FindAllPaginated` этого достаточно.
- `JWTAuth` глобальный (`router.go:83`), `SkipPaths` — `jwt.go:39-52`, двенадцать записей, заметок и поиска там нет.
- Коллизия маршрутов не страшна: `GET /notes/:id` (`router.go:167`) и `GET /notes/search` (`router.go:176`) уже сосуществуют; `c.FullPath()` возвращает точный шаблон маршрута, поэтому запись `/api/v1/notes/:id` в `SkipPaths` не откроет `/notes/batch`, `/notes/:id/links` и прочие — они имеют другие шаблоны. Проверено чтением списка маршрутов.
- `cacheControlMiddleware` висит на обоих открываемых GET (`router.go:167,176`) — требование «не трогать `private`/`Vary`» выполнимо, заголовки ставятся на маршрут, а не на аудиторию.

## PUB-2 — **принимается; две конкретные точки внимания**

- Якорь подтверждён: `graph.ts:253` — `isAuthenticated() ? "v1/graph/full" : "v1/graph/public"`.
- Ловушка с кэшем реальна и её стоит назвать точнее, чем «проверь nocache»: `PreloadService.preloadedGraph` — **единый слот** с `lastHash` и флагом `isPublic` (`PreloadService.ts:44`, записи на :142-190). При переключении режима дельта-запрос `getGraphDelta(this.preloadedGraph.lastHash)` (`:205`) уйдёт с хешем чужого режима — `v1/graph/delta` ключуется не режимом. Исполнителю: кэш надо сбрасывать или ключевать по режиму, иначе режим «Сообщество» подмешает дельту «Моего графа» и наоборот.
- Отдельно проверить, считает ли graph-service дельту в скоупе вызывающего: если дельта считается по графу пользователя, то для режима «Сообщество» инкрементальное обновление может быть неприменимо — тогда для него дельту отключать, а не чинить.
- Умолчание «аноним → Сообщество, авторизованный → Мой граф» согласуется с текущим поведением и обратимо. Место для переключателя — рядом с тумблерами вида (`GraphTopBar`/`GraphPageShell`) — подтверждаю, органы управления видом там.

## AUTO-1 — **принимается с двумя уточнениями реализации**

### По защите от самозапуска — выбор признака

Постановка просит выбрать надёжный признак. Ответ: **автор коммита, не актор события**. `github.actor` на `push` — это учётка, сделавшая push; я пушу локально под учётными данными владельца, поэтому актором будет владелец и защита по актору не отличит мой push от его. Различие есть только в авторе коммита: мои коммиты подписаны `devin-ai-integration[bot]` (см. `git log`). Условие — пропускать запуск, если `head_commit.author.email` (или `username`) содержит `devin-ai-integration`. Push человека и push Claude Code (`Claude Opus 5 <noreply@anthropic.com>`) должны триггерить — это и есть желаемый хендoff.

Крайний случай для полноты: смешанный push, где head-коммит мой, а чужой есть ниже — пропустит запуск, хотя работа чужого внутри. Приемлемо: следующий не-ботский push или ручной запуск её подхватит; усложнять условие ради этого не стоит.

### По запуску сессии Devin

`DEVIN_API_KEY` необходим, но, возможно, недостаточен: создание сессии через API обычно требует, чтобы репозиторий был подключён к организации Devin (интеграция/доступ), а промпт — указывал ветку `ai-agents`, иначе сессия может стартовать на `main`. Рекомендация постановке: в промпт workflow стоит вписать не только «прочитай `docs/AI_HANDOFF.md` и делай своё», но и явную работу на ветке `ai-agents` — доска сама про ветку не скажет.

### Подтверждённая реализуемость

- `paths: docs/AI_HANDOFF.md` на `on: push` покрывает критерий 4 (холостой ход) штатно.
- Суточный лимит реализуем без внешнего хранилища: `GITHUB_TOKEN` + `gh api repos/{repo}/actions/workflows/{id}/runs?created=YYYY-MM-DD` — посчитать сегодняшние запуски и пропустить при исчерпании. Число предложу при реализации (ориентир: десяток — ревью за день не бывает чаще).
- Критерий 6: `secrets` нельзя читать в `jobs.<job>.if` — секрет маппится в `env` на уровне джобы, а шаги гардятся `if: env.DEVIN_API_KEY != ''` либо отдельным шагом с внятным сообщением и `exit 0`. Оба варианта рабочие.
- Правило автопуша в обеих копиях `/kg-work` — механически просто; условия (только `ai-agents`, только свои коммиты, конфликт → стоп и запись на доску) сформулированы достаточно.
