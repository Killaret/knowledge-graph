# PUB-1. Открыть анониму чтение публичной заметки и поиск по публичным

Постановка для Devin. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code на живом тест-стеке.

**Очерёдность:** первая из тройки PUB. Блокирует VIS-1 раунд 3 — пока поиск закрыт, анонимный визуальный эталон снимает плашку ошибки.

**Это изменение публичного периметра.** Читать раздел «Что выяснено» до начала.

## Зачем

Решение владельца: публичный граф — витрина сообщества. Неавторизованный посетитель заходит, видит опубликованные заметки, читает их и ищет по ним; после входа переключается на своё.

Сегодня замысел выполнен наполовину. Граф рисуется, но **прочитать заметку нельзя**: узел несёт только `ID, Title, Type, Creator, Public` (`services/graph-service/internal/db/postgres_client.go:13-19`), содержимого в нём нет, а `GET /api/v1/notes/:id` требует токена. Поиск отвечает `401`:

```
GET /api/v1/notes/search?q=star   ->  401 Unauthorized
```

Получается витрина из подписанных точек, которые нельзя открыть.

## Что выяснено в коде

**1. Поиск — слой данных готов.** `applyNoteScope` (`backend/internal/infrastructure/db/postgres/note_repo.go:36-48`) при `userID == uuid.Nil` добавляет `WHERE is_public = true`, и `Search` через него проходит (`note_repo.go:218,247,265`). Здесь достаточно пропустить запрос.

**2. Чтение по id — слой данных НЕ готов, и это главное в задаче.** `FindByID` (`note_repo.go:90-101`) не принимает `userID` и не вызывает `applyNoteScope` вовсе: `Where("id = ?", id)` без всякого ограничения. `Handler.Get` (`notehandler/note_handler.go:1002-1036`) после него не проверяет ни владельца, ни `IsPublic` — отдаёт `200` с содержимым любой найденной заметки.

Значит **простое добавление `/notes/:id` в `SkipPaths` открывает анониму содержимое любой приватной заметки по id.** Это не «пропустить запрос», а новая логика доступа, и писать её надо явно.

*Поправка к первой редакции постановки: я утверждал, что слой данных готов для обоих маршрутов. Для чтения по id это было неверно, ошибку нашёл Devin при ревью постановки — разбор в [`SPECS-review-findings.md`](SPECS-review-findings.md).*

**3. Мешает не только middleware.** `JWTAuth` глобальный (`backend/cmd/server/router.go:83`), список исключений — `jwt.go:39-52`, двенадцать записей, заметок и поиска там нет. Но снятие этого барьера — только половина работы.

**4. Коллизии маршрутов бояться не нужно.** `c.FullPath()` возвращает шаблон маршрута, поэтому запись `/api/v1/notes/:id` не откроет `/notes/batch` и `/notes/:id/links` — у них другие шаблоны. Проверено Devin при ревью постановки.

**5. `Cache-Control` трогать нельзя.** После AUD-2 приватные ответы отдаются как `private` с `Vary: Authorization, Cookie`. Те же маршруты будут обслуживать обе аудитории, поэтому вернуть `public` **нельзя**: иначе приватный ответ владельца попадёт в общий кэш. Это прямая регрессия находки S-4 аудита.

## Что сделать

### 1. Пропустить два маршрута без токена

`GET /api/v1/notes/:id` и `GET /api/v1/notes/search` — в исключения `JWTAuth`.

Внимание на способ: `JWTAuth` сравнивает `c.FullPath()`, поэтому в списке должен стоять шаблон Gin (`/api/v1/notes/:id`), а не конкретный путь. Соседние маршруты при этом не откроются — см. пункт 4 выше.

Открыто должно быть ровно два маршрута, оба `GET`. Само по себе это ничего не защищает: защита — в пункте 2.

### 2. Написать проверку доступа для чтения по id

Это основная работа задачи. Способ на твой выбор — скоупленная выборка вместо `FindByID`, либо проверка в хендлере, — важен результат: **анонимный запрос непубличной заметки не отдаёт её содержимого.**

Если выберешь проверку в хендлере, помни, что она обязана стоять до формирования ответа и покрывать все поля: сейчас наружу уходят `content`, `metadata` и `is_public`.

`Search` в этой правке не нуждается — он уже скоуплен.

### 3. Приватная заметка анониму — `404`, а не `403`

Существование чужой приватной заметки не должно подтверждаться. Для анонимного запроса приватный `id` отвечает так же, как несуществующий.

**Про смежный IDOR.** При ревью постановки выяснилось, что `Get` не проверяет владельца и для авторизованных: любой залогиненный читает чужую приватную заметку по id. Это существующий дефект, он шире PUB-1 и вынесен отдельно — см. [`SEC-1-note-idor.md`](SEC-1-note-idor.md). **Не чини его здесь**, иначе в одном диффе смешаются открытие периметра и закрытие утечки, и ревью не сможет отделить одно от другого. Если порядок задач сложится так, что SEC-1 сделан раньше, — тем лучше, тогда здесь останется только анонимная ветка.

### 4. Не трогать

- `Cache-Control` и `Vary` — остаются `private`.
- Запись: создание, правка, публикация, удаление остаются за токеном.
- `POST /notes/:id/publish` и `unpublish` — не трогать.
- Рекомендации, ключевые слова, достижения — вне задачи.

## Критерии приёмки

1. Анонимный `GET /api/v1/notes/<id публичной>` отдаёт `200` с содержимым.
2. Анонимный `GET /api/v1/notes/<id приватной>` отдаёт `404`.
3. Анонимный `GET /api/v1/notes/search?q=<слово из публичной>` отдаёт `200` и только публичные заметки.
4. Анонимный поиск по слову, которое встречается **только в приватной** заметке, не возвращает её.
5. Авторизованный владелец по-прежнему видит и приватные — в чтении и в поиске.
6. Запись анонимом по-прежнему `401`: `POST /notes`, `PUT /notes/:id`, `DELETE /notes/:id`.
7. Заголовки не изменились: `Cache-Control: private`, `Vary: Authorization, Cookie`.
8. **Проверено мутацией, двумя.** Первая: убрать ветку `userID == uuid.Nil` из `applyNoteScope` — тест на критерий 4 (поиск) обязан покраснеть. Вторая: убрать новую проверку доступа из чтения по id — тест на критерий 2 обязан покраснеть. Без второй мутации главная защита задачи ничем не удерживается.

## Что приложить к результату

Вывод `curl -D -` по критериям 1–4 и 6, анонимно и под токеном, на одних и тех же идентификаторах. Плюс текст отказа из мутации по критерию 8.

Числа тест-стека для ориентира: сидер с `PUBLIC_PERCENT=50` даёт 20 заметок, из них 10 публичных.
