# DOC-AUDIT-2. Документация против кода: полная сверка

Статус: **бэклог — Devin**, после UI-LOAD-1. Постановка — Claude Code, 2026-09-26, по просьбе
владельца.

**Решение владельца (2026-09-26, DOC-AUDIT-2):** провести полное ревью всей документации. Проверить
иерархию, а актуальность — прямо в коде. Из планов и постановок убрать сделанное и добавить
несделанное. Владелец понимает, что это дорого, и идёт на это сознательно.

## Почему

Документ `docs/architecture/FRONTEND_ARCHITECTURE_EN.md` четыре месяца описывал постепенную загрузку
графа из тумана. Владелец считал её сломанной, а её в коде не было. По истории git её потеряли:

- сделана 2026-04-15 (`d6b0658`) в старом 3D-модуле;
- удалена 2026-05-20 вместе с ним (`86e66d9`, «Clean up junk and obsolete files») — без решения и
  без правки документации;
- новый 3D-движок `features/graph-3d/` её не унаследовал.

Подробности — в постановке UI-LOAD-1 ([`UI-DESIGN-1-app-design-review.md`](UI-DESIGN-1-app-design-review.md)).

Прежние заходы такого не ловили. DOC-AUDIT-1 ([`DOC-AUDIT-1-documentation-inspection.md`](DOC-AUDIT-1-documentation-inspection.md))
сверял документы между собой и с индексом. DOC-REORG-1 разложил их по каталогам. Утверждения
документов с кодом не сверял никто.

Вне объёма — история, её не правят: `docs/archive/`, `docs/AI_LOG.md`, датированные записи,

отдельная задача [`SPEC-AUDIT-1`](SPEC-AUDIT-1-specs-vs-code.md) (решение 70). Исключение: если текущий документ ссылается на закрытую постановку как на
описание работающего поведения, это утверждение проверяется в составе того документа.

## Метод — на каждый документ

1. **Выписать проверяемые утверждения о текущей системе:** пути, функции, эндпоинты, ключи
   конфигурации, команды, значения по умолчанию, поведение. План и история — не утверждения о
   текущем. Но пометка «✅ Done» и слова «реализовано», «работает» — утверждения.
2. **Сверить каждое с кодом по норме «Verifying a Finding»** (`.windsurfrules`). Поиск находит
   кандидата, но не подтверждает. Поведение проверяется исполнением: тест, стенд, запрос. Чтения
   для этого мало.
3. **Вынести вердикт:**

   | Вердикт | Что делать |
   |---|---|
   | верно | ничего |
   | расхождение — код делает иначе | если поведение кода закреплено тестом или решением — править документ; иначе — владельцу |
   | **нет в коде** — описано, но отсутствует | по истории (`git log -S`) установить: не было никогда или было и удалено — коммит, дата, было ли решение. Молча не удалять: в тексте документа пометка «не реализовано — DOC-AUDIT-2, <дата>», в реестре — строка владельцу: делать или вычеркнуть |
   | устарело — в плане то, что уже сделано | перенести в сделанное со ссылкой на коммит или `CHANGELOG.md` |

   Ради класса «нет в коде» задача и затеяна. Решения по нему владелец принимает вместе с составом
   версии 1.0 ([`RELEASE-1`](../AI_HANDOFF.md)).
4. **Иерархия:**
   - у каждой темы один канонический документ;
   - копии (EN и RU, зеркала) совпадают с ним по фактам;
   - ссылки живые (`check-docs-links`);
   - каждый документ достижим из `docs/README.md`.

## Планы (этап B)

- **Убрать сделанное.** `docs/product/BACKLOG.md` сам говорит, что сделанное в нём не ведётся, а
  живёт в `CHANGELOG.md`.
- **Добавить несделанное:**
  - обещанное постановками, но не сделанное, — строкой в план или в бэклог доски;
  - «✅ Done» без кода — находка «нет в коде».
- **Постановки** — не здесь: их сверяет с кодом [`SPEC-AUDIT-1`](SPEC-AUDIT-1-specs-vs-code.md).

## Результат

- Реестр `docs/tasks/DOC-AUDIT-2-register.md`, раздел на каждый документ. Колонки: утверждение, где
  (файл:строка), вердикт, доказательство (файл:строка кода, команда и её вывод, коммит), действие.
- Отдельный список «нет в коде» — на решение владельцу, с историей по каждому пункту.
- Правки документов входят в те же коммиты, что и строки реестра о них.

## Критерии приёмки — на каждый этап

1. Реестр покрывает каждый документ этапа: число утверждений и вердиктов. Если утверждений о коде
   нет, стоит пометка «утверждений о коде нет».
2. Каждое «расхождение» и «нет в коде» — с доказательством, которое ревьюер может повторить.
3. Ревьюер проверяет выборку из 10 случайных вердиктов «верно». Хотя бы одно неподтверждённое
   возвращает этап.
4. Ни одно «нет в коде» не удалено молча: в тексте пометка, в списке владельцу — строка.
5. Сторожа зелёные: `check-docs-links`, `check-tasks-index`, `check-decisions`, `check-board-limits`.
6. Этап B: в планах нет «✅ Done» без кода, у сделанного есть ссылка, несделанное из постановок
   записано в план.

Этапы сдаются на ревью по одному, от A к D.

## Чего не делать

- Не реализовывать найденное «нет в коде» в этой задаче: только реестр и решение владельца.
  Исключение — UI-LOAD-1, она уже поставлена.
- Не менять норму. В `.windsurfrules`, скиллах и промптах правятся только факты: пути, команды,
  имена. Предложения по самим правилам — Claude Code.
- Не трогать историю (см. «Вне объёма»).
