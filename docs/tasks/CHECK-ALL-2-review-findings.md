# CHECK-ALL-2 — разбор ревью

Ревьюер: Claude Code. Дата: 2026-09-22. Реализация: Devin, `134a9e3`.
Источник задачи: наблюдение 2026-09-21 — `check-all` пропустил обе интеграционные фазы с
причиной «Docker daemon is unavailable» при девяти живых контейнерах.

**Вердикт: принято.** Причина названа верно (вывод `docker info` выбрасывался в `$null`, и
любой сбой читался как «демона нет»), исправление проверяемо, и — что важнее — на него
написан тест, который подделывает `docker` на `PATH`, а не верит настоящему демону.

## Проверено исполнением

| Что | Результат |
|---|---|
| `node --test scripts/testing/check-all-docker-skip.test.mjs` | зелёный: 4 случая — `ps1` и `sh` × (падающая заглушка → SKIP с текстом, здоровая заглушка → фаза выполняется) |
| **Мутация**: причина пропуска возвращена к `'Docker daemon is unavailable'` | **FAIL** — «ps1: failing docker stub -> SKIP naming command and output». Тест смотрит на содержание причины, а не на факт пропуска |
| Тестовый крючок `-Manifest`/`--manifest` | одна фаза из фикстуры вместо полного манифеста; сверка манифеста с CI при этом пропускается — она про настоящий манифест, и это оговорено в коде |
| Синхронизация фаз | `check-core-workflow-sync` — «28 local phases match 28 CI steps»; `docker-skip-test` есть и в `core-checks.tsv`, и в `_core-checks.yml` |
| Поведение на живом демоне | `check-all` 2026-09-22 с поднятым стеком: обе интеграционные фазы **выполнились**, не пропущены |

Повтор `docker info` один раз через 3 секунды — правильная реакция на ту ситуацию: 21.09
демон был жив, но отвечал под нагрузкой (шли сборки образов). Теперь причина пропуска несёт
код выхода и три последние строки вывода — по ним видно, чем именно ответил демон.

## Мелочи

1. Хвост вывода режется по 300 символов и склеивается через ` | ` — для типичной ошибки
   («cannot connect…») этого хватает, для многострочной трассы Windows-клиента может обрезать
   самое полезное. Не блокер: полный вывод всё равно оседает в логе фазы.
2. Тест подделывает `docker` на `PATH` и потому проверяет ровно то, что нужно, но обе
   «здоровые» ветки считают фазу выполненной по коду выхода — если однажды фаза начнёт
   падать по своей причине, тест этого не отличит. Достаточно для задачи, назвал для порядка.

## Принято без замечаний

- Исправлены оба раннера, `ps1` и `sh`, а не только тот, которым пользуюсь я.
- Тест не зависит от состояния настоящего Docker — его можно гонять в CI, где демона нет.
- Фаза `docker-skip-test` заведена в манифест и в CI одновременно, сверка зелёная.
