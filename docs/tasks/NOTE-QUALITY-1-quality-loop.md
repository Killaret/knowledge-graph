## Постановка этапа 1 — система без весов (Claude Code, 2026-09-26)

### Что показал корпус владельца

Считал только числа по `work-nlp4/notes_dataset.json` (108 заметок, локально, вне git);
названия и тексты не печатались.

- 97 заметок пришли импортом по ссылке: первая строка `## [title](url)`.
- Объём двугорбый: p25 = 18 слов, p50 = 377. У 40 заметок меньше 30 слов, 8 из них — голая ссылка.
- **39 заметок упёрлись в старый лимит импорта**: тело после первой строки ≥ 4 990 рун
  (`import_fetcher.go:19`, `maxTextRunes = 5000`). 37 из них оборваны на полуслове: треть корпуса
  «неоконченна» из-за нас, а не из-за автора.
- Подборок ссылок в корпусе нет. Из 10 заметок, где доля слов в предложениях меньше 0,3, восемь —
  голые ссылки, две — заголовок без текста. У 9 заметок нет ни одного предложения из четырёх и более
  слов. (Первая версия этой постановки ошибочно называла эти 10 заметок подборками.)

### Три части, по порядку

1. **URL-HEADING-1, этап A** — по его постановке целиком (разделы A1–A6, критерии 1–7). Новые
   импорты перестают обрезаться на 5 000 рунах и сохраняют структуру страницы. Дополнение для этой
   задачи: при обрезке по бюджету импорт пишет `metadata.import_truncated = {"sections_dropped": N}`,
   то есть точный признак вместо догадки по длине. От NLP-4 не зависит, поэтому идёт первой.
2. **Сигналы и отсечки** — этот раздел. Делается после NLP-4: берёт его очищенный текст, чанки
   CHUNK-1 и документ `nlp_artifacts` в Mongo.
3. **Перезабор старых обрезанных заметок** — действие пользователя с превью и подтверждением
   (подраздел «Индикатор и действия»). Делается после части 1: перезабор идёт новым извлечением.

### Сигналы

| Измерение | Сигнал | Как считается |
|---|---|---|
| объём | `words` | слова без адресов и разметки ссылок, в очищенном тексте NLP-4 (при выключенном NLP-4 — в исходном) |
| | `prose_words` | слова в строках-предложениях: не заголовок, не пункт списка, не строка из одной ссылки |
| оконченность | `ends_with_sentence` | последняя непустая строка кончается `.`, `!`, `?`, `…` или закрывающей разметкой |
| | `truncated_by_import` | `metadata.import_truncated` у новых импортов; у старых — тело после первой строки ≥ 4 990 рун |
| | `unclosed_fence` | нечётное число ``` ``` ``` |
| структура | `headings` | заголовки, кроме первой строки импорта |
| логичность | `coherence_min`, `coherence_median` | косинус соседних чанков CHUNK-1 текущей моделью; `null`, если чанков меньше двух |
| присутствие мысли | `sentences` | предложения из четырёх и более слов в прозе |
| | `prose_share` | `prose_words / words` |
| | `kind` | `stub` — единственная строка-ссылка; `collection` — `prose_share < 0,3` и не меньше трёх строк-ссылок или пунктов; иначе `text` |
| готовность | `keywords`, `links`, `has_embedding` | из базы: сколько ключевых слов, сколько связей (ручных и автосвязей), есть ли вектор (соображения 17.09) |
| кодировка | `mojibake` | доля символов замены `�` и типичных кракозябр (`Ð`, `Ã` в кириллическом тексте) больше 1 % |

Числа в таблице (0,3; четыре слова; 1 %; 4 990) — границы признаков, а не веса меры. Они вынесены
в конфиг `nlp.quality.*` и пересматриваются на этапе 2 вместе с весами. Шкала `coherence_*` зависит
от модели: после смены модели в MODEL-2 её граница калибруется заново.

### Отсечки — единственные решения этапа 1

Формат решения — тот, что уйдёт в контракт с Java: `verdict ∈ {create, enrich, manual}` плюс
`reasons[]`.

| Отсечка | Условие | `verdict` | Что видит пользователь |
|---|---|---|---|
| `stub` | `kind = stub` | `enrich` | «только ссылка»; «перезабрать», если есть `source_url` |
| `truncated` | `truncated_by_import` | `enrich` | «обрезана при импорте»; «перезабрать» |
| `empty` | нет ни текста, ни `source_url` | `manual` | «пустая» |
| `mojibake` | `mojibake` | `manual` | «битая кодировка» |

Всё остальное — `create` без балла: сигналы записаны, судить по ним будет этап 2. **Этап 1 ничего
не блокирует и ничего не меняет в заметке**: создание, ключевые слова, векторы и автосвязи идут
как сейчас; `enrich` и `manual` — только индикатор и предложение действия.

### Цикл и правило остановки

- Оценка (`quality:assess`) ставится после `nlp:normalize` и повторно — когда завершается любая из
  задач обогащения заметки (ключевые слова, вектор, автосвязи). Кнопка «доработать» и метка
  «требует доработки» ставят её вручную.
- **Остановка:** если сигналы не изменились с прошлой оценки той же версии текста (`source_hash`),
  новая оценка не ставится. Больше трёх автоматических оценок на одну версию текста не бывает;
  если отсечка держится после третьей — флаг `needs_manual_review`.
- **Сети нет.** Задача оценки не обращается к загрузчику страниц — решение владельца 13.09.
  Перезабор делает только пользователь (ниже).

### Хранение, лог, API

- Документ NLP-4 `nlp_artifacts` той же версии текста получает поле
  `quality: {signals, gates, verdict, reasons, attempt, computed_at, pipeline_version: "quality-v1"}`.
- Лог — коллекция `quality_log`: каждая оценка (заметка, `source_hash`, триггер, сигналы, отсечки,
  что изменилось относительно прошлой оценки). Хранится последние 10 записей на заметку.
- `GET /api/v1/notes/{id}/quality` — последняя оценка и лог; права — как на чтение заметки;
  `openAPI.yaml` вместе с кодом.
- Выключатель `nlp.quality.enabled` (env → конфиг), по умолчанию **`false`**: задача не ставится,
  API отвечает `{"enabled": false}`.

### Индикатор и действия

- **Панель заметки:** строка «Качество» — «в порядке», «только ссылка», «обрезана при импорте»,
  «пустая» или «битая кодировка» — и по наведению сигналы, из-за которых так. Балла нет: он
  появится на этапе 2.
- **«Доработать»** — пересчитать оценку, без сети.
- **«Перезабрать»** (часть 3) — для `stub` и `truncated` с `source_url`. Пользователь жмёт →
  превью новой версии через извлечение этапа A (длина, оглавление, выбранное название) → «заменить»
  с подтверждением. Прежний текст сохраняется в `metadata.previous_content`, действие «вернуть как
  было» откатывает замену: предлагать, не навязывать, откат по желанию — решение владельца 13.09.

## Материал обсуждения 13–21.09

**2026-09-13 — обсуждение.** Постановка от владельца: нужен pipeline, который после создания/импорта заметки проверяет, нормализует и обогащает её до тех пор, пока она не соответствует критериям качественных данных. Критерии ещё не определены. Предварительные решения владельца зафиксированы ниже.

## Цель

Заметки, особенно импортированные из закладок/ссылок (`dust`), должны проходить контролируемый цикл обработки **до** того, как их увидит пользователь и до того, как запустятся текущие фоновые задачи (`ExtractKeywords`, `ComputeEmbedding`, `RecalculateLinkWeights`, `RefreshRecommendations`).

Pipeline должен:
- проверять структурную и семантическую корректность заметки;
- нормализовать title, content, metadata, `source_url`, type;
- обогащать (до тех пор, пока не исчерпаны возможности);
- сообщать пользователю о дубликатах/битых ссылках/низком качестве;
- не удалять и не принудительно объединять без согласия пользователя;
- писать всё, что сделал, в лог.

## Решения владельца (2026-09-13)

- **Без cron.** Обогащение — синхронная/очередная задача при создании/импорте и по ручной кнопке пользователя "доработать заметку".
- **Пользователь может поставить метку** на заметку, и она уходит на ту же лупу обработки.
- **Переклассификация допустима** (`dust` → `star`/`planet` и т.д.), но под контролем пользователя.
- **Связи/дубликаты**: не удалять, не объединять автоматически; предлагать пользователю, если хочет — откат.
- **Ссылки**: не ходить по сети. Проверять только синтаксическую валидность; битые помечаем, но не делаем ничего.
- **Всё пишем в лог**: какие критерии не прошли, какие изменения были предложены/применены.

## Главный открытый вопрос: критерии качества

Без определения "хороших данных" pipeline не знает, когда остановиться. Нужна система динамических весов и коэффициентов, по которым вычисляется **quality score** заметки.

### Предварительные критерии

1. **Структурные**:
   - `title` не пустой, в лимите, без мусора.
   - `content` не пустой или есть `source_url`.
   - `type` валиден, соответствует содержимому.
   - `source_url` синтаксически корректен (если есть).

2. **Семантические**:
   - Ключевые слова извлечены.
   - Эмбеддинг посчитан.
   - Нет дубликатов по `source_url` или embedding-близости.
   - Есть смысловой "вес" — не менее N слов или есть ссылка/цитата.

3. **Связностные**:
   - Есть рекомендации/связи, либо явно помечена как singleton.
   - Нет orphaned links.

4. **Пользовательские**:
   - Не помечена "требует доработки".
   - Не стоит в статусе `dust`/`debris` бесконечно.

### Идея шкалы качества

| Уровень | Диапазон | Что означает |
|---------|----------|--------------|
| `low` / низкое | 0.0 – 0.4 | Структурно сломано: пустой title, невалидный type, битая ссылка, дубликат. Требуется ручная обработка или повторный цикл. |
| `medium` / среднее | 0.4 – 0.7 | Есть данные, но маловато: нет keywords/embedding, мало контента, type не уверен (`dust`). Идёт на повторный проход. |
| `high` / высокое | 0.7 – 1.0 | Структура, семантика и связи на месте. Можно запускать `ExtractKeywords`/`ComputeEmbedding`/`RefreshRecommendations` и показывать пользователю. |

Коэффициенты можно делать динамическими: за каждый пройденный критерий начисляется вес, за критический дефект (`title` пустой, `type` невалиден) — штраф, который невозможно компенсировать другими баллами.

## Вариант stopping criteria

- **По достижению уровня `high`.**
- **По исчерпанию возможностей**: за итерацию ничего не изменилось (не добавились keywords, не сдвинулся type, не появились связи).
- **По лимиту попыток**: максимум 3 итерации с нарастающими задержками (30 сек, 5 мин, 1 час). После третьей — `needs_manual_review`.

## Предлагаемый pipeline (первый вариант)

```
Создание / импорт / ручная кнопка / метка "доработать"
        │
        ▼
┌──────────────────────────────┐
│ 1. Структурная проверка      │
│    (title, content, type,    │
│     source_url)              │
└──────────────────────────────┘
        │
        ▼
┌──────────────────────────────┐
│ 2. Нормализация              │
│    (trim, dedup, type infer, │
│     url parse)               │
└──────────────────────────────┘
        │
        ▼
┌──────────────────────────────┐
│ 3. Quality score             │
│    (динамические веса)       │
└──────────────────────────────┘
        │
        ▼
  quality >= high? ──YES──► запускаем ExtractKeywords / ComputeEmbedding / RecalculateLinkWeights / RefreshRecommendations
        │ NO
        ▼
┌──────────────────────────────┐
│ 4. Обогащение                │
│    (title infer, dedup hint, │
│     type suggestion)         │
└──────────────────────────────┘
        │
        ▼
  итерации исчерпаны? ──YES──► needs_manual_review
        │ NO
        └───────► ещё один проход (с задержкой)
```

## Что не входит (явно)

- Автоматическое удаление/объединение заметок.
- Cron-обход всех заметок (до решения владельца).

## Дальнейшие соображения владельца (2026-09-14)

- **Quality / health — видимая фича, а не внутренняя метрика.** Расчёт `quality_score` должен давать пользователю понятный индикатор «заметка хорошая / средняя / плохая», а также агрегированный health библиотеки или кластера. Это можно связать со «стражами» (`/health`, status checks), о которых говорил владелец.
- **Векторное сравнение title.** Доменная модель `Note` хранит `title` и `type`, но не вектор. Поиск дубликатов и оценка качества title должны быть на уровне прикладного/инфраструктурного сервиса, который вызывает NLP-эмбеддинги. Домен не знает про эмбеддинги.
- **Дубликаты — не автоматическое объединение.** Pipeline находит семантически близкие заметки (по title vector, content vector, source_url) и выделяет их для пользователя. Пользователь решает, что делать: объединить, откатить, оставить связь, отправить на доработку. Сами близкие заметки могут отображаться с маркером/группировкой.
- **Title-кандидаты и сравнение.** При импорте/обогащении `source_url` у нас будет несколько кандидатов в title (`<title>`, `h1`, `h2`, fallback URL). Качество title = семантическая близость к content и удалённость от шаблонных фраз. Это может быть отдельный критерий `NOTE-QUALITY`.
- **Структурные дивиденды заголовков.** Если `h2`/`h3` дают чёткую иерархию, качество content выше. Если текст сплошной монолит — ниже. Веса в `quality_score` должны учитывать наличие outline.
- **NLP-модуль в pipeline.** NLP не только keywords/embedding, но и оценка title, summary, дубликатов, relatedness. Это расширяет границы `NOTE-QUALITY-1` и `URL-HEADING-1`.

## Дальнейшие соображения владельца (2026-09-17)

Записано по обсуждению формулы рекомендаций (RECO-1) и замены экстрактора (NLP-2).

- **Отсутствие связей и отсутствие ключевых слов — сигналы качества, а не только следствия.**
  Проверка «у заметки нет связей» и «у заметки нет ключевых слов» нужна независимо от того,
  появятся ли автосвязи (RECO-1, п. 3): автосвязи — способ добавить связи, а не способ узнать,
  что заметка в порядке.
- **Нет ключевых слов → скорее всего, качество хромает.** Не «экстрактор не сработал», а
  «в заметке нечего извлекать». Такую заметку надо **дообогащать** — до порога по мере качества.
- **Мера качества — контракт с Java-сервисом.** `source-text-handler` по ней решает: делать
  заметку самому или **вернуть сырые данные через очередь** на дообработку. Это связывает три
  открытых вопроса в один: критерии и веса (эта задача), как Java создаёт заметки (IMP-4-JAVA)
  и как он свяжет заметки без UUID (BATCH-DESIGN-1). Без меры качества ни один из трёх не
  закрывается.
- **Веса меры ещё не разработаны** — и это блокер для всех трёх задач сразу, а не только для
  этой. Следующий шаг: Claude Code готовит конкретную таблицу критериев с числами как
  предмет для правки владельцем, а не как готовый ответ.

Из RECO-1 в эту задачу переходит наблюдение: `JaccardSimilarity` считает две заметки **без
ключевых слов полностью похожими** (1.0 при двух пустых наборах). С точки зрения качества
это ровно наоборот — две пустые заметки не похожи, они обе не готовы.

## Дальнейшие соображения владельца (2026-09-21, вечер)

- **Что измеряем.** Мера качества — это мера весов по четырём измерениям того, что пришло на
  вход: **объём данных**, **оконченность** (текст завершён, а не оборван), **логичность**
  (связность), **присутствие мысли** (есть ли в тексте утверждение, а не только перечисление).
  Это прямое уточнение решения 42: по этой мере Java-сервис `source-text-handler` решает,
  создавать заметку или вернуть сырые данные в очередь.
- **Чья постановка.** Постановка пишется для Java-сервиса, но куски — от нас: критерии и
  числа рождаются здесь, в этой задаче; Java получает контракт.
- **Вместе с URL-HEADING-1.** Извлечение данных из страниц (заголовки, структура, шум) —
  часть той же цепочки: чем лучше вытащено, тем меньше потом обрабатывать. Обе постановки
  обсуждаются в одном разговоре; владелец назначит, когда. До этого таблица критериев
  (следующий шаг из соображений 17.09) не пишется вслепую — она предмет того разговора.
