## Цель

Импортированная по URL заметка получает **название, которое дал бы странице человек**, и
**содержимое, сохраняющее структуру документа** — вместо сайтового `<title>` с суффиксом
(`JSON Web Tokens - jwt.io`) и плоского `innerText`, обрезанного на 5 000 рунах
(`import_fetcher.go:19`, `maxTextRunes`).

Что должно измениться для пользователя: в превью импорта он видит выбранное название,
остальных кандидатов и оглавление страницы; в заметке — разделы с заголовками, списки и код
как в источнике, а не одну простыню.

## Границы

- **Входит:** всё, что идёт через `ImportFetcher.Extract` — превью и импорт закладок
  (`POST /api/v1/import/bookmarks/preview`, `POST /api/v1/import/bookmarks`), букмарклет.
- **Не входит:** обогащение уже существующих заметок с `source_url` (вопрос 7 черновика) —
  это цикл NOTE-QUALITY-1; дедупликация по содержимому (вывод 8 пробы) — задача W-1/RECO-1,
  здесь только `is_new` по URL, как сейчас; чанкование и «логическая форма» — NLP-4.
- **Ограничения остаются:** тело ≤ 1 МиБ, только `http(s)`, приватные адреса отвергаются
  (`IsAllowedURL`), `title` ≤ 200 рун, `content` ≤ 50 000 рун, рунная обрезка.

## Этап A — детерминированное извлечение, без модели

Делается первым и принимается отдельно: не зависит от MODEL-1, полезен сам по себе.

### A1. Контейнер содержимого

Первый найденный: `<main>` → `<article>` → `[role=main]` → предок с `id`/`class` из списка
`content|page-content|post-content|entry-content|markdown-body|mw-parser-output|documentation|article`
→ `<body>`. Список — константа в коде с комментарием, какая страница пробы каждый пункт
оправдала (проба, вывод 6: Confluence, Keycloak, jsonformatter без `<main>`/`<article>`).

### A2. Шум

Внутри контейнера вырезаются поддеревья: `nav aside footer form script style noscript template
iframe svg`, `[role=navigation|complementary|banner|contentinfo]`, `[aria-hidden=true]`,
и элементы с `id`/`class`, совпадающими с
`promo|subscribe|newsletter|related|sidebar|rail|popular|comments?|share|social|breadcrumb|cookie|banner|advert|\bads?\b`
(проба, вывод 5: рекламные `h2` внутри `<main>` у Практикума, Skillbox, Coursera).

`<header>` — прямой потомок `<body>` — шум; `header` внутри контейнера **сохраняется**
(проба, вывод 3: у Википедии и Atlassian `h1` лежит в `header`-подобном блоке статьи).

Вырезанное не пропадает: см. решение 3.

### A3. Оглавление и Markdown

Обход контейнера после чистки. `h1`–`h6` → `Heading{Level, Text}`; блоки между заголовками:

| Источник | Markdown |
|---|---|
| `p`, текстовые узлы | абзац |
| `ul`/`ol`, вложенные | `- ` / `1. `, вложенность отступом |
| `pre`, `code` блочный | огороженный блок ``` ``` ``` |
| `table` | таблица `\|` при ≤ 6 колонках, иначе строки как абзацы |
| `blockquote` | `> ` |
| `strong`/`b`, `em`/`i`, строчный `code` | `**`, `*`, `` ` `` — соображение владельца о типографике |
| `a` | только текст; ссылки внутри содержимого не сохраняются (адрес источника уже в первой строке) |
| `img`, `video`, `figure` | пропуск |

Уровни нормализуются: первый заголовок в оглавлении становится `##` (первую строку `## [title](url)`
строит `BuildContent`, как сейчас), остальные — относительно него, глубже `######` не бывает.

### A4. Бюджет и обрезка

`maxTextRunes` = 5 000 заменяется на бюджет **по разделам**: раздел добавляется целиком, если
входит; если нет — обрезка происходит на границе абзаца, никогда внутри списка или кодового
блока (непарные ``` ``` ``` — дефект); в конце дописывается строка `_(обрезано: N разделов не
вошли)_`. Размер бюджета — настройка `IMPORT_CONTENT_MAX_RUNES`, по умолчанию **20 000**:
предел заметки 50 000; эмбеддинг до NLP-4 всё равно видит только начало (128 токенов), так что
больше — не лучше для поиска, а для чтения 20 000 рун — примерно семь экранов. Цифра для
владельца: посмотреть в превью и утвердить или сдвинуть.

### A5. Кандидаты в название и выбор по правилу

Кандидаты, по порядку:

1. `h1` внутри контейнера, в порядке документа (все, не только первый);
2. `og:title`;
3. `<title>` после отрезания сайтового суффикса: разбить по ` — `, ` – `, ` - `, ` | `, ` · `,
   ` : `; последний сегмент отбросить, если он совпадает (без учёта регистра) с `og:site_name`,
   `application-name` или доменной меткой без TLD (`jwt`, `skillbox`, `mozilla`). Проба,
   вывод 1: суффикс почти на каждой странице;
4. последний сегмент пути URL, очищенный (`-`/`_` → пробел) — крайний случай.

Правило этапа A: первый кандидат из списка длиной от 3 до 200 рун, не равный имени сайта.
Все кандидаты (≤ 5) отдаются в превью как `title_candidates` и сохраняются в
`metadata.title_candidates`, источник выбора — `metadata.title_source = "rule"`.

### A6. Контракт превью

`PreviewItem` (`application/import/service.go:53`) расширяется полями:
`title_candidates []string`, `outline []{level, text}`, `noise_dropped int`, `title_source string`.
`openAPI.yaml` — вместе с кодом (`TestRouterMatchesOpenAPISpec` это охраняет). Фронтенд
(`routes/import/bookmarks/+page.svelte`): у элемента превью — выпадающий список кандидатов и
свёрнутое оглавление; выбор пользователя уходит в импорт как `title`, как сейчас уходит
правка названия руками.

Ошибки загрузки (401/403/404/таймаут) — без изменений: путь «только заголовок» из IMP-7,
`metadata.fetch_status` с кодом.

## Этап B — выбор названия моделью (после MODEL-1)

Соображение владельца 14.09: «нельзя выбирать title одним правилом, нужен векторный сравнитель».

- NLP-сервис: `POST /rank_titles` `{candidates: [...], text: "...", site_name: "..."}` →
  `[{candidate, score}]`, `score = cos(e(candidate), e(text_head)) − λ·cos(e(candidate), e(site_name))`,
  где `text_head` — начало содержимого (первые 512 токенов; после NLP-4 — среднее по чанкам).
  Второе слагаемое штрафует «сайтовые» кандидаты (`Home`, имя сайта, `Меню`).
- Бэкенд вызывает его **только в превью**: пользователь видит выбор. Модель переопределяет
  правило этапа A, только если лучший `score ≥ τ`; иначе остаётся выбор по правилу.
  `metadata.title_source = "model"` с `score`. NLP недоступен → этап A, `"rule"`, без ошибки.
- `λ` и `τ` калибруются на золотом наборе (ниже) **после MODEL-1**: смена модели меняет шкалу
  косинусов, калибровать дважды бессмысленно (решение 41). До этого этап B в коде за флагом
  `IMPORT_TITLE_RANKER=off`.

## Три вопроса — предложения внутри общей картины

1. **Несколько `h1`.** Первый в контейнере — кандидат № 1, остальные — тоже кандидаты, **не
   склеивать**: склейка даёт название, которого никто не писал. Проба: первый в `main` верен
   на 15 из 19 доступных страниц; остальные четыре — как раз случаи для этапа B.
2. **`<title>` — fallback или всегда кандидат.** Всегда кандидат (после отрезания суффикса):
   на этапе A он третий по правилу, на этапе B модель ранжирует всех. Так этап A работает
   без модели, а этап B ничего не ломает — только переставляет.
3. **Заголовки из `nav`/`aside`/`footer`.** Из названия и оглавления — вон; их **ссылки**
   (текст + `href`, ≤ 20) — в `metadata.related_links`. `Note.Metadata` — свободная карта
   (`domain/note/value_objects.go:47`), схемы это не трогает; потребителя пока нет (кандидат —
   NOTE-QUALITY-1: оглавление сайта и «похожие статьи» как сигнал качества), поэтому хранить,
   не показывать. Владелец 14.09 склонялся к «сохранять» — это оно.

### Дальнейшие соображения владельца (2026-09-14)

- **Разделение тем по уровню.** Если заголовки на одном уровне разделены вставкой структуры низшего уровня, это, скорее всего, разные темы. Низший уровень (списки, пунктуация, вложенные предложения) раскрывает одну мысль, а не смешивает с соседним заголовком.
- **Связность внутри ветки.** Текст под `h2`/`h3` должен быть связан с родительским заголовком: мысль раскрывается, повторяется в других словах, ссылается. Это можно использовать при вычислении `quality_score` и при поиске дубликатов.
- **Текстовая структура и шрифты.** Параграфы обычно имеют однородную типографику. Курсив/жирный/блоки кода внутри текста могут указывать на особое назначение (цитаты, термины, примеры). При превращении в Markdown стоит сохранять `**жирный**`, `*курсив*`, `` `код` ``.
- **`<title>` vs `h1` — нужен векторный сравнитель.** Нельзя выбирать title одним правилом. Надо:
  1. Получить кандидатов: `<title>`, `h1` (фильтр `nav`/`aside`/`footer`/`header`), `h2` (если `h1` нет или плохой).
  2. Привести каждого к эмбеддингу.
  3. Сравнить с эмбеддингом всего текста и, возможно, с уже известными заметками (дубликаты).
  4. Выбрать кандидата с наибольшей семантической близостью к контенту и наименьшей близостью к шаблонным фразам (`Home`, `Menu`, site name).
- **Векторные дубликаты title.** В доменной модели пока хранится только `title` и `type`. Для поиска дубликатов нужно сравнивать не по точному совпадению `title`, а по векторной близости. Векторное произведение — **не часть доменной модели**, его должна вычислять инфраструктурная/прикладная служба (NLP, embeddings, similarity). Домен знает `title` и `noteType`, но решение «это дубликат» принимает прикладной сервис на основе внешнего score.
- **`<main>`, `<article>` и классы `main`/`content`/`article`.** В современной вёрстке основной контент обычно лежит в `<main>` или `<article>`, либо в `div` с классом/id `main`, `content`, `article`. Заголовки внутри этих контейнеров имеют более высокий приоритет. Сайтовый `header`/`nav`/`aside`/`footer` часто находятся в других grid/контейнерах.
- **Мусорные разделы в другом grid.** В многоколоночных layout мусорные блоки (списки ссылок, реклама, related, comments) обычно лежат в отдельных `div`/`grid`, а не в главном content-гриде. Это дополнительный признак, помимо самих тегов.
- **Title — бизнес-атрибут, vector — технический.** `title` должен оставаться в домене, векторная близость — в инфраструктуре/приложении. Сравнение кандидатов в title и поиск дубликатов идёт через NLP/эмбеддинги, но сама `Note` не хранит вектор.
- **Header/footer/sidebar — не всегда мусор.** Там может быть дополнительная информация (связанные статьи, оглавление, автор). Сначала фильтруем их из outline/title, но сохраняем как дополнительный `metadata`/`related_links` для дальнейшей обработки.
- **Health/quality как отдельная фича.** После извлечения структуры заметки нужно считать меру качества: насколько title соответствует content, насколько контент структурирован, есть ли дубли, битые ссылки. Это можно привязать к существующим «стражам» (`/health`, `NOTE-QUALITY-1`) и сделать видимым health-индикатором у библиотеки/кластера.

### Результаты пробного прогона (2026-09-14)

Devin прогнал временный Go-прототип на 22 URL из `bookmarks_11.09.2026.html` (5 tech_doc, 5 course, 5 russian, 7 complex). Полный отчёт с таблицей, outline и детальным разбором по страницам: [`URL-HEADING-1-findings-probe.md`](URL-HEADING-1-findings-probe.md).

#### Главные выводы

1. **`<title>` обычно требует чистки.** Сайтовые суффиксы (`— Википедия`, `- jwt.io`, `| OneLogin Developers`, `- Изучение веб-разработки | MDN`) встречаются почти на каждой странице. Суффикс лучше отрезать до сравнения кандидатов.
2. **`h1` внутри `<main>`/`<article>` — лучший кандидат в `title`.** Пример: `<title>` `JSON Web Tokens - jwt.io`, а `h1` — `JSON Web Token (JWT) Debugger`; `<title>` `Chrome DevTools: ... / Skillbox Media`, а `h1` — `Chrome DevTools: основные инструменты и полезные функции`.
3. **Не весь `<header>` — мусор.** В Википедии/Atlassian основной `h1` лежит внутри `header`-подобного контейнера (`mw-body-header`); слепой skip `header` удаляет title. Надо различать страничный `header` (под `<body>`) и заголовочный блок статьи.
4. **`h2`/`h3` дают надёжный outline.** Техдоки (Keycloak, OneLogin, OpenID specs), MDN, The API Book, Stepik, курсы и русскоязычные статьи (Habr, Yandex, Skillbox) строят чёткую иерархию.
5. **Шум — не только в `<footer>`/`<aside>`.** Promotional h2 (`Курс с помощью в трудоустройстве`, `Новости`, `Спасибо за подписку!`) всплывают внутри `<main>`/`<article>` у Yandex Practicum, Skillbox, Coursera. Требуется фильтрация по классам/id (`promo`, `subscribe`, `news`, `related`, `course-promo`, `sidebar`, `rail`, `popular`).
6. **`<main>`/`<article>` есть далеко не везде.** Atlassian Confluence, Keycloak docs, jsonformatter.org, JSON specs не используют `<main>`/`<article>`; заголовки лежат в `div`/`section`/`table`. Fallback на ancestor-классы (`content`, `page-content`, `mw-parser-output`, `documentation`, `post-content`) необходим.
7. **Курсы и маркетплейсы — самый грязный контент.** Страницы Stepik, Coursera, Karpov, Skillbox, Litres перемешивают программу, отзывы, цены, похожие курсы, формы подписки. Outline работает, но много шума.
8. **Дубликаты по title-строке — слишком агрессивны.** `Auth Code Flow + PKCE` и `Auth Code Flow pt. 2` схлопываются в одну группу. Для duplicate review нужен контентный вектор и настраиваемый порог, а не строковая метрика.
9. **Авторизация/битые ссылки.** `web.postman.co` и `web.postman.co/workspace/...` возвращают 401; `docs.id.itmo.pro/...` — 404. Нужен graceful fallback: если страница недоступна, помечать `source_url` как «не удалось загрузить» и не падать на всём батче.
10. **Кириллица парсится корректно.** `golang.org/x/net/html/charset` распознаёт `windows-1251` закладочного файла и сайты. Русскоязычные h1/h2 извлекаются и нормализуются так же, как английские.

#### Что пока не работает / требует решения

- **Выбор `title` без NLP.** Сейчас прототип выбирает `h1` в `<main>`/`<article>`, иначе `h1`, иначе `<title>`. Для страниц без `h1` в main и с длинным `<title>` (спецификации, маркетплейсы) всё ещё требуется бизнес-логика выбора.
- **Очистка `<title>` от сайтовых суффиксов.** Нужен более устойчивый способ, чем жёсткий список: извлекать домен, сравнивать конец title с брендовым паттерном или обучать шаблоны на частых суффиксах.
- **Фильтрация шума по layout.** Мы не используем CSS/grid напрямую; приходится опираться на class/id и ancestor-теги. Без движка layout-анализа это лучший доступный сигнал.
- **Группировка и дедупликация.** Сейчас только title-level Jaccard. Контентный embedding, source_url и сравнение с уже импортированными заметками — отдельная задача, за пределами доменной модели.
