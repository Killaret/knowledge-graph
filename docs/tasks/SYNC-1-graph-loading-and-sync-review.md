# SYNC-1. Загрузка и синхронизация графа: разбор постановки владельца

Статус: **в работе — Devin, этап A реализован, ждёт ревью Claude Code.** Разбор — Claude Code,
2026-09-26, по просьбе владельца; дыры подтверждены на живом стенде.

**Решение владельца (2026-09-26, SYNC-1):** синхронизация графа чинится в 1.0 отдельной задачей, до
3D-части UI-LOAD-1. В 1.0 входит и доставка изменений через SSE, как записано в ADR 014; опрос
остаётся запасным путём.

## Замысел

Слова владельца (2026-09-26): с графом можно работать, пока он грузится. Если данные меняются, граф
подменяется на лету. Дельта, кеши и их сброс сделаны ради удобства пользователя.

Где замысел записан:

- `docs/architecture/ARCHITECTURE_EN.md`, раздел «Redis and Private Graph Cache»:
  - `/me/graph/cached` сразу отдаёт граф из кеша;
  - `/me/graph/fresh` считает свежий граф и может вернуть дельту;
  - фронтенд показывает граф мгновенно и обновляет холст плавно, без полной перерисовки.
- `docs/architecture/decisions/014-event-driven-cache-invalidation.md`:
  - изменение публикуется в Redis, graph-service сбрасывает кеш;
  - **фронтенд подписан через SSE или WebSocket и получает изменения сам**.
- `docs/product/BACKLOG.md`, «Graph API unification»: `PreloadService.seedGraph`, дельта по `last_hash`.
  В планах там же — потоковая выдача большого графа: узлы рисуются по мере прихода.
- `docs/architecture/FRONTEND_ARCHITECTURE_EN.md`, «Progressive Rendering (Fog of War)» — граф
  проявляется из тумана по мере загрузки. Это UI-LOAD-1: 2D-часть Devin сдал в `c938609`, она ждёт
  ревью.

**Условия проверки:**
- стенд из этой ветки, `SKIP_AUTH=false`, каждый прогон под новым одноразовым пользователем;
- граф — через тот же путь, что у фронтенда (`/graph-service/api/v1`);
- события считаются по логу graph-service только для этого пользователя.

С `SKIP_AUTH=true` проверять нельзя: graph-service кеширует граф под пустым пользователем, а события
приходят с настоящим id, и результат был бы артефактом стенда.

## Оценка постановки — Claude Code, 2026-09-26

**Ценность — да.** Связи — главная ценность продукта, а появляются они асинхронно: автосвязи воркер
создаёт через секунды после записи. Без живого обновления пользователь не видит, как «полочка»
раскладывается сама, — а это и отличает её от блокнота. Постепенная загрузка при сотнях заметок —
прежде всего вопрос восприятия. По-настоящему она понадобится на тысячах узлов и в 3D, где раскладка
тяжёлая: по комментарию в `engine.ts`, синхронный досчёт на 500 узлах занимает до секунды.

**Реализуемость — да, и большая часть деталей уже есть:** кеш, события, сброс, дельта, предзагрузка,
применение дельты в 2D. Не хватило не идей, а контракта. Без этих четырёх правил детали не
складываются в работающее целое:

1. дельта считается от версии клиента, а если сервер её не помнит — клиент перезагружается целиком;
2. каждый путь записи публикует событие, и есть проверка, которая ловит новый путь без события;
3. удаления передаются явно, и клиент их применяет;
4. версия графа считается от данных, а не от раскладки. Сейчас хеш берётся от всей раскладки вместе
   с позициями, а заметки и связи читаются без `ORDER BY` — версия может смениться без изменения
   данных.

**Как спроектирована работа.** Сильная сторона: замысел записан с причинами и разобранными
альтернативами — ADR 014 редкость для проекта одного человека. Слабые стороны:

- замысел разнесён по четырём документам, контракта с правилами нет ни в одном;
- нет сквозного теста на обещание пользователю «изменил — граф сошёлся». Каждая деталь проходила
  свои тесты, а целое не работало ни разу;
- пункты ADR не превратились в задачи. SSE так и остался рисунком: решение без задачи на доске не
  делается;
- поведение, не закреплённое тестом, потерялось при переписывании (3D, май);
- механизм рассчитан на масштаб, которого нет (потоковая выдача, gRPC, серверная раскладка), а
  базовая корректность — удаления — не проверялась.

**Рекомендация.** Для 1.0 — оставить нынешний механизм и закрыть четыре правила: этапы A–C ниже.
Если появятся несколько устройств или пользователей — перейти на синхронизацию по номеру ревизии.
Это счётчик изменений в Postgres и журнал изменений с отметками удаления. Тогда дельта считается
прямо из базы, без снимков в Redis и без гонок с TTL.

## Что сделать

1. **Сервер.**
   - Снимки раскладки хранить по хешу, неизменяемыми, с TTL не меньше нескольких интервалов опроса.
     Дельту считать от снимка **клиента**.
   - Если снимка нет — отвечать «перезагрузись целиком» (`resync`), а не «всё добавлено».
   - Событие сбрасывает только указатель на текущую раскладку, не снимки.
   - Версия — от данных, а не от раскладки: хеш по отсортированным узлам и связям, запросы с
     `ORDER BY`.
2. **Все пути записи публикуют событие:** импорт, пакетное создание, восстановление, `gamma-links-regenerate`.
   Обход — по сторожу или тесту, чтобы новый путь записи без события был виден сразу.
3. **Доставка — SSE:** «граф изменился, хеш такой-то». Клиент по этому сигналу берёт дельту, опрос
   остаётся запасным путём.
4. **Клиент.**
   - Дельта применяется по месту: в 2D через `addNodesToSimulation` и удаление, без перезапуска
     раскладки. 3D — после 1.0 (решение 82).
   - При `resync` граф заменяется, а не сливается.
5. **Первая загрузка.** Сразу граф из кеша (`/me/graph/cached` есть), потом сверка со свежим через
   дельту — как обещает ARCHITECTURE_EN.
6. **Сквозной тест контракта.** Сценарий: создал, переименовал и удалил заметку и связь,
   импортировал, воркер создал автосвязи — граф клиента сходится за N секунд.

   Мутации, которые должны его ронять:
   - дельта от кеша вместо снимка;
   - без события в импорте;
   - слияние вместо замены при `resync`.

## Этап A2 — механизм событий (решение 71)

**Решение владельца (2026-09-26, SYNC-1):** события графа — через публикующую обёртку над репозиториями и
transactional outbox; триггеры Postgres — нет (нарушение слоёв); доменные события — позже, DOMAIN-EVENTS-1.

Этап A сделал события на всех путях записи, но вручную: публикация стоит у каждого вызова, а
`check-graph-write-paths.mjs` следит за 29 местами. Этап A2 заменяет это устройством, в котором забыть
событие нельзя. Дельта, снимки и `resync` из этапа A остаются как есть.

1. **Таблица `graph_outbox`:** номер (растёт монотонно), тип события, id сущности, пользователь,
   полезная нагрузка, время создания, время отправки.
2. **Обёртка над репозиториями заметок и связей:** каждая запись идёт в одной транзакции со строкой
   outbox. Типы событий — по одному на метод записи.
3. **Ретранслятор:** забирает неотправленные строки (`FOR UPDATE SKIP LOCKED`, пачками), публикует в
   Redis, помечает отправленными. Доставка «хотя бы один раз»: получатели переносят повтор.
4. **Публикация в обход ретранслятора запрещена:** ручные вызовы из этапа A убираются, сторож следит,
   что их нет.

Решено владельцем: граница транзакции — в обёртке; ретранслятор — инфраструктура; отправленные строки
удаляются через 30 дней.

Размещение по слоям — согласовано с владельцем 2026-09-26:

- обёртка — декоратор в `infrastructure/` над репозиториями Postgres, транзакция передаётся через
  контекст; домен и приложение видят только прежние интерфейсы репозиториев;
- ретранслятор и очистка — `infrastructure/outbox/`, запуск из точки сборки воркера (`cmd/worker/main.go`);
- порт `application/events.Publisher` и ручные вызовы публикации из обработчиков и сервисов убираются;
- владелец для события — единообразно для всех записей: каждая запись по id (удаление, пакетное
  удаление, восстановление, удаление связей заметки, обновление весов) возвращает затронутые пары
  `(id, creator_id)` через `RETURNING`; `Save` берёт владельца из сущности. Передавать `userID` параметром
  в каждый метод — строже, но меняет интерфейсы домена; отложено до DOMAIN-EVENTS-1;
- исключение для синхронизации черновика в `check-graph-write-paths.mjs` проверить: синхронизация идёт
  через обработчик черновиков, а не заметок, и событие, похоже, не публикуется.

Критерии этапа A2:

1. Каждый метод записи оставляет строку outbox; при откате транзакции строки нет — тест на метод.
2. Процесс упал между коммитом и отправкой — ретранслятор допубликует после перезапуска: тест.
3. Прямых вызовов публикации вне ретранслятора нет — сторож; мутация «ручной вызов» — красная.
4. Живые сценарии из таблицы дыр 1, 2, 4 — по-прежнему верны.
5. Манифест `core-checks.tsv` и CI совпадают. Этап A добавил сторожа путей записи в манифест, но не в
   CI, и `check-all` красный на сверке манифеста.

## Этапы и критерии приёмки

Этапы сдаются на ревью по одному.

**A. Правильная дельта (пункты 1, 2 и замена при `resync` из пункта 4).** Критерии:

1. Три живых сценария из таблицы дыр (1, 2, 4) дают правильный результат:
   - дельта от старого хеша после чужой загрузки содержит новую заметку;
   - удалённая связь приходит в `removed_links`;
   - импорт даёт событие, и заметка появляется на графе без ожидания TTL.
2. Интеграционный тест на каждый сценарий. Мутации «дельта от кеша», «без события в импорте» и
   «слияние при `resync`» — тесты красные.
3. Проверка, которая перечисляет пути записи заметок и связей и падает, если у пути нет события.

**B. Применение по месту (пункт 4, 2D; 3D — после 1.0, решение 82).** Критерии:

1. Добавление, переименование и удаление заметки и связи видны на холсте без перезапуска раскладки.
   Уже стоящие узлы не сдвигаются.
2. Тест на каждое; мутация «перезапуск раскладки при изменении» — тест красный.

**C. SSE (пункт 3).** Критерии:

1. Автосвязь, созданная воркером, появляется на открытом графе за секунды, без действия пользователя.
2. При обрыве соединения клиент переподключается, до переподключения работает опрос.
3. Тест на доставку события и на переподключение.

**3D-часть UI-LOAD-1** (туман при загрузке, постепенное появление в 3D) — после 1.0 (решение 82);
когда до неё дойдёт, она опирается на применение по месту из этапа B.

## Реализация — Devin

### Этап A (2026-09-26, реализация готова, ждёт ревью)

**Снимки и resync (дыры 1, 2).**
- `graph-service:snapshot:{user}:{hash}` — неизменяемый снимок отданной раскладки, ключ — хеш,
  который клиент пришлёт как `last_hash` (`cache/redis_cache.go`, TTL `snapshot_ttl_seconds`,
  по умолчанию 900 с — несколько интервалов опроса).
- `GET /graph/full`, `GET /graph/public`, gRPC `GetFullLayout` после отдачи раскладки сохраняют
  снимок под её хешем. `GET /graph/delta` и gRPC `GetDelta` считают дельту **от снимка клиента**:
  снимка нет → `resync` (HTTP: `resync:true` в ответе; gRPC: `NotFound`). Снимок найден → дельта
  от него, ответ кешируется, новый `current_hash` тоже сохраняется снимком.
- События сбрасывают `note:*`, `full:{user}`, `delta:{user}:*` — снимки не трогают;
  `InvalidateAll` пропускает `snapshot:`-ключи.
- `ComputeDelta`: связь с тем же ключом, но изменёнными `weight`/`source_type`/`gamma_origin`
  уходит в `added_links` (клиент применяет с set-семантикой); удалённые — в `removed_links`.

**Версия от данных (дыра 8).** `computeDataHash` — sha256 по отсортированным полям заметок и связей;
запросы в `postgres_client.go` получили `ORDER BY id`. Раскладка больше не влияет на версию.

**Все пути записи публикуют событие (дыра 4).** `import.Service`, `Refetch`/`RefetchRestore`
(notehandler), `linkweight.Service` получили паблишер и публикуют `NoteCreated`/`NoteUpdated`/
`LinkUpdated`; проводка в `cmd/server` и `cmd/worker`. Сторож `check-graph-write-paths.mjs`

### Этап A2 (2026-09-27, реализация готова, ждёт ревью)

**Таблица.** Миграция `036_graph_outbox` — `graph_outbox(id bigserial, event_type, entity_id,
user_id, payload jsonb, created_at, sent_at)`; индексы по `sent_at IS NULL` и по `sent_at` для
чистки.

**Транзакция через контекст.** `postgres.ContextWithTx`/`dbFromContext` (`postgres/tx.go`):
write-методы репозиториев берут `*gorm.DB` из контекста, если там транзакция, иначе свой
инстанс. Декораторы `outbox.NoteRepository`/`outbox.LinkRepository` открывают транзакцию,
кладут её в контекст, вызывают нижележащий репозиторий и в той же транзакции пишут строку
outbox. Откат любой стороны откатывает обе — критерий 1.

**Владелец события.** Методы записи по id (`Update`, `Delete`, `DeleteBatch`, `Restore`,
`DeleteBySource`, `DeleteByTarget`, `UpdateWeights`, `DeleteViaNote*`) получили `RETURNING`
варианты, возвращающие пары `(id, creator_id)`; `Save` берёт владельца из сущности. Для
сгенерированных связей без `creator_id` декоратор дочитывает создателя source-заметки —
утверждённый fallback постановки.

**Ретранслятор.** `outbox.Relayer` в `cmd/worker` — единственный долгоживущий писатель;
`FOR UPDATE SKIP LOCKED`, пачки по `OUTBOX_BATCH_SIZE`, пометка `sent_at` в той же транзакции
что и publish → падение между коммитом и отправкой допубликовывается следующим процессом
(критерий 2). `Flush` вызывается на старте (долив после падения) и из CLI
`gamma-links-regenerate` перед выходом. `OUTBOX_RELAY_INTERVAL_MS` — интервал опроса.

**Чистка.** `PurgeSentBefore` — из ежедневного `cleanup:soft_deleted` воркера,
`OUTBOX_SENT_RETENTION_DAYS` (30).

**Ручная публикация снята.** Удалён порт `application/events.Publisher`; из note/link
handler'ов, `import.Service`, `linkweight.Service`, `queue.Worker` убраны поля и вызовы
паблишера. Черновик-синк (`draft.Service → noteRepo.Save`) — исключение из постановки —
теперь покрыт автоматически: декоратор видит `Save` и кладёт `NoteUpdated`.

**Сторож инвертирован.** `check-graph-write-paths.mjs` краснеет на (а) ручном
`PublishNote*`/`PublishLink*` вне `outbox/relay.go` и (б) конструкторе
`postgres.NewNoteRepository`/`NewLinkRepository` без обёртки `outbox.New*`. Фикстуры обеих
мутаций красные; оба шага добавлены в `_core-checks.yml`, манифест синхронизирован
(критерии 3 и 5).

**Проводка.** Декораторы во всех точках сборки: `cmd/server`, `cmd/worker`,
`cmd/gamma-links-regenerate`, `cmd/cli`, `cmd/nlp-artifacts-recompute`,
`cmd/quality-recompute`, `recompute/poststeps.go`.

**Тесты.** `internal/infrastructure/outbox/outbox_integration_test.go` — реальные
Postgres+Redis (testcontainers/miniredis): строка появляется на заметке и связи, fallback
владельца gamma-связи, откат не оставляет строку, релей доставляет, «падение» между коммитом
и отправкой доливается, повтор после ошибки Redis, purge старше срока. Пакет зелёный
(57 с). `worker_gamma_integration_test.go` теперь читает событие через настоящий
outbox+релей, не через прямой publish.

**Документация.** ADR 014 — статус переведён на outbox; `ARCHITECTURE_EN.md` — раздел
кешей; `CONFIGURATION_EN/RU` — ключи `backend.outbox.*` и env; `config/backend.json` +
сгенерированный `knowledge-graph.config.json`.
