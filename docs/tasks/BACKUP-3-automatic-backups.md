# BACKUP-3. Бэкап Personal-стека — автоматический, а не «когда стек поднят в два ночи»

Постановка: Claude Code, 2026-09-21. Исполнитель: Devin. Продолжение BACKUP-2
([постановка](BACKUP-2-backup-location-single-source.md), [разбор](BACKUP-2-review-findings.md)).

**Решение владельца (2026-09-21, BACKUP-3):** «бэкап бы нам сделать всё-таки автоматическим».
Определение «автоматический» для этой задачи: изменение в базе Personal оказывается в
синхронизируемой папке (`Desktop\my items`) без действий владельца, а его отсутствие видно.

## Что есть — три производителя, работает один

| Путь | Когда срабатывает | Куда пишет | Что с ним не так |
|---|---|---|---|
| cron в `kg-backup-scheduler` (`docker-compose.personal.yml:255`) | 02:00 ежедневно, вс 23:00 еженедельно | `/backups` = синхронизируемая папка | только если стек поднят в эту минуту; на ноутбуке, который к ночи выключают, — почти никогда. 16.09 → 21.09 файлов нет |
| воркер по событию: любое изменение заметки → задача `backup:database` через 30 с, дедупликация 5 мин (`tasks/backup.go:83`) | ровно тогда, когда появилось что сохранять | `BACKUP_LOCAL_PATH`, по умолчанию `./backups` **внутри контейнера** (`config.go:510`) | в `worker_personal` том не примонтирован (у сервиса нет `volumes:`); дампы ложатся в слой контейнера — их не видит ни папка, ни `check-personal-backup`, ни сторож; `docker compose down` их уносит. `BACKUP_ENABLED=true` стоит (`docker-compose.personal.yml:156`), так что путь **работает и пишет в пустоту** |
| `backup-personal.ps1` руками | когда владелец вспомнил | папка | это не автоматика |

Наблюдение из папки, 2026-09-21: файлы от 12.09, 16.09 (два) и `backup-personal-daily-2026-09-21.sql.gz`
(16:11). У последнего нет времени в имени — ни один из трёх производителей так не называет
(скрипт: `daily-<ГГГГ-ММ-ДД-ЧЧММСС>`, воркер: `backup-personal-<ts>`); видимо, сделан вручную или
переименован. Не блокер, но спросить владельца стоит: если он делает дампы своим способом,
сторож свежести это учитывать не обязан.

Строка про воркер — статическая находка по compose и коду; первый шаг задачи — подтвердить её
на живом стеке (`docker exec kg-worker-personal ls -la backups`), с разрешения владельца.

## Что сделать

1. **Событийный путь — в папку.** Примонтировать `${KG_BACKUP_DIR}` в `worker_personal` как
   `/backups` (та же строка тома, что у `backup_scheduler`) и задать `BACKUP_LOCAL_PATH=/backups`.
   После этого каждое изменение заметки даёт `.sql.gz` в синхронизируемой папке через ~30 с.
   Это и есть основной автоматический путь: он срабатывает ровно тогда, когда есть что сохранять,
   и не зависит от времени суток.
2. **Ретенция не должна съедать чужое.** `Runner.cleanupOldBackups` (`runner.go:140`) удаляет по
   mtime **все** `backup-personal-*.sql.gz` старше `BACKUP_RETENTION_DAYS` (умолчание 7). В общей
   папке это через неделю снесёт еженедельные снимки cron, которым положено жить 90 дней.
   Воркер именует свои файлы отличимо (`backup-personal-auto-<ts>.sql.gz`) и чистит только их;
   cron-скрипт уже чистит только свой режим (`backup-personal-${MODE}-*`). Тест: в каталоге лежат
   `daily`, `weekly` и `auto` старше порога — после чистки воркера первые два на месте.
3. **Страховка на старте.** `start-personal.ps1` после `postgres_personal` healthy: если свежайший
   бэкап старше `KG_BACKUP_MAX_AGE_HOURS` (из `backup-policy.env`) — запустить
   `backup-personal.ps1 -Mode daily` и напечатать результат; если свежий — напечатать его возраст.
   Закрывает случай «cron в 02:00 не дожил, изменений с прошлого раза не было, но стек поднимают
   ради удаления». Планировщик Windows не нужен: пока стек лежит, данные не меняются, и бэкап
   ничего нового не даст.
4. **Видимость.** Строка свежести (`check-personal-backup.ps1`) — в выводе `start-personal.ps1`.
   Внутри стека её показывать некому: воркер не видит папку хоста. Существующего сторожа
   разрушающих команд достаточно; уведомление в интерфейсе — отдельная задача, если владелец
   захочет.
5. **Документация.** `docs/operations/BACKUP.md`: таблица «три производителя» выше — в документ, с указанием,
   какой из них основной; `docs/CONFIGURATION_*.md` — `BACKUP_LOCAL_PATH` для Personal.
   `kg-backup` скилл — один абзац про то, что бэкап теперь событийный.

## Критерии приёмки

1. На живом Personal-стеке (с разрешения владельца): изменить заметку → через ≤ 1 мин в
   `Desktop\my items` появляется `backup-personal-auto-*.sql.gz`, `gunzip -t` проходит, внутри
   есть `CREATE TABLE notes`. Показать `ls -la` до и после.
2. Мутация: убрать монтирование тома → файл появляется внутри контейнера, в папке — нет; тест
   compose-конфигурации (`docker compose config` + проверка, что у `worker_personal` есть том
   на `/backups`) красный. Это машинная проверка, а не чтение YAML глазами.
3. Ретенция: тест п. 2 с тремя файлами трёх производителей — воркер удалил только `auto`.
   Мутация: вернуть старый префикс-фильтр → тест красный.
4. `start-personal.ps1` со свежим бэкапом — не делает дамп, печатает возраст; с устаревшим
   (подложить файл с mtime −48 ч) — делает. Обе ветки показаны выводом.
5. `check-all` зелёный, `test-cleanup-honesty.ps1` и `test_guard_personal_data.py` зелёные —
   сторож и гейт бэкапа не трогались, но их фикстуры лежат в той же папке.

## Чего не делать

- Не поднимать Personal-стек без явного разрешения владельца — проверки п. 1 согласовать.
- Не трогать Yandex.Disk REST-путь: он выключен решением 31 и остаётся opt-in.
- Не менять `backup-policy.env`: порог 24 ч и каталог — решение владельца.
