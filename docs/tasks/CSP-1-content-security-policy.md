# CSP-1. Content-Security-Policy: инвентаризация источников и включение через отчёты

Постановка для Devin. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code на живом тест-стеке.

**Очерёдность:** после PUB-1..3. CSP описывает, откуда страница грузит ресурсы, а PUB-2 меняет источники данных графа — политику разумно писать по устоявшемуся состоянию.

**Задача выделена из AUD-5**, где CSP был явно исключён с формулировкой «требует отдельной работы по инвентаризации источников». Инвентаризация ниже — она сделана, начинать с нуля не нужно.

## Что уже есть

`nginx.conf` после AUD-5 отдаёт `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и держит `server_tokens off`. **CSP нет нигде** — ни в nginx, ни в `svelte.config.js`, ни в `app.html`.

## Инвентаризация источников

Проверено по коду, а не по памяти.

**Внешние источники: практически ноль.**

| Источник | Где | Что значит для политики |
|---|---|---|
| `https://oauth.yandex.ru` | вход через Яндекс | Переход верхнего уровня, а не запрос. Обычными директивами не ограничивается; `connect-src` не нужен |
| `https://svelte.dev` | ссылки в комментариях и текстах | Не загружается, в политику не входит |
| `http://backend`, `http://graph-service` | SSR-обращения из `hooks.server.ts` | Серверная сторона, к CSP браузера отношения не имеет |

Шрифтов нет — в `static/` только `favicon.svg` и `robots.txt`, `@font-face` и Google Fonts не используются. Значит `font-src 'self'` достаточно.

**Динамики, из-за которой обычно приходится ослаблять политику, тоже нет.** Поиск по `src/` не находит ни `eval(`, ни `new Function`, ни `new Worker`, ни `createObjectURL`. Значит ни `'unsafe-eval'`, ни `worker-src blob:` в продакшене не потребуется.

**Three.js подключён минимально** — ядро, `OrbitControls`, `CSS2DRenderer`. Загрузчиков с воркерами (Draco, KTX2) нет. `CSS2DRenderer` меняет `element.style` из JavaScript — это CSSOM, политика его не ограничивает.

**Куда ходит браузер:** `/api` и `/graph-service/api` — тот же источник. В прод-конфигурации `connect-src 'self'` покрывает всё. Исключение — ветка `graph.ts:156` с `http://localhost:9091/api`, она только для локальной разработки.

## Главная трудность: 76 инлайновых стилей

Это единственное место, где политика упирается в код.

- 68 атрибутов `style="..."` в `.svelte`-разметке;
- 8 директив `style:`, компилирующихся туда же;
- плюс `src/app.html:10` — `<div style="display: contents">%sveltekit.body%</div>`.

Атрибут `style` управляется директивой `style-src-attr`, и нонсы к атрибутам неприменимы. Либо `style-src-attr 'unsafe-inline'`, либо переписывать 76 мест.

**Решение владельца, 2026-09-08: разрешить `style-src-attr 'unsafe-inline'` сейчас, рефакторинг вынести в бэклог.** Инъекция стиля без возможности выполнить скрипт даёт мало — подмена внешнего вида и утечка через селекторы фона; против главного риска защищает `script-src`, и его ослаблять не нужно. Запись о снятии уступки — `docs/BACKLOG.md`, TD-CSP-STYLES.

Переписывать 76 мест в этой задаче **не нужно**. Уступка обязана быть помечена в политике комментарием со ссылкой на запись в бэклоге, чтобы через полгода её не приняли за небрежность.

## Ловушка: визуальные тесты идут в обход CSP

`frontend/playwright.config.ts:67`:

```ts
bypassCSP: true, // Required for Argos stabilization script injection
```

Флаг стоит по делу — Argos внедряет в страницу свой скрипт стабилизации. Но следствие такое: **весь визуальный набор выполняется с отключённой политикой и сломанную CSP не поймает.** Зелёные снимки ничего про политику не скажут.

Поэтому проверка нужна отдельная, с включённой политикой. Флаг не снимать — сломаются снимки.

## Что сделать

### 1. Политику генерирует SvelteKit, а не nginx

У SvelteKit есть встроенная поддержка: `kit.csp` в `svelte.config.js`, режимы `nonce` и `hash`. Использовать её.

Причина: страница содержит инлайновый скрипт гидратации, который генерирует сам SvelteKit. Захардкоженный в nginx хеш разойдётся с ним при первом же обновлении фреймворка — молча, как расходились у нас конфиг с источником и промпты с правилами. SvelteKit считает хеш сам.

**Дублировать заголовок в nginx нельзя.** Два заголовка CSP означают пересечение политик, то есть фактически более строгую из них, и отладка становится мучением. Если решишь оставить в nginx — только для статики, которую SvelteKit не отдаёт, и с объяснением в комментарии.

### 2. Сначала режим отчётов, потом запрет

Включать сразу запрещающую политику на живом приложении — способ узнать о недостающей директиве от пользователя. Порядок:

1. `Content-Security-Policy-Report-Only` с целевой политикой;
2. прогон по всем экранам: главная, граф 2D, граф 3D, поиск, вход, регистрация, кокпит, создание заметки, вход через Яндекс;
3. собрать нарушения из консоли;
4. дополнить политику ровно тем, что понадобилось, **с объяснением каждой уступки**;
5. перевести в запрещающий режим.

Пункт 4 — суть задачи. Директива без объяснения через месяц не отличима от скопированной с чужого сайта.

### 3. Отправная политика

Ориентир, не догма — правь по результатам пункта 2:

```
default-src 'self';
script-src 'self' 'nonce-...';
style-src 'self';
style-src-attr 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
frame-ancestors 'self';
base-uri 'self';
form-action 'self';
object-src 'none'
```

`frame-ancestors 'self'` повторяет нынешнее поведение `X-Frame-Options: SAMEORIGIN` — **решение владельца, 2026-09-08**. Строже не делаем: замысел графа сообщества допускает будущий встраиваемый виджет публичного графа, и закрывать эту дверь политикой сейчас незачем. От clickjacking `'self'` защищает так же.

### 4. Разработка и продакшн различаются

Vite в режиме разработки требует `'unsafe-eval'`. Политика не должна ломать `npm run dev`: либо она применяется только в продакшн-сборке, либо режим разработки получает свою. Захардкоженного `'unsafe-eval'` в продакшн-политике быть не должно.

### 5. Проверка, которая переживёт следующую правку

Нужен тест, который ходит по приложению **с включённой политикой** и падает при нарушении. Отдельный Playwright-проект без `bypassCSP`, слушающий консоль на `Content Security Policy`, — достаточно; хватит нескольких ключевых экранов, включая 3D.

Без этого политика проживёт до первой библиотеки, которая захочет инлайновый скрипт, и будет молча ослаблена.

## Ограничения

- Не снимать `bypassCSP: true` в существующей конфигурации Playwright: сломаются визуальные эталоны.
- Не добавлять `'unsafe-eval'` в продакшн-политику.
- Не ослаблять `script-src` ради удобства: инлайновые стили — приемлемая уступка, инлайновые скрипты нет.
- TLS и HSTS в задачу не входят — отложены отдельным решением владельца.
- Не переписывать инлайновые стили: решение владельца, отдельная запись в бэклоге.
- Не делать `frame-ancestors` строже `'self'`.
- Не трогать заголовки из AUD-5.

## Критерии приёмки

1. Политика присутствует в ответе приложения; заголовок один, не два.
2. Все девять экранов из пункта 2 работают без нарушений в консоли: граф рисуется в 2D и 3D, поиск ищет, вход проходит.
3. Каждая уступка в политике объяснена комментарием: что её потребовало.
4. `npm run dev` работает.
5. Визуальный набор остаётся зелёным.
6. Есть проверка с включённой политикой, и она **падает при нарушении** — проверить мутацией: добавить в разметку инлайновый `<script>` и убедиться, что проверка краснеет. Вернуть.
7. `check-all` без `-Quick` зелёный.

## Что приложить к результату

Список нарушений, собранный в режиме отчётов на шаге 2, — до того, как политика была дополнена. Это единственное доказательство, что политика выведена из поведения приложения, а не переписана из статьи. Плюс вывод мутации по критерию 6.
