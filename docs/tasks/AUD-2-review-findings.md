## Блокер. Сидер не работает — тестовую учётку создать нечем

`backend/cmd/seed/main.go:56-58`:

```go
var roleID uuid.UUID
if err := database.WithContext(ctx).Raw("SELECT id FROM user_roles WHERE name = 'user' LIMIT 1").Scan(&roleID).Error; err != nil {
```

GORM `Scan` в `uuid.UUID` (это `[16]byte`) пытается разложить строку в массив байт поэлементно и падает. Проверено запуском против базы тест-стека:

```
APP_ENV=test SEED_TEST_USER_PASSWORD=verify-pass DATABASE_URL=...knowledge_test go run ./cmd/seed

2026/09/05 20:01:19 failed to look up 'user' role: sql: Scan error on column index 0,
name "id": converting driver.Value type string ("3916db86-7cd1-49b2-9aae-687e369fb1cf")
to a uint8: value out of range
exit status 1
```

Сидер не отработал ни разу. Проверка `if roleID == uuid.Nil` на строке 60 недостижима — до неё выполнение не доходит.

Чинится сканированием в строку с последующим `uuid.Parse`, либо `Pluck`, либо `Row().Scan`. Ветку с `uuid.Nil` после этого стоит сохранить: она осмысленна.

**Почему это блокер, а не мелочь.** Миграция `029` удаляет старую тестовую учётку, а создать новую нечем. В связке это оставляет тест-стек без пользователя с нулевым UUID, на которого завязан режим `SKIP_AUTH`.

Проверено на базе тест-стека, а не выведено рассуждением. Чтение в режиме `SKIP_AUTH` пользователя не требует — `applyNoteScope` (`note_repo.go:40-44`) обходит фильтр и к таблице `users` не обращается. Запись требует: `notes.creator_id` несёт внешний ключ на `users(id)` (`migrations/016_add_auth_and_sharing.up.sql:17`), а middleware пишет в него нулевой UUID (`skip_auth.go:31`).

```
INSERT INTO notes (..., creator_id, ...) VALUES (..., '00000000-0000-0000-0000-000000000000', ...);

ERROR:  insert or update on table "notes" violates foreign key constraint "notes_creator_id_fkey"
DETAIL:  Key (creator_id)=(00000000-0000-0000-0000-000000000000) is not present in table "users".
```

Та же зависимость у `user_settings.user_id`, `user_achievements.user_id`, `note_likes.user_id` и таблиц шаринга — все `NOT NULL REFERENCES users(id)`. Значит любой сценарий, который создаёт заметку, меняет настройку или начисляет достижение, падает; сценарии только на чтение проходят. Отказ выглядит плавающим, хотя он системный.

**Про способ проверки.** `go test ./...` зелёный и это правда, но ни один тест не выполняет путь сидера против базы — поэтому отказ был невидим. Постановка требовала критерий 4 «на тест-стеке после `seed-test-data.ps1` вход под тестовой учёткой работает»; он не выполнялся, и в отчёте честно сказано, что живая проверка оставлена ревьюеру. Нужен тест, который поднимает базу и прогоняет сидер, иначе следующая регрессия здесь снова пройдёт мимо.

# Раунд 3. Переоткрыто: AUD-2 молча откатил конфигурацию тумана

Статус: **отклонено.** Найдено при ревью AUD-3, относится к `889c33e`.

## Что произошло

`889c33e` менял `knowledge-graph.config.json`, чтобы добавить `app_env`. Вместе с этим изменились плотности тумана 3D-сцены:

| Пресет | Было (`44bdb87`) | Стало (`889c33e`) |
|---|---|---|
| `birth.density_initial` | 0.01 | 0.08 |
| `birth.density_final` | 0.0006 | 0.005 |
| `nebula.density_initial` | 0.005 | 0.04 |
| `nebula.density_final` | 0.0003 | 0.015 |

Последствие: три теста в `frontend/src/features/graph-3d/lib/engine.performance.test.ts` красные — `expected 0.04 to be close to 0.005`. Плюс сцена визуально другая: туман в восемь раз плотнее.

## Корень — не невнимательность, а конструкция

`knowledge-graph.config.json` **генерируется** из `config/` скриптом `scripts/build-config.js`, но при этом закоммичен и правится руками.

`config/frontend.json:39-41` до сих пор содержит **старые** значения:

```json
"birth": { "density_initial": 0.08, "density_final": 0.005 },
"nebula": { "density_initial": 0.04, "density_final": 0.015 },
```

То есть `44bdb87` поправил сгенерированный файл, не тронув источник. Любая последующая регенерация обязана была это откатить — и откатила при первой же необходимости добавить `app_env`.

Винить исполнителя не за что: регенерация выглядит безобидной операцией, а расхождение источника и артефакта ничем не проверяется.

## Что сделать

1. Решить, какие значения верны. Судя по `44bdb87`, `9ee17b1` и ожиданиям тестов — `birth 0.01/0.0006`, `nebula 0.005/0.0003`.
2. Внести их в `config/frontend.json`, а `knowledge-graph.config.json` **пересобрать**, а не править.
3. Закрыть класс проблемы: шаг в CI, который выполняет `npm run build-config` и падает, если сгенерированный файл отличается от закоммиченного. Это та же болезнь, что и P-2 с промптами: копия расходится с источником, потому что расхождение ничем не ловится.

## Страж проверен мутацией

Одного факта, что шаг добавлен, недостаточно — проверил, что он краснеет.

Смоделировал ровно тот сценарий, который и породил регрессию: правку сгенерированного файла руками, попавшую в индекс. Затем выполнил шаги стража как в CI:

```
npm run build-config
git diff --exit-code knowledge-graph.config.json   ->  1
```

Ненулевой код — страж срабатывает. Дерево восстановлено.

Логика верна в обе стороны: правка артефакта мимо источника ловится, потому что регенерация её затирает и дифф расходится; забытая регенерация после правки `config/` ловится по той же причине.

## Отдельно: страж переносим

Проверил риск, из-за которого такой шаг обычно становится вечно красным. `build-config` пишет `JSON.stringify(...) + '
'` в `utf8`, то есть LF на любой платформе; закоммиченный блоб тоже LF; `.gitattributes` покрывает только `*.sh` и JSON не нормализует. На Linux-раннере поведение совпадёт с локальным. Скрипт зависит только от `fs` и `path`, поэтому отсутствие корневых `node_modules` в джобе роли не играет.

## Наблюдение, не замечание

Шаг живёт в джобе `frontend-checks`, после `npm run check`. Функционально место верное — там уже настроен Node, а `working-directory: .` уводит выполнение в корень репозитория. Смысловое несовпадение всё же есть: расхождение конфигурации касается всего репозитория, а не фронтенда. Сейчас `_core-checks.yml` не фильтруется по путям, поэтому шаг выполняется всегда; но если когда-нибудь `frontend-checks` получит `paths:`, страж молча перестанет работать. Стоит держать в голове, переносить сейчас незачем.
