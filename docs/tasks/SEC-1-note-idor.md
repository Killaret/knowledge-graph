# SEC-1. Любой зарегистрированный читает, правит и удаляет чужие приватные заметки

Постановка для Devin. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code на живом тест-стеке.

**Очерёдность: первой, впереди всего.** Это не улучшение и не долг — это открытая дыра в боевом коде. PUB-1 без неё делать нельзя: она сняла бы последний барьер и вынесла бы то же самое наружу, анониму.

**Критично.** Регистрация публична, значит порог входа — один POST.

## Что происходит

Проверено на живом тест-стеке. Завёл вторую учётку обычной регистрацией и обратился её токеном к приватной заметке `testuser`.

```
POST /api/v1/auth/register           -> 201
POST /api/v1/auth/login              -> 200, токен получен

GET    /api/v1/notes/<чужая private> -> 200   title, is_public:false, content целиком
GET    /api/v1/notes/<...>/links     -> 200
PUT    /api/v1/notes/<...>           -> 200   заметка перезаписана
POST   /api/v1/notes/<...>/publish   -> 403   единственное закрытое место
DELETE /api/v1/notes/<...>           -> 204   заметка удалена
```

После `DELETE` строки в базе нет вовсе:

```sql
select id, title, deleted_at is not null from notes where id='85bdbec1-...';
-- (пусто)
```

То есть посторонний не только прочитал чужую приватную заметку, но и **перезаписал её и удалил безвозвратно**.

## Причина, и она короткая

Проверка владельца в проекте **есть** — `notehandler/note_handler.go:785`, пять строк:

```go
if existing.CreatorID() == nil || *existing.CreatorID() != userID {
    apicommon.Forbidden(c)
    return
}
```

Она применена ровно в одном месте — в `setPublic`, который обслуживает `publish`/`unpublish`. Отсюда и одинокий `403` в таблице выше.

В `Get`, `Update` и `Delete` её нет. Все трое зовут `FindByID` (`note_repo.go:90-101`), который принимает только `id`: ни `userID`, ни `applyNoteScope`, ни `is_public`.

Единственное, что сегодня защищает чужие заметки, — **незнание идентификатора**. Это не защита. Идентификаторы утекают: `GET /notes/:id/links` посторонним отдаёт `200`, то есть от одного известного id можно обойти всю связанную компоненту.

## Что сделать

**Применить существующую проверку владельца в `Get`, `Update`, `Delete`** и во всём, что читает или меняет заметку по id. Список маршрутов не считай закрытым — пройди по `router.go` и проверь каждый, где есть `:id`: `links`, `suggestions`, `restore`, `batch`.

Правило доступа:

- владелец — полный доступ;
- посторонний и аноним к публичной заметке — только чтение;
- посторонний и аноним к приватной — **`404`, а не `403`**. Существование чужой приватной заметки подтверждать нельзя. Нынешний `403` в `setPublic` этому правилу не следует; привести к общему виду.

**Где ставить проверку — на твоё усмотрение, но одинаково для всех маршрутов.** Пять строк, скопированные в шесть хендлеров, разойдутся: один забудут. Разумнее либо скоупить выборку (`FindByID` с `userID`, по образцу `applyNoteScope`), либо общий помощник, через который проходят все.

## Ограничения

- Не менять формат ответов и коды для законных случаев: владелец получает то же, что и раньше.
- Не трогать `SkipPaths` — открытие периметра это PUB-1, отдельной задачей.
- Не трогать `Cache-Control` и `Vary`.
- Публичные заметки остаются читаемыми для любого авторизованного — это продуктовое решение владельца, а не дефект.

## Критерии приёмки

1. Посторонний авторизованный: `GET` чужой приватной → `404`.
2. Посторонний авторизованный: `PUT` чужой приватной → `404`, и **содержимое в базе не изменилось**.
3. Посторонний авторизованный: `DELETE` чужой приватной → `404`, и **строка в базе на месте**.
4. Посторонний авторизованный: `GET` чужой **публичной** → `200`. Не сломать витрину сообщества.
5. Владелец: чтение, правка и удаление своих заметок работают как раньше.
6. То же для `links`, `suggestions`, `restore` и всего прочего с `:id`, что найдёшь в `router.go`.
7. `publish`/`unpublish` приведены к `404` вместо `403`.
8. **Каждый из критериев 1, 2, 3 закрыт тестом, и каждый тест проверен мутацией:** убрать проверку — тест обязан покраснеть. Три отдельные мутации, не одна: три маршрута могут быть защищены по-разному и сломаться поодиночке.

## Что приложить к результату

Ту же таблицу проб, что выше, снятую до и после правки, одним и тем же способом: вторая учётка заводится обычной регистрацией, обращение идёт к приватной заметке первой. До — `200/200/204`. После — `404` везде.

И отдельно состояние базы после проб `PUT` и `DELETE`: заметка обязана остаться нетронутой. Коды ответов без этого — половина доказательства; в первой пробе `DELETE` вернул `204` и строка исчезла.
