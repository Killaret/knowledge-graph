## 1. `nltk` — high, но исправления не существует

**Рекомендация называет шесть уязвимых API:** `TransitionParser.train`,
`TransitionParser.parse`, `AveragedPerceptron.save`, `AveragedPerceptron.load`,
`PerceptronTagger.save_to_json`, `save_maxent_params`. Суть — эти публичные функции
работают с путями через обычный `open()` в обход `pathsec`, поэтому читают и пишут вне
разрешённых корней.

**Условие срабатывания** (дословно из PoC): «приложение включает `pathsec` и позволяет
недоверенным сценариям выбирать пути импорта или экспорта модели».

**Что делает наш код** (`nlp-service/app/nlp_utils.py`):

```python
nltk.data.find("tokenizers/punkt")
nltk.download("punkt")
nltk.data.find("corpora/stopwords")
nltk.download("stopwords")
nltk.corpus.stopwords.words("russian") + nltk.corpus.stopwords.words("english")
```

Ни одного из шести уязвимых API. Пути — строковые литералы, недоверенный ввод в них не
попадает, `pathsec` не включён.

**Отдельно проверил собственную же прошлую формулировку.** В решении 25 написано
«уязвимые model-artifact API не вызываются». Буквально читая, `nltk.download` — тоже
model-artifact API, и я готов был признать обоснование неверным. Сверка со списком
показала, что `download` в него не входит. Формулировку стоит уточнить: вызываются
не «никакие model-artifact API», а **не вызывается ни один из шести перечисленных**.

**Исправления нет:** `vulnerable_version_range: <= 3.10.3`,
`first_patched_version: null`. Обновляться некуда — мы уже на 3.10.3.

## 2. `cookie` — low, дважды, чинится только чужими руками

Приходит транзитивно: `@sveltejs/kit@2.70.3` → `cookie@0.6.0`. Kit жёстко объявляет
`cookie: ^0.6.0`, поэтому **обновление kit не помогает** — Dependabot-обновление до
2.70.3 уже смержено, а `cookie` остался прежним. Исправлено в `cookie@0.7.0`.

**Суть уязвимости:** в имя, путь или домен куки можно протащить лишние символы и тем
самым подменить другие поля — например, имя `userName=<script>...; Max-Age=2592000; a`
даст не то, что ожидается. Обходной путь из самой рекомендации: не передавать в эти
поля недоверенные значения.

**Что делает наш код.** Куки ставит Go-бэкенд, а не npm-пакет
(`backend/internal/interfaces/api/handlers/auth/handler.go:98`):

```go
c.SetCookie(accessTokenCookieName, accessToken, maxAgeAccess, "/", "", secure, true)
```

Имя — константа, путь — литерал `/`, домен — пустая строка. SvelteKit в
`hooks.server.ts` только **пробрасывает** заголовок `cookie` как прокси, не сериализуя
его с нашими значениями. Условие уязвимости не возникает.

Область в корневом манифесте — `development`; во фронтенде — `runtime`, то есть пакет
физически едет в образ, но по вышеописанной причине в нашем потоке не используется
опасным образом.

## Что предлагаю — решение за владельцем

Все три алерта имеют **нулевую практическую применимость** в нашем коде, и ни один
нельзя закрыть обновлением: у `nltk` патча не существует, `cookie` зажат чужим
манифестом.

**Вариант А — закрыть алерты как принятый риск** (`tolerable_risk`) с письменным
обоснованием, поставив условия пересмотра. Тогда счётчик на GitHub обнуляется, и
следующий новый алерт будет виден сразу, а не утонет среди трёх вечных. Сегодня
`allow-ghsas` в `security.yml` глушит только проверку CI — сам алерт остаётся открытым,
поэтому GitHub и пишет «3 vulnerabilities» на каждом push.

**Вариант Б — оставить открытыми** как напоминание. Цена: постоянный шум, на фоне
которого новая настоящая находка не выделится.

**Вариант В — форсировать `cookie@0.7.0` через `overrides`.** Технически возможно, но
это подмена транзитивной зависимости фреймворка ради уязвимости, которая у нас не
достижима. Риск регрессии в обработке кук больше выигрыша.

**Рекомендую А.** Условия пересмотра записать явно:

- `nltk` — как только выйдет версия выше 3.10.3 с исправлением, снять и исключение
  `allow-ghsas` из `security.yml`, и закрытие алерта;
- `cookie` — как только SvelteKit поднимет зависимость до `^0.7`, обновить и закрыть;
- если в коде появится вызов любого из шести API `nltk` или сериализация куки с
  вычисляемым именем/путём/доменом — обоснование аннулируется, риск пересматривается.

Третий пункт важнее первых двух: принятый риск верен **при нынешнем коде**, а не вообще.

## Исполнено (2026-09-14)

Владелец выбрал **вариант А**. Все три алерта закрыты через API как `tolerable_risk`
с обоснованием в комментарии и ссылкой на этот файл:

```
alert 70 (nltk,   high) -> dismissed / tolerable_risk
alert 90 (cookie, low)  -> dismissed / tolerable_risk
alert 31 (cookie, low)  -> dismissed / tolerable_risk
открытых алертов: 0
```

Первая попытка закрытия **не сработала** и вернула ошибку разбора ответа — комментарий
был слишком длинным. Проверка состояния показала `open`, попытка повторена с коротким
текстом. Записываю, потому что без проверки я бы отчитался о закрытии, которого не было:
ровно тот класс ошибки, ради которого в норму внесён абзац «операция, сообщившая об
успехе, не проверена».

Исключение `allow-ghsas: GHSA-8mgp-746c-j5xp` в `security.yml` **остаётся** — оно
глушит проверку CI, закрытие алерта её не заменяет. Снимать оба разом, когда выйдет
патч.
