# LINKS-2 — разбор ревью

Ревьюер: Claude Code. Дата: 2026-09-23. Реализация: Devin, `523beac`, `b56ff5e` (2026-09-22).
Постановка: [`LINKS-2-manual-link-over-gamma.md`](LINKS-2-manual-link-over-gamma.md). Код уже в
`main` (слияние `21691ea`) — ревью шло после слияния.

**Вердикт: принято с условием.** Три состояния пары работают — повышение, отказ и снятие
отказа проверены живьём на стенде и каждое своей мутацией. Условие одно: удаление
**подтверждённой** связи тихо записывает «не связаны», а интерфейс об этом не предупреждает и
не может предупредить — граф-API не отдаёт происхождение связи.

Отдельно, не по LINKS-2: при живом прогоне пересчёта найден старый дефект пакетного подбора
соседей — постановка [`LINKS-3`](LINKS-3-batch-similarity-order.md). Он же делает неверным
счётчик `--dry-run` из этой задачи.

## Условие: удаление подтверждённой связи — решение, о котором человеку не сказали

По решению 53 удаление связи с происхождением записывает «не связаны» — бэкенд так и делает:

```
DELETE /api/v1/links/01a5c139…   (source_type=user, metadata.gamma есть)  → 204
link_suppressions для этой пары: 1
```

Но в интерфейсе у такой связи обычная кнопка «Удалить»: пояснение «пара будет помечена как
несвязанная и больше не будет предлагаться» показывается **только** для `source_type='gamma'`
(`routes/graph/+page.svelte:318`), остальные удаляются сразу. И узнать, что связь несла
происхождение, фронтенд не может: граф-сервис отдаёт у связи ровно
`link_type, source, source_type, target, weight` — метаданных нет (проверено ответом
`/api/v1/graph/public`).

Итог: человек подтвердил связь, потом удалил её — и пара навсегда перестала предлагаться, о чём
он не узнал. Постановка требовала обратного: «без пояснения человек не поймёт, что удаление
стало решением, а не уборкой».

Что нужно: граф-API отдаёт признак происхождения (булево `gamma_origin` или аналог — не весь
`metadata`), фронтенд показывает то же пояснение для связей с этим признаком; e2e или
свидетельство с экрана в `MANUAL_TEST_FEEDBACK.md`. Строка бэклога — сверху, после LINKS-3.

## Мелочи — не чинить в ущерб очереди

1. **Гонка повышения с пересчётом.** `SaveUserLink` читает gamma-строку без `FOR UPDATE` и
   обновляет по `id`, не проверяя `RowsAffected`. Если `gamma-links-regenerate` удалит строку
   между чтением и записью, `UPDATE` затронет ноль строк, а API вернёт **200** со связью,
   которой нет. Редко (пересчёт запускают руками), но это тихий успех. Лечится проверкой
   `RowsAffected == 1` и повтором как создания.
2. **Критерий 2 по букве.** Свойство «повышенная строка переживает пересчёт» охраняется двумя
   тестами (`PromotesGamma` — строка становится `user`; `DeleteBySourceType` — `user` не
   удаляется), но не тем, чего просила постановка: константа `gammaSourceType` в
   `cmd/gamma-links-regenerate` не охраняется ничем — CLI исключён из покрытия.
3. **Встречное направление.** Ручная связь Y→X при существующей gamma X→Y создаётся рядом
   (`201`), обе остаются, у ручной нет происхождения — проверено живьём. Постановка про
   повышение говорила «на паре», и в разделе отказов пара без направления; реализация смотрит
   только в то же направление. Намерение решения 53 — одно ребро на пару; удобно доделать
   вместе с условием.
4. **`link_type = NULL` ничем не пишется.** `DELETE` записывает конкретный тип; «никакой связи»
   существует только в тестах. Для генератора разницы нет (он предлагает только `related`).
5. Нормализация пары держится только в Go (`NormalizePair`); `CHECK (note_a_id < note_b_id)`
   в миграции нет.

## Принято без замечаний

- Повышение, отказ и снятие отказа — в одной транзакции (`SaveUserLink`, `DeleteAndSuppress`).
- Удаление чистой ручной связи отказа не пишет — проверено живьём (записей было 2, осталось 2).
- Adversarial-фаза нашла настоящий дефект (гонка пересчёта с ручной вставкой роняла весь
  прогон) и закрыла его тестом, красным до исправления, — это та работа, ради которой фаза
  введена.
- Флаки-тест симметрии пойман и переписан так, чтобы мутация «только прямое направление»
  краснела гарантированно.
