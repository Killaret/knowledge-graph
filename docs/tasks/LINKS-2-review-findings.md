## Условие: удаление подтверждённой связи — решение, о котором человеку не сказали

По решению 53 удаление связи с происхождением записывает «не связаны» — бэкенд так и делает:

```
DELETE /api/v1/links/01a5c139…   (source_type=user, metadata.gamma есть)  → 204
link_suppressions для этой пары: 1
```

Но в интерфейсе у такой связи обычная кнопка «Удалить»: пояснение «пара будет помечена как
несвязанная и больше не будет предлагаться» показывается **только** для `source_type='gamma'`
(`routes/graph/+page.svelte:318`), остальные удаляются сразу. И узнать, что связь несла
происхождение, фронтенд не может: граф-сервис отдаёт у связи ровно
`link_type, source, source_type, target, weight` — метаданных нет (проверено ответом
`/api/v1/graph/public`).

Итог: человек подтвердил связь, потом удалил её — и пара навсегда перестала предлагаться, о чём
он не узнал. Постановка требовала обратного: «без пояснения человек не поймёт, что удаление
стало решением, а не уборкой».

Что нужно: граф-API отдаёт признак происхождения (булево `gamma_origin` или аналог — не весь
`metadata`), фронтенд показывает то же пояснение для связей с этим признаком; e2e или
свидетельство с экрана в `MANUAL_TEST_FEEDBACK.md`. Строка бэклога — сверху, после LINKS-3.

## Мелочи — не чинить в ущерб очереди

1. **Гонка повышения с пересчётом.** `SaveUserLink` читает gamma-строку без `FOR UPDATE` и
   обновляет по `id`, не проверяя `RowsAffected`. Если `gamma-links-regenerate` удалит строку
   между чтением и записью, `UPDATE` затронет ноль строк, а API вернёт **200** со связью,
   которой нет. Редко (пересчёт запускают руками), но это тихий успех. Лечится проверкой
   `RowsAffected == 1` и повтором как создания.
2. **Критерий 2 по букве.** Свойство «повышенная строка переживает пересчёт» охраняется двумя
   тестами (`PromotesGamma` — строка становится `user`; `DeleteBySourceType` — `user` не
   удаляется), но не тем, чего просила постановка: константа `gammaSourceType` в
   `cmd/gamma-links-regenerate` не охраняется ничем — CLI исключён из покрытия.
3. **Встречное направление.** Ручная связь Y→X при существующей gamma X→Y создаётся рядом
   (`201`), обе остаются, у ручной нет происхождения — проверено живьём. Постановка про
   повышение говорила «на паре», и в разделе отказов пара без направления; реализация смотрит
   только в то же направление. Намерение решения 53 — одно ребро на пару; удобно доделать
   вместе с условием.
4. **`link_type = NULL` ничем не пишется.** `DELETE` записывает конкретный тип; «никакой связи»
   существует только в тестах. Для генератора разницы нет (он предлагает только `related`).
5. Нормализация пары держится только в Go (`NormalizePair`); `CHECK (note_a_id < note_b_id)`
   в миграции нет.

### Блокер: `gamma_origin` отдаёт монолит, а связи холста приходят из graph-service

Страница графа грузит связи так (`frontend/src/shared/api/graph.ts:245–273`):

```
loadGraph → getFullGraphData(…, mode)
  → getGraphApi().get("v1/graph/full" | "v1/graph/public")   ← graph-service, /graph-service/api
  → при ошибке и mode === "personal": getFreshGraph()        ← монолит, /api/v1/me/graph/fresh
```

`gamma_origin` добавлен в `backend/internal/interfaces/api/graphhandler/graph_handler.go` — то есть
в `/me/graph/cached|fresh` монолита, который фронтенд зовёт **только как запасной путь**, когда
graph-service не ответил. В graph-service признака нет: структура связи
`services/graph-service/internal/engine/layout.go:34` несёт `source_type`, а поиск по всему сервису
на `gamma_origin|GammaOrigin` — **ноль совпадений**; запрос связей
(`db/postgres_client.go`) метаданные не выбирает.

В обычной работе у связи на холсте `gamma_origin` нет, `normalizeLink` подставляет `false`, и
`handleLinkDelete` для подтверждённой связи снова удаляет без пояснения — ровно то, что было
условием. Фронтенд-тест `graph.test.ts` зелёный, потому что кормит маппинг ответом, в котором
поле есть; настоящий сервер его не шлёт.

Что нужно: признак в graph-service — выбрать `metadata ? 'gamma'` (или готовое булево) в запросе
связей, поле `gamma_origin` в `engine/layout.go` и во всех ответах, отдающих связи (`full`,
`public`, `delta`, `note`); тест graph-service на ответ с повышенной связью; мутация «не выбирать
признак» — красная. И проверка по-настоящему: через ответ `/graph-service/api/v1/graph/full` на
стенде, а не через маппинг.

### Вторая находка, серьёзнее условия: у связей холста нет `id` — удаление с холста не работает вообще

В том же ответе graph-service у связи нет **`id`**: структура `LayoutLink`
(`services/graph-service/internal/engine/layout.go:29`) — это `source`, `target`, `weight`,
`link_type`, `source_type`. Объект связи под курсором собирается в
`frontend/src/features/graph-interaction/event-bridge.ts:350–362` и берёт `id` из связи холста —
значит, `undefined`. А `handleLinkDelete` (`routes/graph/+page.svelte:303`) при отсутствии `id`
молча выходит («Cannot delete link without id», лог только в режиме разработки).

Следствие: кнопки «Удалить» и «Не связаны» в подсказке связи на холсте ничего не делают — ни для
какой связи. Проверка обработчика на `id` появилась 2026-08-02 (`6685318`, удаление связей из
интерфейса), связи холста приходят из graph-service — так что дефект старше LINKS-2, но
отказ «не связаны» из LINKS-2 с экрана поэтому недостижим. Моё ревью LINKS-2 22.09 проверяло
отказ через API и оставило проверку с экрана (п. 11) владельцу — туда этот дефект и упал.

И третье: `event-bridge.ts` не копирует `gamma_origin` в объект под курсором вообще — даже когда

Проверено по коду и живому ответу API; с экрана не проверял — навести курсор на связь в холсте

### Мелочи

1. **Одна строка с `source_type IS NULL` роняет весь граф.** Выражение
   `(source_type = 'gamma' OR …)` при NULL даёт NULL, а pgx не кладёт NULL в `bool`. Проверено на
   стенде: `UPDATE links SET source_type = NULL` на одной ручной связи → `/graph/full` отвечает 500
   `can't scan into dest[6]: cannot scan NULL into *bool`; после отката — 200. Колонка допускает NULL
   (`024_add_links_source_type.up.sql`: `DEFAULT 'user'`, без `NOT NULL`), а соседняя колонка в том
   же запросе защищена `COALESCE`. В коде NULL никто не пишет, но цена — пустой граф. Починка:
   `COALESCE(source_type, 'user') = 'gamma'`, в тест — строка с NULL.
2. **Сид падает на встречной паре.** `seed-test-data.ps1` берёт случайные пары. Если выпадает B→A
   при уже созданной A→B, правило «одно ребро на пару» (решение 53) отвечает 409, и сид выходит с
   кодом 1. На моём прогоне так и вышло: `custom` 5bed9efb→d35757ca, затем обратная. Сиду брать
   неупорядоченные пары.
3. **Текст модалки для подтверждённой связи** — «Remove this suggested link?», хотя человек её
   подтвердил. Нужна своя формулировка: связь предложила модель, человек подтвердил, удаление
   запишет «не связаны».

### Не LINKS-2 — строки в бэклог

- **Наведение попадает не на ту связь.** `findLinkAtPosition` (`interactions.ts:62`) берёт
  **первую** связь в пределах 8 единиц, а не ближайшую. На стенде со всеми типами связей у каждой из
  шести повышенных связей в любой точке найдётся другая ближе 8 единиц. Первая попытка навести на
  `0fbb2edd` открыла подсказку соседней автосвязи. Подтвердить или удалить связь, на которую не
  навести, нельзя.
- **Панель заметки не показывает связи.** Там «Links (undefined)». Клиент `getNoteLinks`
  (`shared/api/links.ts:64`) ждёт массив, а API с марта отдаёт `{incoming, outgoing}`; клиент
  в нынешнем виде — с 2026-07-16 (`13151ae`). Правка, удаление и массовое удаление связей из панели недоступны. Когда список
  вернётся, одиночное удаление там сразу пишет отказ без пояснения (`CockpitNoteDetails.svelte:127`).
  Массовое (`DeleteByNote` → `DeleteBySource`) отказов не пишет и берёт только исходящие связи. Что
  должно делать массовое удаление, решает владелец.

### Принято без замечаний

- Запросы связей выбирают `id::text` и признак с той же семантикой, что `IsGamma() ||
  HasGammaProvenance()` монолита. На стенде `gamma_origin` совпал с базой во всех 251 строках.
- `delta.ts` починен и по `id`, и по `source_type`. Потеря `id` в дельте ломала бы удаление после
  любой правки графа.
- Удаление с холста работает: `id` доходит до `DELETE` (дефект с `6685318`, 2026-08-02).
- Решение не трогать gRPC-`LayoutLink` объяснено: холст читает HTTP, `protoc` локально не
  генерируется.

## Доработка после второго отклонения — Devin, 2026-09-24

Блокер закрыт в реальном пути: `transformRawGraph` (`graphLoader.ts`) теперь копирует
`gamma_origin`, а не сбрасывает его между ответом graph-service и холстом.

Регрессия `GraphCanvas.events.spec.ts` начинается с объекта связи в формате ответа
graph-service (`source_type=user`, `gamma_origin=true`), пропускает его через
`transformRawGraph`, рендерит настоящий `GraphCanvas`, наводит мышь на связь и нажимает
Delete. `onLinkDelete` обязан получить `id` и `gamma_origin=true`. Это покрывает цепочку
`graph response → graphLoader → simulation → event-bridge → delete callback`; удаление
поля в любом из этих звеньев роняет тест. Мутация без строки в `graphLoader.ts` красная:
получено `gamma_origin: undefined` вместо `true`.

Дополнительно закрыты две находки ревью:

- SQL признака использует `COALESCE(source_type, 'user')`, поэтому историческая строка с
  `source_type=NULL` больше не роняет весь граф; интеграционная фикстура содержит NULL.
  Мутация с прежним `source_type = 'gamma'` красная: `cannot scan NULL into *bool`.
- Root/depth-путь теперь проверяет непустой `id` и `GammaOrigin` для живой gamma- и
  повышенной связи, а не только длину массива.
- `delta.test.ts` закрепляет `id`, `source_type` и `gamma_origin` после delta-restart;
  мутация без копирования флага красная.
