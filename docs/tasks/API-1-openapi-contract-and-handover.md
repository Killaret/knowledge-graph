# API-1. Спецификация API: правдивость по договору и передача второму разработчику

Постановка для Devin. Порядок работы: [`../AI_AGENT_PROTOCOL.md`](../AI_AGENT_PROTOCOL.md).

Ставит Claude Code, реализует Devin, проверяет Claude Code.

**Очерёдность:** не блокирует PUB-2 и PUB-3, но пункт 2 после PUB-3 придётся выполнять
заново — см. «Взаимодействие с PUB-3».

## Сначала — отзыв моей собственной находки

В прошлой сессии я сообщил владельцу, что `/swagger/index.html` отдаёт пустую
спецификацию. **Это неправда, находку снимаю.**

Я посмотрел `backend/docs/swagger.json` (там действительно ноль путей, файл сгенерирован
26 июля), увидел отсутствие аннотаций `@Router` — и сделал вывод, не посмотрев, чем
UI вообще питается. А питается он другим:

```go
// backend/cmd/server/router.go:97
r.GET("/swagger/*any", ginSwagger.WrapHandler(swaggerFiles.Handler,
    ginSwagger.URL("/openapi.yaml"),
    ...
r.StaticFile("/openapi.yaml", "./openAPI.yaml")
```

То есть UI указан на рукописный `backend/openAPI.yaml`, файл раздаётся статикой, путь
освобождён от обеих проверок авторизации (`middleware/jwt.go:58`,
`middleware/apikey.go:36`) и копируется в образ (`backend/Dockerfile:23`). Пустой
`swagger.json` к отображению отношения не имеет.

Это ровно тот случай, против которого написан раздел «Verifying a Finding» в
`.windsurfrules`: поиск находит кандидата и никогда не подтверждает его.

## Зачем задача

Разработчику Java-сервиса нужен договор, которому можно верить: посмотреть, что вернёт
создание заметки, и импортировать спецификацию в Postman для проб. Сегодня договор есть
и он в неплохом состоянии — но ничто не мешает ему разойтись с кодом молча, а первым
об этом узнает человек, который на него уже что-то написал.

## Что проверено исполнением

Собрал одноразовый тест в `backend/cmd/server/`, поднял роутер тем же `setupRouter`,
что и боевой, и выгрузил `r.Routes()`. Затем сверил с `openAPI.yaml` по парам
метод + путь, приведя `{id}` к `:id`.

```
операций в openAPI.yaml : 70
маршрутов в роутере     : 75  (из них 3 служебных: /openapi.yaml GET+HEAD, /swagger/*any)
задокументировано лишнего: 0
не задокументировано    : 2
    GET /api/v1/graph/analytics
    PUT /api/v1/links/:id
```

**Спецификация правдива.** Ни одного пути, которого нет в коде. Пробел — два маршрута.

**Ловушка, на которой я сам споткнулся и которую надо учесть в пункте 2.** Первый прогон
дал 69 маршрутов и «шесть путей в спеке, которых нет в коде» — все шесть про черновики.
Причина: я передал `nil` вместо обработчика черновиков, а эти маршруты регистрируются
условно. С `&drafthandler.Handler{}` их стало 75, и ложная находка исчезла. **Тест,
который строит роутер беднее боевого, покажет дрейф там, где его нет.**

Одноразовый тест удалён, `git status` чист.

## Что сделать

### 1. Задокументировать два недостающих маршрута

`GET /api/v1/graph/analytics` и `PUT /api/v1/links/{id}` — в том же стиле, что соседние
операции: теги, параметры, тела запроса и ответа, коды. Путь `/api/v1/links/{id}` в
файле уже есть (`backend/openAPI.yaml:1156`), добавляется только операция `put`.

### 2. Контрактная проверка против дрейфа

Go-тест в `backend/cmd/server/`, который строит роутер и сверяет `r.Routes()` с
`backend/openAPI.yaml`. Падает в обе стороны: маршрут без описания и описание без
маршрута — одинаково дефект.

Требования:

- **Роутер строится в полной комплектации.** Все обработчики, влияющие на состав
  маршрутов, передаются ненулевыми — см. ловушку выше. Если появится ещё один условно
  регистрируемый обработчик, тест обязан его учитывать.
- **Служебные маршруты исключаются явным списком** (`/swagger/*any`, `/openapi.yaml`), с
  комментарием, почему каждый в нём. Список коротким не будет случайно — он должен быть
  коротким намеренно.
- **Нижняя граница на число сверенных маршрутов**, как в
  `TestNoteIDRoutesRequireAccessGuard`: тест, который однажды не найдёт ни одного
  маршрута и останется зелёным, ничего не сторожит.
- Сравнение по паре метод + путь, `{param}` приводится к `:param`.
- Сообщение об ошибке называет конкретный маршрут и сторону расхождения. «Спецификация
  разошлась с кодом» без имени маршрута бесполезно.

**Доказать мутацией, обе стороны:**

1. добавить в роутер маршрут, которого нет в спецификации, — тест краснеет и называет
   его;
2. удалить из `openAPI.yaml` операцию существующего маршрута — тест краснеет и называет
   её.

Обе мутации откатить, приложить вывод.

### 3. Судьба пакета `backend/docs`

Сгенерированные `docs.go`, `swagger.json`, `swagger.yaml` от 26 июля содержат ноль
путей, подключены слепым импортом (`backend/cmd/server/main.go:16`) и копируются в
образ (`backend/Dockerfile:24`). UI ими не пользуется.

Убрать: пакет, слепой импорт и строку `COPY` из `Dockerfile`. Пустая спецификация,
лежащая рядом с настоящей, — приглашение однажды перепутать.

**Осторожно:** слепой импорт регистрирует спеку в swaggo, и по `/swagger/doc.json` она
отдаётся. Проверить живьём, что после удаления UI по-прежнему открывается и показывает
70 операций, — это часть критериев приёмки, а не формальность.

### 4. Передача второму разработчику

Общего документа об API в `docs/` нет: есть только
[`../API_ERRORS_EN.md`](../API_ERRORS_EN.md) про ошибки. Завести новый
`docs/API_EN.md` по принятому в проекте именованию (`ARCHITECTURE_EN`,
`DEPLOYMENT_EN`, `CONFIGURATION_EN`) и добавить строку в указатель
[`../README.md`](../README.md). Содержание короткое:

- где открыть UI: `http://localhost:8080/swagger/index.html` (порт сверить с
  `docker-compose.dev.yml`, не писать по памяти);
- откуда взять сам файл: `GET /openapi.yaml`, он же `backend/openAPI.yaml`;
- как импортировать в Postman: коллекция создаётся из OpenAPI напрямую, отдельный
  экспорт коллекции заводить не нужно и не надо — второй артефакт с тем же содержимым
  разойдётся с первым;
- как авторизоваться для проб: где взять токен, какой заголовок, что часть маршрутов
  открыта анонимно после PUB-1.

Текст — на английском, как остальная продуктовая документация.

## Взаимодействие с PUB-3

PUB-3 переименовывает `/api/v1/graph/all` в `/graph/public`. В спецификации этот путь
описан (`backend/openAPI.yaml:1659`). После PUB-3 проверка из пункта 2 обязана
покраснеть, если спецификацию не поправили, — это хороший признак, а не помеха.
Если PUB-3 делается раньше, переименование в `openAPI.yaml` входит в неё.

## Ограничения

- **Аннотации `@Router` не заводить.** Рукописная спецификация — источник правды;
  генерация из кода означала бы переписать 70 операций и получить второй источник.
  Решение зафиксировать в шапке `openAPI.yaml` одной строкой, чтобы следующий не начал
  генерацию заново.
- Существующие описания не переписывать, кроме двух добавляемых операций.
- Personal-стек не трогать.

## Критерии приёмки

1. `openAPI.yaml` описывает все маршруты роутера, кроме служебных; расхождений ноль.
2. Контрактный тест есть, зелёный, и **обе** мутации из пункта 2 ловятся с указанием
   конкретного маршрута; вывод приложен.
3. Тест строит роутер в полной комплектации: добавление условно регистрируемого
   обработчика не создаёт ложного расхождения.
4. Пакет `backend/docs`, слепой импорт и строка `COPY` убраны.
5. **Живая проверка:** стек поднят, `/swagger/index.html` открывается, показывает
   операции, и `GET /openapi.yaml` отдаёт файл с кодом 200. Свидетельство — в
   [`../MANUAL_TEST_FEEDBACK.md`](../MANUAL_TEST_FEEDBACK.md), поле «Screenshot / Logs».
6. Раздел о передаче написан, порт и URL проверены запуском, а не памятью.
7. `check-all` зелёный.
