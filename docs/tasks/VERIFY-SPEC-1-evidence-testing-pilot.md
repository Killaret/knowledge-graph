# VERIFY-SPEC-1. Пилот доказательного тестирования на одной задаче

Статус: **бэклог** — владелец согласовал пилот 2026-11-14. Задачу для пилота выбирает он (см. «Что
решает владелец»). Постановка — Claude Code, 2026-11-14. Откуда взялось — [`RULES-IMPORT-1`](RULES-IMPORT-1-external-skill-set.md), п. 9.

## Что это

Методика `verify-by-spec` из набора скиллов, который передал владелец. Тест не задаёт поведение, а
добывает доказательство, что система соответствует критериям постановки. Подгонку результата
методика делает дороже честного пути. Механика:

1. **Инварианты до тестов.** Каждый критерий приёмки превращается в утверждение «при X наблюдается Y»
   и в то, что его опровергает. Файл инвариантов ревьюит не исполнитель и коммитит отдельно, раньше
   тестов.
2. **Журнал прогона.** Тест пишет в `run-<дата>.jsonl` наблюдения из сырых данных системы: ответ
   API, строку БД через `SELECT`, строку лога. Пишет до assert, чтобы падение не теряло наблюдение.
   Схема — `run-schema.json`.
3. **Вывод делает скрипт.** `check-run.py` выносит итог по журналу, а не по assert. Он же ловит
   тесты, закоммиченные после прогона (`+wt`), паузы по таймеру и изменённые тесты без `why`. Возможные
   итоги:
   - `доказано: подтверждено`;
   - `доказано: опровергнуто`;
   - `нестабильно`;
   - `не доказано`;
   - `не проверено`;
   - `вопрос к спецификации`.
4. **Аудит.** `reread.py` перечитывает первичные данные по ссылкам `ref` из журнала и сверяет их с
   записанным. Так ловится выдуманное наблюдение.
5. **Два уровня.** Полный — безопасность, глобальное действие, зависимость от времени или порядка,
   решение о выпуске. На полном уровне добавляются отрицательный контроль поломкой стенда и два
   прогона в разном порядке. Базовый — всё остальное.

## Чем отличается от того, что у нас уже есть

| | Сейчас (`.windsurfrules` на `ai-agents`, `kg-work`) | `verify-by-spec` |
|---|---|---|
| проверка, что тест ловит дефект | мутация реального пути, зелёная мутация — находка (урок 2026-09-23) | поломка стенда из каталога профиля; по смыслу то же |
| тесты второй фазы | атака на допущения реализации, запись попыток в findings | нет отдельного понятия |
| критерии не правит исполнитель | `kg-work`, шаг 4 (урок PUB-3) | инварианты коммитятся до тестов, поздний инвариант не считается |
| итог ревью | вердикт ревьюера по прогону `check-all.ps1` и диффу | итог — только вывод `check-run.py` по журналу |
| «не смог доказать» | явного итога нет | нормальный итог, за него не отклоняют |
| перепроверка через месяц | по истории git | журнал с `ref` на первичные данные и версией проверяющего |

Новое для нас — пункты 1–4 механики. Отрицательный контроль у нас уже есть в виде мутаций.

## Что сделать

1. **Взять методику в репозиторий для пилота, не как скилл.** Каталог `scripts/verify/`:
   `check-run.py`, `reread.py`, `run-schema.json` и их тесты, `test_check_run.py` и `test_reread.py`.
   По заявлению набора тестов 85. Прогон — `python -m unittest` в этом каталоге, он должен быть
   зелёным до начала пилота. Методика как текст — `docs/operations/VERIFY_BY_SPEC.md`, ядро
   `SKILL.md` и справочники шагов с убранными упоминаниями треков и аналитика. Архив — у владельца,
   Claude Code передаст файлы.
2. **Профиль Knowledge Graph** — `docs/operations/VERIFY_PROFILE_KG.md` по заготовке
   `profile-template.md`:
   - окна и писатели: HTTP-ответ backend на тест-стеке `:18083`, PostgreSQL `:15434` только
     `SELECT`, лог backend, UI через Playwright;
   - каталог поломок: какие сервисы тест-стека можно остановить или испортить конфигом и какой
     инвариант должен опровергнуться;
   - ловушки: Windows, cp1251 в выводе Python (сам `board-status.py` из набора лечит это
     `reconfigure`), порты тест-стека из `.windsurfrules`.
3. **Пилот на одной задаче Devin.** До тестов: файл инвариантов, ревью Claude Code, отдельный коммит.
   Затем тесты, прогон, журнал, вывод `check-run.py` в постановке задачи. Ревью Claude Code — по выводу
   скрипта и журналу. Плюс выборочный аудит `reread.py`.
4. **Замер в этой постановке после пилота:**
   - сколько времени ушло на инварианты, обвязку журнала и профиль сверх обычной задачи;
   - что нашёл скрипт или аудит из того, чего не нашли бы мутации и `check-all`. «Ничего» — тоже
     результат;
   - какие правила набора на нашем стеке не сработали или мешали.

## Что решает владелец

- **Задача для пилота.** Предложение — следующая задача Devin, где есть безопасность, порядок или время
  (полный уровень), например одна из строк `SYNC-1` или `NOTE-DELETE-1-TAIL`. Простая задача проверит
  только базовый уровень.
- **После замера:** вводить ли методику и на каком уровне. Если вводить — норма в `.windsurfrules`, скилл
  `kg-verify` с якорями на наш стек, производные по `CLAUDE.md`.

## Чего не делать

- Не вводить методику для всех задач до замера.
- Не менять правила `check-run.py` под прогон, который он оценивает. Правила скрипта меняет не тот, чей
  прогон под проверкой.
