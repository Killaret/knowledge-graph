Единый рабочий документ. Заменяет промежуточные `AI_ECOSYSTEM_REVIEW.md` и `PROCESS_REVIEW.md`.

Дата: 2026-09-05. Ветка `feat/2d-adaptive-fog`, коммит `c765fb0`. Нормативный источник проекта — `.windsurfrules`; этот документ его не отменяет.

## Резюме

Проверены: цепочка визуальной верификации, канонический регрессионный цикл, тестовая пирамида, гейты CI, инструкции для агентов, скиллы.

Пять выводов, определяющих приоритет работ:

1. **Визуальная проверка 3D не измеряет 3D.** Скриншот снимается до отрисовки сцены, поэтому эталон в Argos — снимок экрана загрузки. Правки графики в него не попадают физически.
2. **Канонический регрессионный цикл сообщает об успехе при провале тестов.** Integration, E2E, BDD и визуальные тесты в `run-full-test-cycle.ps1` при падении только печатают WARNING, цикл продолжается, а на выходе может быть автокоммит с сообщением «successful regression cycle».
3. **Пороги покрытия не действуют.** Frontend-пороги 70% объявлены в `vitest.config.ts`, но CI запускает прогон без coverage. Для backend порога в CI нет вообще, хотя документация обещает 70% при минимуме 60%.
4. **Роль Claude Code не заведена, инструкции разошлись.** Нет `CLAUDE.md` и `.claude/`; таблицы ролей в четырёх файлах не совпадают; нормативные факты продублированы копированием без проверки согласованности.
5. **Кастомные скиллы принадлежат другому проекту** и недоступны второму агенту, поскольку хранятся вне репозитория.

Первые три — причина того, что цикл правок по графу не сходится: система сообщает «зелено» там, где ничего не проверено.

## Часть A. Верификация и тестирование

### A-1 (критично). Скриншот 3D снимается до рендера сцены

`frontend/tests/visual/visual-regression.spec.ts:141`

```ts
test("3D Graph - renders 3D view", async ({ page }) => {
  await page.goto("/graph/3d" + STABLE_RENDER);
  const viewer = page.locator('[data-testid="graph-3d-viewer"]');
  await expect(viewer).toBeVisible({ timeout: 15000 });
  await argosScreenshot(page, "3d-graph-view", { fullPage: true });
});
```

`data-testid="graph-3d-viewer"` висит на внешнем контейнере `Graph3DViewer.svelte:74`. Он рендерится сразу при монтировании — до проверки WebGL, до динамического импорта `Graph3DScene.svelte`, до создания движка Three.js и до первого кадра. Тест дожидается появления обёртки и немедленно снимает кадр.

Для 2D сделано верно (`waitForGraph` в том же файле):

```ts
const canvas = page.locator('[data-testid="graph-canvas"][data-test-stable="true"]');
await canvas.waitFor({ timeout: 15000 });
```

Атрибут выставляется в `GraphCanvas.svelte:256` после сходимости симуляции. Для 3D аналога нет: ни `data-test-stable`, ни ожидания коллбэка `onReady`, который в компоненте объявлен и тестами не используется.

**Следствие:** эталон `3d-graph-view` — снимок состояния загрузки. Изменения материалов, тумана, камеры, масштаба узлов в него не попадают. Диффа нет, потому что нечему меняться. Наблюдение «снимки одинаковые, хотя должно быть разное» объясняется полностью этим пунктом.

### A-2 (критично). `stableRender` в 3D не поддержан, признак теста определён неверно

`?stableRender=true` обрабатывается только в 2D (`GraphCanvas.svelte:176-180`). В 3D-ветке параметра нет: анимация, автоповорот камеры и переходы тумана продолжают идти во время съёмки.

Выключатель анимации в 3D завязан на другое условие — `Graph3DScene.svelte:33`:

```ts
const isTest = typeof process !== "undefined" && process.env?.VITEST === "true";
```

Это признак Vitest, то есть unit-окружения. В браузере под Playwright `process` не определён, `isTest` всегда `false`, `disableAnimation` не включается, `simulateToStable()` не вызывается. Механизм детерминизма, заложенный в движок (`engine.ts:133`), в сквозных тестах не срабатывает ни разу.

### A-3 (критично). Регрессионный цикл сообщает об успехе при провале тестов

`scripts/testing/run-full-test-cycle.ps1` — канонический прогон из `.windsurfrules`. Следующие фазы при ненулевом коде выхода печатают предупреждение и цикл продолжают:

| Фаза | Строка | Поведение при падении |
|---|---|---|
| Seed тестовых данных | 141 | WARNING, продолжает |
| Backend integration tests | 184 | WARNING, продолжает |
| E2E, SKIP_AUTH | 257 | WARNING, продолжает |
| BDD, SKIP_AUTH | 265 | WARNING, продолжает |
| Seed real-auth | 290 | WARNING, продолжает |
| E2E, real auth | 299 | WARNING, продолжает |
| Seed visual | 345 | WARNING, продолжает |
| Argos visual tests | 361 | WARNING, продолжает |

Итоговый блок `[Final Summary]` печатает список галочек безусловно; агрегирующей проверки результатов фаз нет.

Хуже: шаг 27 подписан комментарием «Auto-commit if all checks passed», но условие содержит только флаг `-AutoCommit` и признак `$devStateChanged` — результаты тестов не учитываются:

```powershell
} elseif (-not $devStateChanged) {
    git add -A
    ...
    $commitMessage = "test: successful regression cycle..."
```

То есть прогон, в котором упали E2E, BDD, интеграционные и визуальные тесты, может закончиться коммитом `git add -A` с сообщением об успешной регрессии. Флаг по умолчанию выключен, но семантика сообщения и `add -A` опасны сами по себе.

### A-4. Визуальная регрессия не запускается на PR

Джоба `visual-regression` объявлена в `.github/workflows/main.yml`, триггер — `push` в `main`. На PR (`ci.yml`) выполняются core-checks, валидация конфига и compose, smoke-тесты; визуальных проверок нет. Визуальный контроль происходит после слияния.

### A-5. Пороги покрытия объявлены, но не применяются

`frontend/vitest.config.ts:96` задаёт пороги 70% по строкам, функциям, веткам и операторам при `all: true`. Пороги действуют только при прогоне с coverage, а `_core-checks.yml:214` запускает `npm run test:unit`, то есть `vitest run` без покрытия. Скрипт `test:coverage` существует и в CI не вызывается.

Для backend в `_core-checks.yml` выполняется `go test -v ./...` без флагов покрытия и без порога, хотя `.windsurfrules` и `MASTER_PROMPT.md` обещают «Target 70% coverage, min 60%».

Фактически ни одного порога покрытия в CI не применяется.

### A-6. WebGL в headless-CI не гарантирован

`Graph3DViewer.svelte:43` при недоступности WebGL показывает оверлей ошибки вместо сцены. В `visual-regression` браузер ставится как `npx playwright install --with-deps chromium` на ubuntu-раннере без GPU-флагов и без проверки контекста. Если WebGL не поднимется, тест из A-1 всё равно пройдёт: обёртка видима, снимок сделан, на нём — сообщение об ошибке. По зелёному CI отличить это от нормы невозможно.

### A-7. Осиротевшие артефакты тестов

Каталоги эталонов без спеков в `frontend/tests`:

| Каталог | Файлов |
|---|---|
| `graph-visual.spec.ts-snapshots` | 9 |
| `graph-visual-mock.spec.ts-snapshots` | 9 |
| `graph-visual-isolated-new.spec.ts-snapshots` | 9 |
| `graph-visual-isolated.spec.ts-snapshots` | 1 |
| `graph-simple.spec.ts-snapshots` | 1 |

29 эталонов, которые ни с чем не сравниваются; визуальные тесты по графу переписывались минимум четыре раза.

Аналогично в BDD: `frontend/tests/features/step_definitions/graph_3d_loading.steps.ts` существует, а среди `.feature`-файлов только `graph_2d_list.feature` и `login.feature`, и ни в одном нет 3D-сценариев. Шаги написаны, сценариев нет — читающий репозиторий делает вывод, что 3D покрыт BDD.

### A-8. Тег `@3d` исключён из прогонов, но им не помечен ни один тест

`playwright.config.ts`, проект `chromium-skip-auth`: `grepInvert: /@3d|@visual|@auth-real|@manual|@canvas/`. Поиск по `frontend/tests` не находит ни одного теста с тегом `@3d`. Сквозного покрытия 3D не существует, кроме нерабочего визуального теста из A-1.

### A-9. `ARGOS.md` описывает не тот сценарий, который реализован

Документ в списке сценариев указывает для 3D «Frozen notice redirect to 2D graph». В коде — `renders 3D view` со снимком `/graph/3d`. Агент, читающий `ARGOS.md` для оценки покрытия, получит неверную картину.

### A-10. Базовая ветка сравнения — `ai-agents`

`ARGOS_REFERENCE_BRANCH: ai-agents` в `main.yml`, при том что работа ведётся в `feat/*` от `main`. Требует проверки на актуальность эталона.

## Часть B. Обвязка агентов

### B-1 (критично). Разрешения Devin противоречат правилу сохранности данных

`.devin/config.local.json` содержит в allowlist `Exec(rm)`, `Exec(rmdir)`, `Exec(del)` без ограничений по путям. `.windsurfrules` объявляет удаление томов `pgdata_personal` / `redisdata_personal` / `mongodbdata_personal` недопустимым без явного разрешения и бэкапа. Единственный работающий барьер сегодня — текст в документации.

Косвенный признак, что риск не теоретический: `.windsurf/PROTECT.md` с содержимым «Do not delete».

### B-2. Роль Claude Code не заведена

Нет `CLAUDE.md`, нет `.claude/`. В таблице ролей `.windsurfrules` Claude отсутствует; в `PROJECT_REVIEW §16` упомянут как получатель промптов. Сессия стартует без проектных правил, разрешения на прогон тестов запрашиваются заново каждый раз.

### B-3. Одна система Cognition описана как два независимых агента

`AGENTS_EN.md` содержит отдельные разделы «Windsurf SWE 1.7 Max» (primary implementation agent) и «Devin» (CLI repository agent) с разными зонами. Это две поверхности одного продукта. Читающий агент делает вывод о четырёх участниках вместо трёх.

### B-4. `AGENTS.md` и `AGENTS_EN.md` — не перевод, а разные документы

Только в EN: Task Routing, Verification, Language Policy, Inactive Tooling. Только в RU: Instruction Files, Required Workflow. Объём отличается в полтора раза; расхождение ничем не детектируется.

### B-5. Нормативные факты размножены копированием

`go test ./...` встречается в 16 markdown-файлах, версии стека — в 8, правило про personal-тома — в 10. Внутри AI-обвязки стек продублирован четырежды: `.windsurfrules`, `SKILL.md`, `MASTER_PROMPT.md`, `MASTER_PROMPT_RU.md`. Проверки согласованности нет ни в CI, ни в хуках.

### B-6. `.windsurfrules` перегружен изменчивыми данными

460 строк, единственная точка входа. Раздел «Current handler decoupling status» перечисляет конкретные файлы с галочками — такой список устаревает быстрее остальных правил и тянет за собой весь документ.

### B-7. Протокол взаимодействия отсутствует

Роли описаны, порядок работы — нет. В репозитории не зафиксировано: кто ставит задачу, кто исполняет, кто верифицирует, через какой канал передаётся состояние, что делать при одновременной работе двух агентов. `PROJECT_REVIEW_AI_AGENTS.md` фактически работает шиной состояния, но обязанность дописывать в него итог сессии нигде не закреплена.

### B-8. Прочее

- `.kilo/` — конфиг Kilo Code с метаданными четырёх worktree (июнь 2026), при том что политика перечисляет Continue/Koda как неиспользуемые. В git не попадает (свой `.gitignore`), сами worktree удалены.
- `.devin/test_permissions.txt` закоммичен и не несёт нагрузки.
- `ANALYSIS_PROMPT.md` дублирует семь ограничений из `.windsurfrules`, одновременно требуя его прочитать.
- До 2026-09-05 все коммиты шли под одной identity, различить работу агентов по истории было невозможно. С `9ee17b1` коммиты Claude Code помечаются автором `Claude Opus 5`.
