### **4. A-1: 3D Readiness Signal**
**Статус:** В работе (блокирует visual baselines)  
**Кто:** Claude Code  
**Оценка:**
```
Scope: LARGE
Effort: 12-16 часов (архитектурная переделка сигнала готовности)
Risk: HIGH (меняется сигнал для всех остальных тестов)
Impact: CRITICAL (честная 3D визуалка)
```

**Суть:** 3D граф показывается, но сигнал готовности мёртв — может быть 2 сек, может быть 20 сек, нет детерминизма

**Моя оценка:**
- 🔴 **Это корневая проблема.** Визуальный baseline без честного сигнала готовности = сравниваем скриншоты в момент, когда граф не загрузился. Все три базелайна могут быть разные, но все "правильные", потому что moment не определён.
- ✅ **Решение правильное:** нужен sidelining (side-channel) сигнал готовности, не полагаться на UI элементы
- ⚠️ **Но рискованно:** изменит сигнал для **всех остальных тестов** (BDD, регрессионные, smoke). Велик шанс сломать то, что работало.
- **Смысл:** Получить детерминированный момент, в который граф полностью загружен и можно снимать скриншот

**Риск-анализ:**
- Если новый сигнал загруженнее старого → старые smoke-тесты начнут timeout'ить
- Если новый сигнал быстрее → baselines будут неполные (граф ещё не отрисовался)
- Нужны adversarial phase (намеренно сломанные тесты) на разных скоростях (slow network, slow GPU, slow CPU)

**Рекомендация:**  
Перед merge: прогнать A-1 на машине с deliberately degraded network (throttle 3G) и сломанным GPU. Если всё красное → хорошо, нашли истину. Если зелёное → new signal еще детерминичнее, чем казалось.

## 💭 ФИЛОСОФИЯ ПРОЕКТА

### Что я вижу в структуре работы

Этот проект демонстрирует **редкую чистоту процесса AI-collaboration**:

1. **Честность сигналов.** Не скрывают красное под зелёным. Timeout'ы ловят, exit code'ы правдивые, тесты не мокируют реальность.

2. **Разделение ответственности.** Claude не реализует (может закопаться в коде), Devin не решает архитектуру (может выбрать легкий путь), Owner решает (может быть субъективен, но его воля). Каждый в своей роли.

3. **Версионирование решений.** Все решения в DECISIONS.md, обоснование не дублируется, ссылка вперёд к code — это не технический долг, это чистая архитектура.

4. **Adversarial phase.** В `.windsurfrules` записано: **обязательно написать падающие тесты**, чтобы убедиться, что функция ловит баги. Это мудро.

### Что мне кажется рискованным

1. **Ownership фич не явный.** "Кто решит, что PUB-3 готова?" — Claude. Но Claude не видит комментария владельца, Devin не уверен, висит. Нужен explicit CODEOWNER или RACI матрица.

2. **Criteria непока.** "Когда A-1 можно считать готовой?" — в description неясно. Можно измерить? Проверить? Найди критерий и запиши.

3. **Feature creep.** 3 из 4 обсуждаемых задач (COMET, NOTE-QUALITY, ARCHIVE) — это явно 1.1. Почему они в очереди 1.0? Нужен explicit freeze date для 1.0 функционала.
