## S. Безопасность

Всё в этом разделе безопасно, пока пользователь один и стек на localhost. S-1…S-4 блокируют любой мультипользовательский деплой.

### S-1 (критично). Учётка с опубликованным паролем вшита в схему, откат её не удаляет

`migrations/019_add_test_user.up.sql:8-15` безусловно вставляет `test_user` с UUID из нулей и Argon2id-хешем пароля, названного в комментарии на строке 6 — `"test"`. Гейта по окружению нет: в `internal/config/config.go` понятия production не существует, ни одной проверки. Миграция применяется одинаково на всех стеках.

Смягчает: роль не назначается, `role_id` остаётся `NULL` (миграция 016 проставляет роли раньше). Это не админский доступ.

Усугубляет: **откат не работает.** `019_add_test_user.down.sql:2` удаляет `...0001`, тогда как up-миграция вставляет `...0000`. Строки с таким id нет, `migrate down` оставляет учётку в базе.

### S-2 (критично). SKIP_AUTH снимает изоляцию данных, а не только логин

`infrastructure/db/postgres/note_repo.go:40-44` — при флаге в контексте запроса `applyNoteScope` возвращает запрос без фильтра по владельцу, то есть заметки всех пользователей. Флаг задаётся обычной переменной окружения (`config.go:455`) без ограничений по профилю.

Слой, где это живёт, — самый слабо покрытый нетривиальный пакет бэкенда (44,8%).

### S-3 (критично). nginx пробрасывает клиентский `X-Internal-Auth` в graph-service

`nginx.conf:52` передаёт заголовок как есть, `nginx.conf:36,57` явно разрешают его браузеру через CORS. `services/graph-service/internal/api/auth.go:118-122`: при совпадении внутреннего токена сервис доверяет заголовку `X-User-Id` и отдаёт граф названного пользователя. Прочие клиентские заголовки nginx тоже не вычищает.

Публичный слушатель и внутренний канал не разделены. Сейчас смягчено тем, что `GRAPH_SERVICE_INTERNAL_TOKEN` по умолчанию пуст и пустой токен отбрасывается (`auth.go:110-112`) — защита держится на том, что фичу не включили.

### S-4 (критично). Приватные ответы отдаются с `Cache-Control: public`

`cmd/server/router.go:79-84` — middleware выставляет `public, max-age=N` безусловно, до вызова хендлера, поэтому заголовок получают и ответы авторизованных пользователей. Применена на `/notes/:id` и `/notes` (60), `/notes/search` (30), `/notes/:id/graph` и `/graph/*` (300), `/me/graph/cached` (60) — строки 159, 166-168, 177-181.

Любой общий кеш на пути вправе сохранить ответ и отдать следующему запросившему.

**Проверено:** `GET /api/v1/graph/all` → `Cache-Control: public, max-age=300`.

### S-5. JWT принимается из query-строки

`middleware/jwt.go:141` — третьим способом извлечения идёт `?token=`. Токен оседает в access-логах nginx, истории браузера и уходит в `Referer` на сторонние домены. Заголовка и HttpOnly-куки достаточно.

Там же (`jwt.go:129-130`): `Authorization` без префикса `Bearer` принимается как сырой токен.

### S-6. PKCE методом `plain`, проверка `state` привязана к флагу PKCE

`handlers/auth/handler.go:635` — `code_challenge_method=plain`, при котором challenge равен verifier и защита от перехвата кода обнуляется. Нужен `S256`.

`handler.go:652-661` — `state` проверяется только внутри ветки `if h.cfg.PKCEEnabled && h.tokenStore != nil`. По умолчанию PKCE включён (`config.go:458`), поэтому CSRF-защита сейчас работает, но `PKCE_ENABLED=false` молча снимает и её. Две разные защиты не должны висеть на одном флаге.

### S-7. nginx не делает ничего, кроме проксирования

Нет TLS, `client_max_body_size`, ограничения скорости на входе и ни одного заголовка безопасности (`Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security`). Белый список CORS (`nginx.conf:11-15`) покрывает только 18081, тогда как фронт живёт ещё на 5173 и 18084.

## F. Функциональные дефекты

### F-1 (критично). Вход через Яндекс сломан в трёх местах

Четыре источника расходятся:

| Источник | Значение |
|---|---|
| `frontend/src/shared/api/auth.ts:82` | зовёт `v1/auth/yandex/login` |
| `cmd/server/router.go:109` | регистрирует `/api/v1/auth/yandex` |
| `backend/openAPI.yaml:219` | документирует `/api/v1/auth/yandex` |
| `middleware/jwt.go:44` | вносит в исключения `/api/v1/auth/yandex/login` |

То есть реальный маршрут в SkipPaths не попал, а в исключениях стоит несуществующий путь.

**Проверено на живом стеке:** оба адреса отвечают **401** анонимному пользователю. До 404 дело не доходит — глобальный `JWTAuth` обрывает запрос раньше, чем Gin отдаёт NoRoute. Починка одного лишь пути на фронте проблему не решает: реальный маршрут тоже закрыт.

Третий слой расхождения — формат: `handler.go:639` отвечает `302`-редиректом на `oauth.yandex.com`, а клиент ждёт JSON `{url}`.

Юнит-тест `frontend/src/shared/api/auth.test.ts:153` утверждает, что клиент зовёт `v1/auth/yandex/login`, и он зелёный: тест проверяет мок, а не систему, и фиксирует сломанный контракт как эталон.

README при этом рекламирует «OAuth2 (Yandex)» как готовую возможность.

### F-2. Отладочные маршруты в продовой сборке

`routes/test/`, `routes/test/link-pair/`, `routes/test/isolated-node/` — обычные страницы SvelteKit без гейта по окружению.

Там же двенадцать реактивных выражений Svelte 4 `$:` и store `$page` (`test/link-pair/+page.svelte:27-52`, `test/isolated-node/+page.svelte:31-41`) — прямое нарушение `.windsurfrules:105-111`, где Svelte 4 помечен как «NEVER use».

## P. Обвязка агентов

### P-1 (критично). ЗАКРЫТО в `4f0f515`. Барьер сохранности данных выводил агента из строя

`.claude/settings.json:41` вызывает хук относительным путём — `python scripts/devops/guard-personal-data.py`, — а исполняется он в текущем каталоге Bash-инструмента. Любая команда `cd backend` ломает Bash **до конца сессии**, включая `cd ..`, которая могла бы всё вернуть: команда восстановления блокируется тем же хуком.

`cd backend && go test ./...` предписана `README.md`, `.windsurfrules:363` и `.devin/prompts/MASTER_PROMPT.md`. Штатная инструкция проекта гарантированно ломает инструмент.

Воспроизведено в сессии аудита: Bash отвалился на второй команде, часть работы пришлось делать чтением файлов; прогнать тесты удалось только после внешнего сброса рабочего каталога, дальше — обходя дефект флагами `go -C` и `npm --prefix`.

Сам скрипт написан устойчиво: `guard-personal-data.py:43-55` находит корень через `git rev-parse`. Хрупок ровно вызов.

**Закрыто до постановки.** В `4f0f515` путь заменён на `python "$(git rev-parse --show-toplevel)/scripts/devops/guard-personal-data.py"` — решение лучше предлагавшегося `$CLAUDE_PROJECT_DIR`, потому что не зависит от переменной окружения инструмента. В `test_guard_personal_data.py` добавлены проверки уровня процесса.

**Проверено Claude Code 2026-09-05:** из `backend/`, `frontend/` и `scripts/devops/` корень репозитория разрешается, безопасная команда проходит молча с кодом 0, `docker volume prune -f` блокируется. Постановка AUD-8 снята как неактуальная.
