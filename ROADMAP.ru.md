### Детали Cosmic Cockpit UI ("космическая кабина")

**Концепция:**

- Четыре выдвижные панели (верх, низ, лево, право) имитируют приборную панель звездолёта, как в игре «Космические рейнджеры».
- Наведение на край экрана выдвигает панель с задержкой 200–300 мс; панель можно «цеплять» за угол и тащить (drag-to-open).
- Якорь закрепляет панель, чтобы она не сворачивалась.
- Кнопка в нижней панели переключает режим «от первого лица» (fullscreen): все панели убираются, остаётся только граф.
- Тёмный фон с сеткой, неоновые акценты (циан/маджента), HUD-строка.

**Распределение по панелям:**

- **Левая панель:** навигация по кластерам, дерево заметок, переключение режимов графа (Force/Honeycomb/Radial/Orbital/Honeycomb 3D), фильтры по типам заметок (множественный выбор, анимация раскрытия сверху вниз).
- **Правая панель:** детали выбранной заметки, мини-граф связей, контекстные действия (редактировать, создать дочернюю заметку, добавить связь, опубликовать).
- **Верхняя панель:** поиск, глобальные фильтры, переключение 2D/3D, статус синхронизации.
- Контекстное меню на узле графа для создания дочерней заметки.
- Зона архивирования «Сингулярность» (Singularity) при перетаскивании; тип «Чёрная дыра» — строго «нерешённая задача», удаление через неё не работает.
- **Нижняя панель:** HUD — текущий кластер, количество заметок/связей, уровень «здоровья» графа, FPS, индикатор дельта-синхронизации, кнопка «от первого лица».

**Управление:**

- Hover с задержкой 200–300 мс.
- Drag-to-open за угол/край панели.
- Якорь — закрепить панель, чтобы не сворачивалась.
- Настройки в блоке UI: чувствительность, автосворачивание, reduced motion.

**MVP:**

- Статичный макет с четырьмя панелями.
- HUD-строка внизу.
- Фильтры типов заметок в левой панели с множественным выбором.
- Режим «от первого лица».
- Базовая анимация выдвижения.

**Зависимости:** FSD-рефакторинг виджетов, Graph-store.

**Связанный анализ:**

- [Анализ дублирования в UI и точек создания заметки](docs/UI_DUPLICATION_AND_NOTE_CREATION_ANALYSIS.md) — описывает дублирование, которое редизайн кабины должен устранить

**Примечание:** Космические уведомления/тосты не входят в MVP Cosmic Cockpit; они реализуются отдельной необязательной подсистемой.

### Аудит и оптимизация потребления ресурсов

**Найденные проблемы (быстрый аудит):**

- **Frontend bundle:** `three` импортируется как `import * as THREE from "three"` в 7+ файлах — в bundle может попасть вся библиотека. Bundle analyzer не настроен.
- **Frontend runtime:** `frontend/src/features/home-page/home-page.svelte.ts` использует `setInterval` для delta-polling; графический animation loop реализован в `frontend/src/entities/graph-canvas/lib/animation.ts` и используется `GraphCanvas.svelte` — нужно проверить корректную очистку жизненного цикла.
- **Лимиты графа:** на фронте `max_nodes: 500`, а в `graph_service.full_limit: 1000` — разрыв лимитов может приводить к OOM или таймаутам.
- **Backend поиск:** `note_repo.go` использует `plainto_tsquery` + `ts_rank` — требуется проверка индексов и стоимости запросов.
- **Backend кэш:** `graph_service` кэширует full layout с TTL 300 секунд; большие графы давят на память Redis.
- **Docker dev stack:** для backend/frontend в `docker-compose.yml` нет memory limits (только test stack имеет 512M–2G).
- **Тестирование:** performance- и memory-тесты в `API_TEST_COVERAGE_PLAN.md` отмечены как `⏳`; в CI нет проверки bundle size.

**План действий:**

1. Добавить `rollup-plugin-visualizer` или `vite-bundle-analyzer` в `frontend/package.json`.
2. Профилировать загрузку 3D-графа на 500+ нодах и замерить FPS по порогам из `knowledge-graph.config.json`.
3. Проверить/добавить `GIN`/`tsvector` индексы для full-text search.
4. Поставить memory limits для backend/frontend в `docker-compose.yml` (dev).
5. Добавить baseline performance smoke tests (загрузка большого графа, бюджет bundle size).

## 🧩 Graph Service: план стабилизации и развития

> **Контекст:** согласно ADR 013, основной бэкенд должен публиковать события `Note*`/`Link*` и перестать быть основным источником графа — `graph-service` берёт на себя расчёт раскладок, кэширование и аналитику. Основной бэкенд сохраняется только как **fallback** при недоступности `graph-service`.

### 1. Событийная инвалидация и fallback-модель

- `note_handler` и `link_handler` публикуют события `NoteCreated`/`Updated`/`Deleted` и `LinkCreated`/`Updated`/`Deleted` через `internal/infrastructure/events/publisher.go` в Redis channel `graph:events`.
- `graph-service` (`internal/subscriber/pubsub.go`) слушает channel и инвалидирует ключи `graph-service:full:*`, `graph-service:note:*`, `graph-service:delta:*`.
- Эндпоинты основного бэкенда `/graph/all`, `/me/graph/fresh`, `/me/graph/cached` становятся **fallback**: frontend/graphql proxy проверяет health `graph-service` и переключается на backend только при недоступности.
- Задача критическая, так как сейчас `events.Publisher` не подключён к хендлерам, и кэш `graph-service` инвалидируется только по TTL.

### 2. Авторизация и user-scoped фильтрация в graph-service ✅

- Добавить JWT-middleware в `graph-service` для HTTP и gRPC.
- `user_id` брать из токена, убрать query-param `user_id` из публичных HTTP-запросов.
- Добавить фильтр `creator_id` в SQL-запросы `postgres_client.go` (`services/graph-service/internal/db/postgres_client.go`) для всех `notes`/`links`.
- Анонимные/неаутентифицированные запросы по умолчанию фильтруются по `is_public = true`, чтобы исключить утечку приватных заметок.
- Прокси `frontend/src/hooks.server.ts` должен передавать `authorization` либо signed `x-internal-auth` header в `graph-service`.
- Публичный граф вынести в отдельный endpoint (`/api/v1/graph/public`) с фильтром `is_public = true`.

### 3. Унификация графового API и устранение двойной загрузки ✅

- Стандартизировать поля ответа graph-service: `id`, `title`, `type`, `source`, `target`, `weight`, `link_type`.
- Убрать fallback-нормализацию (`id/Id/ID`, `source/source_note_id`) в `frontend/src/routes/+page.svelte`.
- `+page.svelte` делает один запрос `getGraphWithPreload()` (который при отсутствии кэша загружает `getFullGraphData()`) в `Promise.all([getNotes(), getGraphWithPreload()])` для аутентифицированных пользователей; последовательный `getFreshGraph()` и повторный `loadGraphData()` удалены.
- Использовать `/api/v1/graph/delta?last_hash=` для инкрементальных обновлений через `PreloadService`.
- В `PreloadService` добавлен `seedGraph(graphData)`, чтобы любой ответ полного графа кэшировался с `lastHash` и мог применяться в дельта-обновлениях.

### 4. Graph analytics API

- Реализовать gRPC/HTTP методы `GetNeighbors`, `GetPath`, `GetRecommendations` в `graph-service`.
- HTTP endpoints:
  - `GET /api/v1/graph/note/:id/neighbors?depth=`
  - `GET /api/v1/graph/path?from=&to=`
  - `GET /api/v1/graph/recommendations?note_id=&limit=`
- Заменить backend BFS (`backend/internal/domain/graph/bfs.go`) и traversal-логику recommendation на вызовы `graph-service`.

### 5. Materialized view / графовый индекс

- Создать materialized view `note_links_closure` для транзитивного замыкания связей.
- Обновлять view по событиям `LinkCreated`/`LinkDeleted` (async через trigger или ASYNQ).
- Использовать view для `GetPath`, подсчёта `degree`, семантической кластеризации и Honeycomb-раскладки.

### 6. gRPC-web / SSE стриминг полного графа

- Для графов >500 узлов стримить `GetFullLayout` по чанкам через gRPC streaming или Server-Sent Events.
- Frontend постепенно отрисовывает узлы и связи (progressive rendering).
- Альтернатива для JSON-API: NDJSON streaming.

### 7. Улучшение layout-алгоритмов

- **Honeycomb View:** радиальная раскладка с центром в узле с максимальным `sum(weight)` и концентрическими кругами по порогам веса.
- **Force-directed 2D/3D:** заменить/дополнить текущий круг/спираль на физическую симуляцию на сервере.
- **Cosmic Navigator:** гибридная серверная 3D-раскладка (`layout=3d`) + клиентская релаксация `d3-force-3d`.

### Фаза 4: Космический навигатор (Spaceship) 🔴 Критическая

Статус: ⏳ Запланирована
Описание: 3D-визуализация графа знаний в виде космоса.

☑ Базовый 3D-рендеринг (Three.js) — разморожен и перенесён в features/graph-3d.
□ Orbital / Solar System 3D-режим — узлы распределены по орбитам вокруг центральной заметки или центра кластера. Орбиты = смысловые слои. Связи опциональны.
□ Honeycomb Stellaris 3D-режим — гексагональная сетка в 3D с изогнутыми светящимися трубками (гиперпространственные маршруты), как в Stellaris.
□ Динамическое переключение между режимами (2D/3D).
□ Серверная кластеризация (Louvain) для автоматического выделения смысловых слоёв и центров.
□ Кэширование кластеров в Redis, инвалидация по событиям.
□ Knowledge Voyager (Полёт по знаниям) — автопилотный полёт по кластерам по сплайн-траектории (`features/graph-3d/lib/autopilot.ts`), с подсветкой узлов, не открывавшихся N дней. Вау-эффект, требует 3D-режимов и кластеризации.
□ Ghost Notes (Призрачные заметки) — публичные заметки с похожими эмбеддингами появляются как полупрозрачные узлы в пространстве между кластерами (`GET /api/v1/graph/ghost-notes?context=clusterId`); пользователь может «захватить» узел в свой граф. Зависит от Knowledge Voyager и публичных заметок.

Статус: ⏳ Запланирована

## 🧪 Экспериментальное и идеи (Гипотезы и эксперименты)

Идеи, требующие проработки, прототипирования и проверки гипотез. Могут быть переведены в активные фазы после validation.

### Фаза 13: Производственная линия (Factory Line) 🟢 Низкий — Гипотеза

**Приоритет:** 🟡 Средний (после кластеризации и сот)
**Статус:** 💡 Идея
**Описание:** Режим визуализации графа как производственной цепочки (Factorio / Shapez).

- Заметки отображаются как «станки» с входами и выходами.
- Связи — конвейеры с анимацией движения (анимация только для связей в текущем viewport, fallback — статические стрелки).
- Типы заметок мапятся на роли: `raw` (сырьё / черновик), `processor` (обработчик / анализ), `product` (продукт / вывод). Источник роли — существующее поле `note.type` или новый тег `factoryRole`.
- Обрыв цепи подсвечивается как «брак».
- Метрика продуктивности: число завершённых цепочек.
- **Гипотеза:** метафора завода мотивирует замыкать цепи и вести гигиену заметок.
- **MVP:** режим отображения с прямоугольными узлами и анимированными стрелками.
- **Зависимости:** нет (отдельный режим визуализации, но требуется ролевая классификация заметок).
- **Validation:** >30% новых связей замыкаются в завершённые цепочки за месяц; режим используется ≥1 раз в неделю активными пользователями.

### Фаза 14: Семантические стражи (Semantic Guardians) 🟢 Низкий — Гипотеза

**Приоритет:** 🟢 Низкий (после кластеризации и архива)
**Статус:** 💡 Идея
**Целевая платформа:** Mobile (сначала PWA, затем нативное приложение) — desktop показывает состояние стражей, но не является основным интерфейсом взаимодействия.
**Описание:** Пассивная геймификация гигиены знаний через персонифицированного стража кластера.

- Каждый кластер получает стража — семантическую фигурку, отражающую суть кластера (герой, бог, автор, предмет). Пользователь называет стража сам.
- Страж привязан к кластеру и может быть перемещён между кластерами (drag-and-drop, touch-оптимизировано для мобильного).
- Сила стража зависит от свежести заметок в кластере, общего количества связей, завершённости кластера и наличия архивных заметок.
- **Волны забвения** пассивно атакуют кластер, если он не обновлялся M дней (ежедневно/еженедельно). Страж автоматически отбивает атаку (авто-анимация), если кластер активен.
- Push-уведомления: «Волна забвения приближается к кластеру "Философия". Достоевский готов защищаться».
- Перемещение стража = переприоритизация: кластер-донор тускнеет, кластер-акцептор усиливается.
- **Семантическая обратная связь:** страж, названный пользователем («Достоевский», «Проект Альфа»), служит напоминанием о заброшенной теме.
- **Гипотеза:** персонифицированные стражи (особенно в мобильном приложении с push-уведомлениями) создают эмоциональную связь с заметками и мотивируют возвращаться к заброшенным темам.
- **MVP:** ручное именование стража кластера, drag-and-drop между кластерами, одна фигурка-силуэт, анимация волны забвения; мобильный PWA-интерфейс (`features/guardians/` + `widgets/guardians-viewer/`) с push-уведомлениями.
- **Зависимости:** Фаза 11 (Галактические кластеры), Фаза 15 (Архив и гигиена заметок), NLP-сервис для будущей авто-генерации имён.
- **Validation:** рост возвратов к «забытым» кластерам на ≥20% в течение месяца; ≥30% активных пользователей дают имя хотя бы одному стражу.

### Фаза 15: Архив и гигиена заметок (Archive & Note Hygiene) 🟡 Средний — Запланирована

**Приоритет:** 🟡 Средний (перед Семантическими стражами)
**Статус:** ⏳ Запланирована
**Описание:** Механика автоматической архивации неиспользуемых заметок.

- Заметка, не обновлявшаяся N дней, с низкой активностью связей и не помеченная как важная, автоматически помечается как «забытая».
- Забытые заметки тускнеют в графе, связи прерываются.
- При достижении критического порога заметка уходит в **Архив** (скрывается из основного графа).
- Архив — отдельный слой графа, не влияющий на основную навигацию. Режим просмотра архива.
- Пользователь может вручную архивировать/разархивировать заметки.
- После Фазы 14 страж кластера может защищать заметки в кластере от архивации.
- Метрика «здоровья графа»: процент активных заметок к общему числу.
- **Гипотеза:** автоматическая архивация снижает когнитивную нагрузку и поддерживает граф в актуальном состоянии.
- **MVP:** ASYNQ scheduled task для пометки «забытых» заметок, UI-переключатель в архив, endpoint для ручной архивации.
- **Зависимости:** нет (базовая механика над существующей моделью заметок); интеграция со стражами (Фаза 14) — опционально.
- **Validation:** ≥70% автоматически архивированных заметок не разархивируются вручную в течение месяца; пользователи отмечают, что граф стал «чище» (опрос/фидбек).

### Фаза 16: Лидерборды и публичные вселенные (Leaderboards & Public Universes) 🟢 Низкий — Гипотеза

**Приоритет:** 🟢 Низкий (после социальных фич)
**Статус:** 💡 Идея
**Описание:** Публичный рейтинг пользователей по активности в графе плюс публичная страница «вселенной» пользователя.

- Backend: агрегация метрик (число заметок, связей, streak) с кэшем в Redis.
- Топ по количеству заметок/связей/streak, обновление раз в N часов (не realtime).
- Публичная страница вселенной `routes/u/[username]` — переиспользует существующий публичный граф (`/api/v1/graph/public`).
- Приватность: пользователь может выключить показ в лидерборде, оставив публичный граф видимым (или наоборот).
- **Гипотеза:** видимость прогресса и чужих «вселенных» повышает вовлечённость и мотивирует держать граф в порядке.
- **MVP:** топ-N лидерборд по количеству заметок (`routes/leaderboard`) + публичная страница вселенной, переиспользующая публичный граф.
- **Зависимости:** публичные заметки ✅ (готово), 🎮 Геймификация (очки/ачивки, сейчас в бэклоге).
- **Validation:** ≥15% пользователей с публичными заметками просматривают лидерборд минимум раз в неделю.

### Фаза 17: Пересылка заметок (Social Sharing) 🟡 Средний — Запланирована

**Приоритет:** 🟡 Средний
**Статус:** ⏳ Запланирована
**Описание:** Отправка заметки другому пользователю по username, с входящим Inbox у получателя.

- Backend: таблица `note_shares` (`note_id`, `sender_id`, `recipient_id`, `status`, `created_at`).

- **Связано:** входит в кандидаты TD-3 (Полная реализация SSE) для мгновенного уведомления получателя вместо появления при следующей загрузке списка.

### Фаза 18: Социальный слой (Чат и гильдии) 🟢 Низкий — Гипотеза

**Приоритет:** 🟢 Низкий (последняя фаза — нужна набранная аудитория)
**Статус:** 💡 Идея
**Описание:** Личные сообщения между пользователями, в перспективе — гильдии/группы вокруг общих графов.

- Гильдии (группы, общий доступ к части графа) — отложить до валидации личных сообщений на реальных пользователях.
- **Гипотеза:** прямое общение вокруг общих тем/заметок удерживает пользователей и создаёт сетевой эффект.
- **MVP:** 1:1 личные сообщения без гильдий.

### 💡 Runtime-конфигурация в БД 🟢 Низкий — Идея

**Приоритет:** 🟢 Низкий  
**Статус:** 💡 Идея  
**Описание:** Хранить редко меняющиеся runtime-параметры в таблице `system_config` и дать защищённый admin API для CRUD + ручной reload.

- **Объём:**
  - Только runtime tunables: rate limits, лимиты графа/рекомендаций/пагинации, password policy, UI thresholds.
  - Секреты (JWT_SECRET, SMTP-пароли, OAuth credentials) остаются в env/JSON.
- **API:**
  - `GET /api/v1/admin/system-config` — список.
  - `POST /api/v1/admin/system-config` — создать ключ/значение.
  - `PATCH /api/v1/admin/system-config/:key` — обновить значение.
  - Защита через `STATIC_API_KEY` (в будущем `RequireAdmin()`).
- **Runtime effect:** загрузка из БД при старте; endpoint ручного reload для обновления in-memory `config.Config`.
- **Валидация:** отложена; рассмотреть строгий registry допустимых ключей и типов.
- **Риски:** дрейф между `knowledge-graph.config.json` и БД; кэширование/reload между инстансами backend и worker.
- **MVP:** миграция + репозиторий + сервис + хендлер + reload endpoint + интеграционные тесты.
- **Зависимости:** паттерн `user_settings`, `RequireAdmin`, `CacheClient`.
- **Критерии успеха:** изменение rate limit через API и reload влияет на живые запросы без рестарта; после внедрения валидации не принимаются невалидные ключи.

### 💡 Движение графа на основе метрик и кластеров 🟢 Низкий — Идея

**Приоритет:** 🟡 Средний (после Фазы 11 Галактические кластеры)  
**Статус:** 💡 Идея  
**Описание:** Перейти от случайного per-node движения к структурно осмысленной анимации: параметры вращения/свечения/частиц зависят от степени узла, расстояния от центра и кластерной принадлежности.

- **Объём:**
  - Скорость вращения, плотность частиц, активность короны и частота пульсации зависят от:
    - степени узла (hubs крутятся/пульсируют иначе),
    - расстояния от центра графа,
    - кластерной принадлежности (`cluster_id` из `/graph/full`, Фаза 11),
    - типа/аномалии заметки.
  - Сохранить текущий fast-fix рандомизацию как fallback при отсутствии структурных данных.
- **Необходимые runtime-данные:**
  - `cluster_id` в ответе `/graph/full`.
  - Предпосчитанная степень узла и/или closeness (graph-service).
  - Опционально: семантическая «масса» из embeddings/NLP.
- **Примеры визуальных маппингов:**
  - Высокостепенные узлы: медленное, тяжёлое вращение; сильное свечение.
  - Периферийные узлы: быстрее, меньше частиц.
  - Узлы одного кластера: общий оттенок/направление орбиты.
  - Comet с множеством исходящих связей: более активный хвост.
- **MVP:** добавить `degree`, `cluster_id`, `distance_from_center` в graph payload; использовать их в `animation.ts`/`particle-system.ts` для смещения существующих параметров.
- **Зависимости:** Фаза 11 (Галактические кластеры), обогащение API graph-service, опционально Phase 16 (DB-backed config) для настраиваемых коэффициентов маппинга.
- **Риски:** чрезмерная сложность motion вредит производительности на 500+ нодах; нужна graceful degradation.
- **Критерии успеха:** по движению видно, где hubs/центр, а где периферия; граф перестаёт выглядеть синхронным скринсейвером.

## ⚠️ Технический долг и исследования

### TD-1: Автоматическое назначение CelestialBody (MVP)

**Приоритет:** 🟡 Средний
**Статус:** ⏳ Запланирован
**Описание:** Временное автоматическое назначение типа небесного тела на основе размера заметки и количества связей. Проблема: сейчас типы CelestialBody назначаются вручную и не имеют семантической привязки. Автоматическое определение через кластеризацию и NLP — сложная задача, требующая данных о реальном использовании. Нужно временное правило, чтобы типы имели хотя бы базовый смысл.

- **Градация по количеству символов:**
  - 0–100 → Осколок (астероид)
  - 100–500 → Комета
  - 500–2000 → Планета
  - 2000–10000 → Звезда
  - 10000+ → Галактика
- **Модификаторы:**
  - > 5 связей → повысить тип на один уровень (Планета → Звезда)
  - Нет связей → понизить тип (Звезда → Комета)
  - Сирота и <100 символов → Космическая пыль (почти не видна)
- Тип пересчитывается при каждом сохранении заметки.
- **Важно:** это временное решение. После внедрения кластеризации и накопления данных о пользовательском поведении логика будет пересмотрена.
- **Зависимости:** нет (использует существующие поля size и связи).

### TD-3: Полная реализация SSE вместо HTTP-polling

**Приоритет:** 🟡 Средний (устраняет реальную проблему производительности/нагрузки)
**Статус:** ⏳ Запланирована
**Контекст:** В приложении сейчас **нет** ни одного push-канала до браузера. То, что выглядит
как «events» — на самом деле обычный HTTP polling:

- `GET /graph-service/api/v1/graph/delta?last_hash=...` — фронтенд опрашивает раз в 30 секунд
  и при window focus (`frontend/src/features/home-page/home-page.svelte.ts`).
- `GET /api/v1/users/me/achievements` — по-прежнему использует защищённый interval polling в
  `frontend/src/entities/achievement/model/store.svelte.ts`; значение интервала `0` отключает
  таймер и предотвращает прежний tight loop.
- Единственный реальный pub/sub в проекте — Redis Pub/Sub между backend и graph-service
  (`backend/internal/infrastructure/events/publisher.go` → `services/graph-service/internal/subscriber/pubsub.go`),
  используется только для инвалидации кэша графа на graph-service, наружу к браузеру не транслируется.
- В ADR-015 SSE для ачивок помечен как TODO ещё на этапе принятия решения, но реализация
  так и не была сделана — вместо этого закрепился polling.

**Описание:** Спроектировать и реализовать единый SSE-слой (`text/event-stream`,
`EventSource` на фронте) для всех сценариев, где сейчас используется polling или где нужны
уведомления в реальном времени, переиспользуя существующую Redis Pub/Sub инфраструктуру
как транспорт между сервисами.

**Кандидаты на перевод с polling/refresh-after-action на SSE:**

1. **Ачивки** (`/api/v1/users/me/achievements`) — событие `AchievementUnlocked` пушится сразу
   после того, как `achievement.Service.CheckTrigger` сохраняет `UserAchievement` (сейчас это
   выполняется в фоновой горутине после ответа на create note/link — идеальное место для publish).
2. **Дельта графа** (`graph-service/api/v1/graph/delta`) — событие `GraphChanged` при
   NoteCreated/NoteUpdated/NoteDeleted/LinkCreated/LinkDeleted вместо периодического пулла
   каждые 30с; устраняет и polling, и связанное с ним «моргание графа» при неудачных дельтах.
3. **Достижение стрика логина / прогресс streak** (`GetStreak`, пока не имеет отдельного
   роута на бэкенде — см. отсутствующий `GET /api/v1/users/me/streak`, обнаруженный при
   аудите OpenAPI) — можно сразу спроектировать под push-модель.
4. **Уведомления о совместном доступе** (`share`) — когда кому-то предоставили доступ к
   заметке (`ShareNote`), адресат может получить мгновенное уведомление вместо обнаружения
   при следующей загрузке списка.
5. **Draft-конфликты** (`draft.SyncDraft` / `ResolveConflict`) — сейчас клиент должен сам
   узнать о конфликте синхронизации; SSE может проактивно уведомить об изменении состояния
   черновика с другого клиента/вкладки.
6. **Achievements/streak toast в реальном времени между вкладками** — сейчас у каждой вкладки
   свой независимый polling; один SSE-коннект на пользователя устраняет дублирование.

**Архитектура (план):**

- Backend: единый SSE-хаб (`internal/infrastructure/sse` или аналогично) — реестр активных
  подключений по `user_id`, с graceful обработкой обрыва соединения и переподключения.
- Транспорт между инстансами backend: тот же Redis Pub/Sub (`internal/infrastructure/events`),
  расширенный новыми типами событий (`AchievementUnlocked`, `GraphChanged`, `ShareCreated`,
  `DraftConflict`), которые публикуются из соответствующих application-сервисов.
- Endpoint: `GET /api/v1/events/stream` (единый мультиплексированный стрим на все типы событий
  для одного пользователя, с полем `event:` в SSE-фрейме для маршрутизации на фронте) —
  предпочтительнее нескольких стримов на каждую фичу.
- Frontend: единый `EventSource`-клиент в `shared/services` с авто-переподключением
  (`retry`, backoff) и подпиской компонентов на нужные типы событий; при разрыве соединения —
  временный fallback на существующий polling/refresh-after-action, чтобы не терять
  функциональность при недоступности SSE (прокси/файрвол/старый браузер).
- Both nginx-шлюзы (dev/personal) должны поддерживать долгоживущие HTTP-соединения без
  буферизации (`proxy_buffering off`, увеличенный `proxy_read_timeout`) — проверить конфиги
  `docker/nginx/*`.

**MVP:** один SSE-эндпоинт (`/api/v1/events/stream`) только для достижений (`AchievementUnlocked`),
переиспользующий существующий Redis Pub/Sub канал; после стабилизации — расширение на
`GraphChanged` и остальные кандидаты из списка выше.

**Зависимости:** нет новых внешних сервисов (используется существующий Redis); требует
согласования с `knowledge-graph-security` по аутентификации долгоживущих SSE-соединений
(JWT в query-параметре или отдельный short-lived token, т.к. `EventSource` не поддерживает
кастомные заголовки).
